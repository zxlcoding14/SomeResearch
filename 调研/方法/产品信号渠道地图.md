# 产品信号渠道地图 — 找需求 / 找场景 / 找思路，去哪些网站，怎么用（**Windows 桌面工具为主场景**）

> **文档类型**：方法论索引（渠道清单 / 入口路径 / 检索式 / 使用纪律），非具体产品分析
> **视角**：产品经理（PM）
> **主场景（v1.1 追加）**：**Windows 桌面工具（面向知识工作者的效率型 mini-tool）**。§一—§六 为**平台通用内容**（Mac / Web / 移动同样适用）；**§七 是 Windows 专属渠道与用法**（含官方需求池、国内悬赏区、系统内置雷达）。不做 Windows 时可整章跳过。
> **适用对象**：个人开发者、小团队、内部创新小组；不限品类（软件 / SaaS / AI 工具 / 硬件 / 内容产品）
> **适用场景**：① 想知道"除了刷榜单还能去哪找需求" ② 手上有一堆想去的网站但不知道每个该看哪一块 ③ 想把零散的采集动作固化成排期 ④ **在 Windows 上找效率工具的机会点**
> **版本**：v1.1（2026-10-13）
> **本文要回答的 3 个问题**：① 找需求/场景/思路**有哪些渠道**（尽量铺全）？② **每个渠道具体怎么用**（看哪一块、搜什么词）？③ 怎么把这些渠道**串成一条可持续运转的管线**？
> **数据口径声明**：本文只给渠道清单、入口路径与检索方法，**不含任何平台的用户量、活跃度、市场规模等外部量化数据**。渠道的"信噪比/成本"评级为**经验判断**，非实测统计。文中示例均为格式示范。

## 〇、结论先行（TL;DR）

1. **渠道要按「证据强度」分级，不能按「名气」分级。** 四层：**T0 自有摩擦 → T1 行为证据（差评 / 求助 / 手工痕迹 / 代做 / 需求池）→ T2 结构信号（招聘 / 政策 / 平台窗口 / 竞品 Non-scope）→ T3 趋势线索（榜单 / 指数 / 资讯）**。**T3 只能当线索，不能作为立项依据**——而多数人 90% 的采集时间恰恰花在 T3 上。

2. **一条渠道值不值得用，只问一件事：它能不能给出这四样之一** —— ① **行为证据**（有人已为此付过钱 / 已在手工做）② **场景原话**（可逐字当落地页文案的表述）③ **价格锚点**（真实成交价）④ **可触达名单**（能指名到具体人/社群）。四样都给不了的渠道 = 娱乐消费，不是采集。

3. **信噪比最高、成本最低的 5 个渠道**（按投入产出比排序）：
   `① 竞品 1–3 星差评（G2 · App Store · Chrome 商店）` > `② GitHub 按 👍 排序的 open feature request` > `③ 代做市场在售（闲鱼 · Fiverr）` > `④ 招聘 JD 里的重复动作` > `⑤ 自己的摩擦日志`。
   **前三者本质上是"别人已经写好的需求说明书，还带了票数和价格"。**

4. **国内 × 海外必须分开配比，用途不同。** 海外渠道（Reddit / G2 / Hacker News / Fiverr）**用来找模式与价格锚点**；国内渠道（V2EX / 少数派 / 小众软件 / 闲鱼 / 小红书 / 即刻）**用来找场景原话与触达路径**。做中文市场的产品，**海外找"什么样的需求成立"，国内找"具体这句话怎么说"**——直接迁移海外的场景原话会踩文化差异的坑。

5. **渠道要按「信号类型」配比，而不是按数量堆。** 一个健康的采集配方：**差评类 40% + 求助类 20% + 手工痕迹/代做 20% + 结构信号（招聘/政策/窗口）15% + 趋势类 5%**。收藏 100 个网站不如固定跑 8 个，并且**排期化**。

6. **同一渠道，"看哪一块"决定信息量。** App Store 要按**「最低评分 + 最新」**排序而不是默认好评；G2 要看 **"Cons" / "What do you dislike"** 而不是 Pros；V2EX 要去**「创意 / 分享创造 / 问与答」**节点而不是首页热帖；GitHub 要按 **👍 reaction 排序**而不是 Star。**渠道对了、板块错了 = 零信息。**

7. **所有采集必须可复现。** 每条信号留**检索式 + 链接 + 采集日期**三件套。凭印象翻榜单的结果无法复核、无法交叉验证，等于没采。

8. **渠道会死、会变。** 社区类渠道（小红书 / 即刻 / Discord）活跃度与内容生态变化最快，搜索引擎语法（GitHub / 站内搜索）也常变。**建议每 6 个月复核一次本清单的入口路径。**
9. **【Windows 主场景】三个 Windows 独占渠道必须加进你的采集体系**：① **微软 Feedback Hub**（官方需求池，用户自己写的需求 + upvote，全网最被忽略的高信噪比池子）② **52pojie（吾爱破解）悬赏求助区**（中文最强的"有人愿付钱"信号 + 直接的价格锚点）③ **Windows Insider 新功能 + PowerToys release notes**（**窗口期雷达**）。**Windows 效率工具的第一死因是"被系统内置"**——截图、窗口管理、录屏、压缩、剪贴板历史、批量重命名都已被吃过多轮。做不到"开工前先扫一遍系统会不会做"，其他采集都是白做。详见 §七。
10. **判断竞品「靠什么赚钱」，读技术痕迹，不读营销话术。** 官网"我们不做广告 / 不设电商 / 数据不外卖"是**宣称**（会滞后、会刻意弱化）；**SDK 披露页 / 应用商店 IAP SKU / 权限与隐私标签**是**技术痕迹**（监管强制披露或直接有商业后果，**没有说谎的动机**）。**两者冲突时以技术痕迹为准，且"冲突"本身就是结论。** 实证：某产品官网三处否认广告与电商，其 SDK 披露清单却列了 **11 个广告联盟 SDK**、商店还在卖「免广告季卡」。详见 §3.10。

## 一、渠道的四层分级：为什么"榜单"是最差的起点

### 1.1 四层模型

| 层 | 名称 | 本质 | 给什么 | 典型渠道 | 能否作为立项依据 |
|---|---|---|---|---|---|
| **T0** | 自有摩擦 | 你自己身上的一手需求 | 最真实的一手痛点（但样本 = 1） | 个人摩擦日志 | ❌ 只能当线索，必须外部交叉验证 |
| **T1** | **行为证据** | 别人已经用**钱或时间**投过票 | 付费意愿 + 工具缺口 + 场景原话 + 价格锚点 | 差评区、求助区、代做市场、需求池、教程/模板 | ✅ **主战场**，权重最高 |
| **T2** | **结构信号** | 由**制度/技术/预算**结构决定的缺口 | 有预算的痛点、新场景入口、竞品软肋 | 招聘 JD、招标公告、政策法规、平台 changelog、竞品 Non-scope | ✅ 需解读，但独占性最强 |
| **T3** | 趋势线索 | 别人做出来的**结果** | 命名与形态灵感、热度方向 | Product Hunt、HN、Google Trends、行业媒体、榜单 | ❌ **只能当线索** |

> **一句话**：T1 告诉你"什么需求被验证过"，T2 告诉你"什么需求马上要出现"，T3 只告诉你"别人已经做了什么"。**T3 是滞后信号——你看到的时候，红利期往往已过半。**

### 1.2 渠道筛选的四个拷问（30 秒决定要不要在这个渠道花时间）

| # | 问题 | 通过 | 不通过 |
|---|---|---|---|
| 1 | 这里能看到**真实行为**吗？（付费记录 / 外包报价 / 手工痕迹） | 有 → 高价值 | 只有观点和讨论 → 降级为 T3 |
| 2 | 这里能拿到**逐字原话**吗？（而非二手转述、总结稿） | 有 → 可当文案库 | 只有"综合报道" → 只作线索 |
| 3 | 这里有**价格数字**吗？（成交价 / 报价 / 预算） | 有 → 直接定价锚点 | 无 → 后续单独找 |
| 4 | 这里能**指认出具体的人/社群**吗？（后续可触达） | 有 → 分发线索 | 无 → 无法验证 |

> **四问全不过 → 这个渠道只适合"拓视野"，不要写进采集排期。**

### 1.3 信噪比 × 采集成本 四象限

| 象限 | 渠道 | 行动建议 |
|---|---|---|
| **高信噪比 · 低成本** | 竞品差评、GitHub 高赞 issue、代做市场销量、招聘 JD、自己的摩擦日志 | **立即做**：投入产出比最高的采集区，占你 70% 以上时间 |
| **高信噪比 · 高成本** | 20 人定向深访、人肉代做 5 单、真实采购方/决策人访谈、行业展会 | **值得投时间**：用于验证快筛通过后的方向 |
| **低信噪比 · 低成本** | Product Hunt 榜单、Hacker News 首页、行业报告、大厂发布会、热搜 | **只当线索**：拓视野用，不写进采集库 |
| **低信噪比 · 高成本** | 大规模问卷、TAM 精算、全量竞品功能对比表 | **别做**：早期投入产出比最差 |

## 三、逐类渠道详解：每个渠道具体怎么用

> 本章只展开**最需要"入口路径"的类别**；操作方法与前两章重复的部分不再赘述。

### 3.1 差评区（最高信噪比，第一优先）

**核心动作：抓 1–3 星评论，做名词/动词词频统计。** 高频出现的名词与动词 = 功能缺口清单。

| 渠道 | 具体入口路径 | 关键技巧 |
|---|---|---|
| App Store | 应用页 → 评分与评论 → 右上角排序选「**最低评分**」+ 切「最新」 | iOS 只能看部分区域；可用 App Store 网页版切换地区多看几个市场 |
| Google Play | 应用页 → 评价 → 筛选「**1 星**」+ 排序「最新」 | 支持按设备/版本筛选，能定位"哪个版本开始变差" |
| G2 | 搜产品 → 页面内找 **`Cons`** 标签页 / 筛「1–2 星评价」 | G2 有时把 Cons 折叠，需展开；注意区分"评产品"与"评供应商服务" |
| Capterra | 产品页 → Reviews → 按最低分筛选 | 与 G2 交叉看，避免单平台样本偏 |
| Chrome Web Store | 扩展页 → 评论 → 排序选「**最低评分**」 | 注意区分"扩展本身差"与"某网站改版导致失效" |
| 少数派 / 小众软件 | 直接进**评论区**，看被顶到最上面的反对意见 | 正文是吹，评论区才是真话 |
| 知乎 | 搜 `<产品名> 缺点` / `<产品名> 难用` / `<产品名> 平替` | 关注"高赞反对回答" |

**判读纪律**：
- **区分「产品差」与「功能缺」**：前者是它的机会（你可以做得更好），后者是你的机会（它根本没有这个能力）。
- **区分「抱怨价格」与「抱怨缺失」**：如果用户骂的是"太贵"而不是"没这个功能"，说明这个生意你做不了（除非你能大幅降本）。
- **必须意识到样本偏差**：只有不满意的用户才会写差评。**差评给你的是"缺口清单"，不是"缺口强度"。**

### 3.2 求助区（场景原话库）

**核心动作：只收「带具体场景 + 已试过什么方案」的求助帖。** 这类帖子的原话可以直接改成落地页文案。

| 渠道 | 具体入口（可直接构造 URL/搜索） |
|---|---|
| Reddit | `site:reddit.com "<品类词>" alternatives` · `site:reddit.com "is there a tool that" <任务词>` |
| V2EX | `site:v2ex.com/t "求推荐" <任务词>` · `site:v2ex.com/t "有没有" <任务词>` · 或直接进 **`/go/create`（创意）**、**`/go/share`（分享创造）** 节点 |
| 少数派 | `site:sspai.com <任务词>` |
| 小众软件 | `site:appinn.com <任务词>`（看文章留言的"求同类"） |
| 知乎 | `site:zhihu.com "求推荐" <任务词>` · `site:zhihu.com "有没有" <任务词> "的工具"` |
| 即刻 / 小红书 | 站内搜 `<任务词> 求推荐` / `<任务词> 有没有更好用的` |

**关键判读**：帖子**浏览量高 ≠ 需求强**。真正有价值的是"发帖人已经试过 3 个方案都不满意"——那说明现有替代确实糟糕。

### 3.3 手工痕迹（工具缺口的最强信号）

**核心公式**：`需求密度 ≈ 教程数量 ÷ 工具成熟度`。某件事教程极多、却没有一个成熟工具 → 缺口最大。

| 动作 | 检索式 | 判断 |
|---|---|---|
| 教程密度 | `"如何用 Excel 做" <任务词>` · `<任务词> python 脚本 批量` · `site:bilibili.com <任务词> 教程 批量` | 教程多 + 无成熟产品 = 缺口 |
| 模板热卖 | Notion 模板榜、Gumroad、WPS 稻壳、飞书模板中心 | 有人在为"流程"付费 = 流程可产品化 |
| 脏脚本 | `github.com/search?q=<任务词>+script&s=stars` | 高手在自己写 = 工具缺失 |
| 口语线索 | `<任务词> "手动" "一个个" "太慢了" "只能"` | 用户的自述痛点原话 |

### 3.4 代做市场（最真实的价格锚点）

**核心动作：看销量、复购率、买家评价中的抱怨。** 这是全网**最被低估**的一类渠道——它同时给出"需求存在 + 有人愿意付钱 + 具体价格"。

| 渠道 | 具体操作 | 提取字段 |
|---|---|---|
| 闲鱼 | 搜「`<任务词>` 代做」→ 按"销量/想要"排 | 报价区间、月销、买家追问 |
| 淘宝 | 搜「代做 / 代运营 / 代写 / 代录 / 数据整理」 | 阶梯报价、复购评论 |
| Fiverr / Upwork | 搜任务词 → 看 gig 数量与起价 | 全球价格锚点、需求密度 |
| 猪八戒 / 一品威客 | 看企业类目的成交记录 | B 端服务价格 |

**纪律**：**平台销量可刷**，必须**交叉 2 个以上平台**，并优先看"买家评价里提到的具体抱怨"（那才是真实使用场景）。

### 3.5 需求池（GitHub / Canny）

**GitHub 是全网性价比最高的需求池**：按 👍 排序的 open feature request ≈ **一份用户自己写好的、带票数的需求清单**。

```
is:issue is:open label:"feature request" sort:reactions-+1 <关键词>
is:issue is:open sort:reactions-+1 <关键词>
is:pr is:open <关键词>              （看社区自己在补什么 = 社区缺什么）
stars:>500 <关键词> pushed:>2026-01-01   （找活跃的可复用轮子）
```

**Canny / UserVoice 类公开需求板**：很多 SaaS 把 roadmap 公开，直接能看到它的用户**按票数排序**在要什么——这既是需求清单，也是竞品的 Non-scope。

### 3.6 招聘 JD（被严重低估的一类）

**底层逻辑**：**企业愿意为某个岗位付月薪，就说明这件事的价值已被验证、且有预算科目。** JD 里的重复动作，就是下一代工具的需求说明书。

**怎么做**：搜 `<任务词> 专员 岗位职责`，只记 JD 里出现「**手工**」「**重复**」「**核对**」「**一一**」「**录入**」的动作描述。

> **免责前提**：**岗位存在 ≠ 该任务可自动化**。有些岗位存在恰恰是因为需要人的判断。**看 JD 里是否明确写了"手工/重复/核对"类动作**，这才是可工具化的部分。

### 3.7 政策与平台窗口（新场景的主要来源）

| 信号类型 | 去哪看 | 产出 |
|---|---|---|
| 新合规要求 | 部委政策发布页 / 行业协会通知 | 强制型痛点（P5），"不做就不能采购" |
| 新 API / 新能力 | 各平台开放平台 changelog、Apple/Google 开发者文档、模型 API 更新页 | "新能力 × 老痛点"交集 = 新场景 |
| 新分发入口 | 插件/扩展市场的新类别、MCP 生态 | 低成本获客窗口 |
| 竞品明确不做 | `site:support.<厂商域名> "not supported"` · `<产品名> pricing` 对比表 | 差异化切口（信息量最高的一层） |

### 3.8 趋势类（只当线索，务必克制）

**Product Hunt / HN / 榜单的用法限制**：
- 拿到的是**别人的答案**，不是"为什么它能成"；
- 它是**滞后信号**——上榜说明需求已被别人验证并吃过一轮；
- 榜单名次由运营与社区投票决定，**名次 ≠ 需求强度**。

**正确用法**：把榜单当"**命名与形态的灵感库**"，然后**立刻去差评区和代做市场找同一需求的真实证据**。

### 3.9 供给侧（先判死，再省钱）

**顺序固定：先查"会不会被免费方案吃掉"，再查"能复用哪些开源"。**

| 要回答的问题 | 去哪查 |
|---|---|
| 有没有现成的替代品？ | AlternativeTo / Slant 输入你的产品概念，看 alternatives |
| 开源是否已覆盖 80%？ | GitHub 搜项目 → 记 **项目名 + Stars + 许可 + 最近推送 + 覆盖度** |
| 系统是否已内置？ | 查当前 OS/平台版本的功能清单与开发计划 |
| 能力底座是否已有？ | RapidAPI / 官方 API 文档 |

> 详细方法见 `开源竞品与可复用能力.md`（该类渠道的专项文档）。

### 3.10 竞品变现结构穿透（用技术痕迹替代营销话术）★

> **一句话**：判断一个产品靠什么赚钱，**别读它的官网 FAQ，去读它的 SDK 披露页和商店 SKU 列表**。

**为什么必须这样做**：官方"我们不做广告 / 不设电商 / 数据不外卖"是**宣称（claim）**——会因品牌定位、口径滞后或刻意弱化而失真；而 **SDK 披露清单 / 隐私政策第三方条款 / 应用商店 IAP SKU / 权限与隐私标签**是**技术痕迹（trace）**——由监管强制披露，或直接产生商业后果，**没有说谎的动机**。

> **实证（2026-10-15 · 体重小本）**：官网 FAQ 三处明确写"不推食品、不卖保健品、**没有减肥课程广告**""**不在 APP 里设置电商模块**"，据此初判「广告被否、电商被否」。但：
> ① 官网《第三方数据合作》披露页列出 **11 个广告类 SDK**（穿山甲 / Gromore / 优量汇 / 快手联盟 / 百度联盟 / 倍孜 / 天目 / ADmobile / Taku / 美数 / 酷盈），多个明示采集 iOS 的 **IDFA / IDFV**；
> ② App Store 在售 **「免广告季卡 ¥12.80」**；
> ③ 会员协议 4.3.1 自认"不会**根据敏感类别**展示**个性化广告**"——反向承认存在非敏感类别的个性化广告。
> → **三段技术证据合起来推翻了官网宣称。** 该项目前两份报告因此判错，第三份才修正。**这就是"读话术"与"读痕迹"的差别。**

#### 四个证据源（按硬度排序）

| # | 证据源 | 入口路径 | 能判定什么 | 硬度 |
|---|---|---|---|---|
| 1 | **第三方 SDK 披露页 / 隐私政策「与第三方共享信息」章节** | 官网底部（ICP 备案行附近）→「第三方信息共享清单 / SDK 目录」；或在隐私政策全文搜 `SDK` | **广告变现**（广告联盟 / 聚合 SDK）、**电商**（有赞 / 微盟）、**数据驱动运营**（神策 / 友盟 / GrowingIO）、推送、崩溃监控 | 高 |
| 2 | **应用商店 IAP / 商品 SKU 列表** | App Store 应用页 →「App 内购买项目」；Google Play →「应用内购买项目」 | 变现**档位与结构**：有无「免广告」权益（→ 说明有广告）、买断档、周期档、消耗型点数 | 高 |
| 3 | **权限与隐私标签** | App Store →「App 隐私」标签（是否声明「用于追踪」）；Android → Manifest 权限 + 商店隐私说明 | 是否做**个性化广告 / 跨 App 追踪**；是否采集敏感权限 | 高 |
| 4 | **抓包实测（兜底）** | 代理抓包（Charles / mitmproxy）看是否请求广告联盟域名 | **最终确证**——仅前三条互相矛盾、或结论要对外拍板时用 | 最高（成本也最高） |

#### SDK 厂商 → 变现类型 归因表（把 SDK 名翻译成商业模式）

| SDK 类型 | 典型厂商 | 它说明了什么 |
|---|---|---|
| **广告聚合 / 中介** | **GroMore（穿山甲系）**、**Taku（TopOn）**、**ADmobile**、**美数 AdMate** | 不只是"有广告"，而是**已在做多平台竞价变现**（变现成熟度信号） |
| **广告联盟** | **穿山甲（字节）**、**优量汇（腾讯）**、**快手联盟**、**百度联盟**、倍孜 / 天目 / 酷盈 | 程序化广告变现 |
| **电商 / 商城** | **有赞**、**微盟** | **存在电商变现**（可能含实物履约） |
| **数据 / 分析** | 神策、友盟、GrowingIO、Firebase | 数据驱动的留存与转化运营（**≠ 数据变现**，后者需另证） |
| **支付** | 微信支付 / 支付宝 SDK | 存在**非商店支付路径**（自有渠道收款） |

#### 一个必须先区分的口径陷阱

> **「没有内容型广告」≠「没有广告」。**
> 官网原话是"没有**减肥课程**广告"——限定的是**广告内容类型**，不是**不投放广告**。把官方的**限定语**读成**全称判断**，是这类分析里最高频的一处偷换。

#### 五步动作（30 分钟可完成）

1. **找披露页**：官网底部 → 隐私政策 →「第三方信息共享清单 / SDK 目录」。找不到就进第 2 步。
2. **抄商店 SKU**：应用页「App 内购买项目」**全量抄录**（名称 + 价格 + 周期 + 是否首期优惠）。
3. **归因**：按上表把 SDK 与 SKU 逐条翻译成变现类型。
4. **对撞宣称**：与官网 FAQ / 白皮书里所有"我们不做 X"逐条比对。**冲突 = 结论**——冲突要么说明官方口径滞后，要么说明它在刻意弱化某条变现线，**两者都是高价值发现，不是噪声**。
5. **定级**：`技术痕迹 > 商店标价 > 官方文档 > 官网宣称`。**结论只能建立在技术痕迹上**；官网宣称只代表"厂商希望你怎么看它"。

#### 产出物：竞品变现结构还原表

```
| 变现类型 | 技术证据 | 具体条目 | 采集点 | 与官方宣称是否冲突 | 证据强度 |
|---|---|---|---|---|---|
| 广告 | 聚合 SDK | GroMore + Taku | 官网 SDK 清单 | ✅ 冲突 | 高 |
| 免广告权益 | IAP SKU | 免广告季卡 ¥12.80 | App Store | 补强上条 | 高 |
| 订阅 | IAP SKU | ¥88/年、¥168 永久 | App Store | — | 高 |
| 电商 | SDK | 有赞商城 | 官网 SDK 清单 | ✅ 冲突 | 中（待实测） |
```

#### 什么时候必做

- 你要给一个**"克制型产品"**判定价与天花板 → **它是否真的克制，决定你能否复制它的模式**；
- 你要判断**赛道头部靠什么赚钱** → 它的收入结构就是这条赛道目前的最优解形状；
- 你要**引用官方口径写进报告** → 先过这一遍，否则容易被营销话术带走（本项目已实际踩过一次）。

#### 三条纪律

1. **不做双份证据不下"有 / 无"判断**：至少 `SDK 清单 + 商店 SKU` 两处互证。
2. **披露页是"当前态"**：SDK 清单可能滞后或被精简，**变更历史拿不到**；要判"何时开始做"，需用商店 SKU 上下架时间 + 版本更新日志交叉。
3. **"SDK 存在" ≠ "业务在运营"**：有赞可以是遗留接入 → **必须再用商品页 / 下单流程实测确认**，否则只能定级为"待实测"。

## 五、把渠道串成管线：使用 SOP

### 5.1 日 / 周 / 月 / 季 排期（落到具体渠道）

| 周期 | 时长 | 固定动作（写死渠道） | 产出 |
|---|---|---|---|
| **每日** | 15–30 min | ① 读 1 个**竞品差评页**（App Store 最低分 / G2 Cons / Chrome 商店低分）② 逛 1 个**求助区**（V2EX / 即刻 / 少数派 / 小众软件 / 对应 Reddit sub）③ 记 1 条**自己的重复摩擦** | 摩擦日志 + 信号草稿 |
| **每周** | 2 h | 补全来源链接 + 日期；**合并同类项**；更新机会库/问题库 | 库内 +3~5 条 |
| **每两周** | 1 h | 对"待验证"条目跑快筛（三问 + 打分卡 + 一票否决） | 3 个候选方向 |
| **每月** | 3 h | ① 深拆 1 个竞品（七层提问法）② **回测**上月预判 ③ 清理已死方向（写死因） | 拆解笔记 + 判断力校准 |
| **每季度** | 0.5 天 | **窗口扫描**：新 OS 能力 / 新模型能力 / 新 API 与政策 × 老痛点交集 | 「能力窗口型」候选 |

> **关键在"固定"**：把探索从依赖灵感改造成依赖排期。灵感不可靠，排期可靠。

### 5.2 演示：从「一个模糊词」到「一条可验证的需求」

以「文件重命名」为例，走一遍完整链路（**仅示范路径，不含真实数据**）：

| 步 | 渠道 | 动作 | 得到 |
|---|---|---|---|
| 1 | 商业重命名工具差评（App Store / 官网） | 抓 1–3 星，统计高频动词 | "不能批量""不能预览""正则难用" |
| 2 | V2EX / 知乎 / Reddit | 搜「批量重命名 求推荐 / is there a tool」 | 场景原话：谁在什么时刻要改几百个文件 |
| 3 | B 站 / YouTube | 搜「批量重命名 教程」 | 教程密度 → 工具缺口 |
| 4 | 闲鱼 / Fiverr | 搜「批量重命名 代做」 | 价格锚点（有人花钱找人改） |
| 5 | GitHub | `is:issue is:open sort:reactions-+1 rename` | 带票的功能需求清单 |
| 6 | 招聘 JD | 搜「档案管理 专员 岗位职责」 | 是否存在"批量改名"的重复动作 |
| 7 | 收敛 | 三问 + 打分卡 | 人群/频次/分发是否成立 |

### 5.3 采集纪律（三条铁律）

1. **每条信号必带「来源链接 + 采集日期」**，否则不入库。
2. **同一结论至少两条独立来源交叉验证**；冲突时把冲突本身记下来（冲突常指向口径差异）。
3. **采集时不判断、不归纳**——判断留给快筛阶段，避免早期偏好污染素材池。**只记原话，禁止改写**（用户的措辞本身就是落地页文案与搜索关键词）。

## 七、Windows 桌面工具方向：专属渠道与用法（★ 本文主体场景）

> 本章只补**通用清单里没有、或需要改写**的渠道。§一—§六 的通用渠道在 Windows 场景下同样有效，本章不重复。**不做 Windows 方向可整章跳过。**

### 7.1 为什么 Windows 需要单独一套渠道

不是"换个搜索词"那么简单，四点结构性差异：

| 差异 | 对采集的影响 |
|---|---|
| **用户社区分布完全不同** | Mac 用户集中在少数派 / 即刻 / Reddit；Windows 用户集中在**远景、卡饭、52pojie、IT之家、TenForums、Reddit r/Windows11** —— 不在这几个地方，就采不到中文 Windows 用户的真实话 |
| **"被系统内置"是第一死因** | 微软每半年一次大版本 + 持续的 PowerToys 更新，会免费吃掉一批小工具。**必须有专门的"窗口期雷达"渠道**（见 7.3③） |

| **官方自带一个免费需求池** | **微软 Feedback Hub** —— 这是 macOS / Web 都没有的对等物（Apple 的反馈系统不对公众开放投票） |

### 7.3 Windows 特有的三个渠道，具体怎么用

#### ① 微软 Feedback Hub = 官方免费需求池
- **入口**：`Win + F` 唤起，或搜索 "Feedback Hub"；网页版可浏览。先按**类别**筛（如「文件、文件夹和存储」「输入」「多任务」），再按 **upvote 排序**。
- **为什么值钱**：能排到前面的反馈 = 大量用户共同遇到的普遍痛点，且**微软自己已确认"这算个需求"**（因为它进了反馈系统）。等于一份**带官方背书的用户需求清单**。
- **怎么用**：读**高赞但长期未解决**的反馈 → 说明微软不做或做不好 → 这正是第三方工具的空间。**务必看状态标签**，区分"微软在做"与"微软不做"。

#### ② 52pojie 悬赏求助区 = 中文最强的「有人愿付钱」信号
- **入口**：吾爱破解论坛 → **悬赏求助**版块（按悬赏金额排序）。
- **为什么值钱**：这是中文 Windows 用户最集中的「**我出钱求一个工具 / 脚本**」场景。**悬赏金额就是价格锚点**，求助描述就是场景原话 —— 它同时满足「需求真实 + 有人愿付钱 + 价格明确」三条。
- **怎么用**：抓**反复出现的求工具类型**（同一需求被反复悬赏 = 真实缺口）；把悬赏金作为定价参考下限。**注意**：该区用户以极客为主，付费意愿与普通用户不同，**必须交叉验证**。

#### ③ Windows Insider + PowerToys = 窗口期雷达
- **入口**：Windows Insider Blog / Windows 更新历史页 / PowerToys 的 GitHub release 与 issue。
- **为什么值钱**：**Windows 桌面工具的第一死因不是竞争，是被系统内置。** 历史被吃掉的类别：截图、窗口管理（Snap）、录屏（Xbox Game Bar）、压缩（原生 zip）、剪贴板历史（`Win + V`）、批量重命名（PowerToys PowerRename）、取色、文件快速预览（PowerToys Peek）……
- **怎么用**：**任何 Windows 工具方向，投入验证之前先做这一步** —— 扫一遍最近 2 个 Insider 版本的新功能 + PowerToys 的 open issue，然后问一句：**"微软会不会在 12 个月内把它免费做掉？"** 会 → 换方向，或按「能力窗口型」机会加速做（窗口期必须快）。

### 7.4 Windows 版反向索引

| 我要找…（Windows 语境） | 主渠道（按优先级） | 具体动作 |

### C.2 缺口声明

- 本文**不含任何平台的用户量、活跃度、市场规模等外部量化数据**；「信噪比 / 成本」评级为**经验判断**，非实测统计，不得当作结论引用。
- 渠道的**入口路径与搜索语法会随平台生态变化**（尤其小红书、即刻、GitHub 搜索语法、App Store 评论排序 UI），**建议每 6 个月复核一次**。
- 本文列的渠道**不保证全部可用**：部分平台可能改版、下架、或对非注册用户设限；**使用前请先验证入口是否有效**。
- 本文与 `产品机会发现方法论.md` §6、`产品问题识别方法论.md` §3 在"信号源"上**存在有意为之的重叠**（本文从"渠道"视角切入，两文从"流程/判定"视角切入）。**若日后出现口径分歧，流程以 `产品机会发现方法论.md` 为准，判定尺度以 `产品问题识别方法论.md` 为准，渠道入口以本文为准。**
- **§七 的 Windows 渠道清单来自公开常识与经验，未逐一实测**（2026-10-13）。其中社区类渠道（远景 / 卡饭 / 52pojie / 异次元 / 果核剥壳）的**版块结构与活跃度变化最快**，使用前须自行验证版块是否仍存在、是否仍开放浏览。
- **§七 中「用户集中于某平台」的判断为经验归纳，无实测流量数据支撑**；不同品类（开发工具 vs 办公工具）的用户聚集地会明显不同，需按自己赛道复核。
- **§3.10 的「SDK 厂商 → 变现类型」归因表基于 2026-10 的 SDK 生态归纳**，厂商归属与聚合关系会变（收购 / 合并 / 更名），使用前须核对最新厂商关系。
- **SDK 披露页本身可能不完整或滞后**：因此"披露页里没有某类 SDK"**只能推出「未观测到」，不能推出「不存在」**；要下"没有广告 / 没有电商"的结论，必须有商店 SKU 或抓包作为第二证据（见 §3.10 三条纪律）。
- **§3.10 的实证案例来自单一项目（2026-10-15）**，其"官网宣称与 SDK 清单冲突"的比例**不代表行业普遍水平**。
