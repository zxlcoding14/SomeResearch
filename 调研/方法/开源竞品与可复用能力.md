# 开源竞品与可复用能力调研（PM 视角）

> **定位**：跨方向公共资产。不绑定 C 端或个人开发者任一方向——它是**每条产品方向上都要过的两道关**。
> **一句话**：开源对桌面工具的意义是双面的——**它既是头号杀死你的竞品，也是你把落地成本砍掉一半的现成底座**。这两个用途需要两套完全不同的动作，混为一谈会同时踩坑。
> **数据口径**：本文所有 Stars / Forks / License / 最后推送时间均为 **GitHub REST API 一手实测**，采集日 **2026-10-08**（研究报告规范中已有的赛道数据沿用其原采集日并逐条标注）。无一个数字来自二手文章或推算。
> **配套**：GitHub 采集细则见 `研究报告规范/SKILL.md`「开源项目调研专用」；本文承担**跨赛道的开源方法论与能力地图**。

## 〇、结论先行（TL;DR）

1. **开源维度的正确用法是「先判死、再省钱」，顺序不能反。** 先问「这条赛道被开源吃干净了吗」，答"是"就直接砍掉，不必进入后面的成本测算；答"否"再问「我能复用什么开源把成本压下来」。反过来先算复用、后判竞品，会做出一堆"成本很低但注定收不到钱"的方案。

2. **许可证是落地的第一道硬门，且它比技术难度更容易致命。** 本次实测的 29 个项目中，**5 个是 GPL / AGPL 系（传染性）**——ShareX（GPL-3.0）、Espanso（GPL-3.0）、Pandoc（GPL-2.0）、Cherry Studio（AGPL-3.0），加上 n8n 的 fair-code 限制。**代码级复用它们做闭源商业产品，等于把整个产品源代码送给用户。** 而 MIT / Apache-2.0 阵营（llama.cpp、PaddleOCR、pdf.js、pdfcpu、PowerToys、Tiptap、Monaco 等）可以安全闭源商用。

3. **【否定性结论】桌面工具赛道里，"能力"本身已经没有定价权了。** 本次实测证明了这件事的量级：截图有 ShareX（39,921★ / 免费 / 活跃）；OCR 有 Umi-OCR（47,653★）+ PaddleOCR（90,740★）；PDF 有 Stirling-PDF（93,746★）；去重有 czkawka（34,057★）；本地大模型有 Ollama（182,505★）+ llama.cpp（130,558★）。**凡是"单一能力型"产品，开源层都已备好且免费。** 能收费的位置只剩开源不做的那一段——**持续交付成本 + 责任承担 + 结构化交付**（与研究报告规范六条赛道结论同构，这是第七次验证）。

4. **对个人开发者，开源是本次最有价值的发现：桌面 AI mini-tool 的"最后一公里"已有全套 MIT / Apache 底座。** 壳（Tauri / Wails）、本地推理（llama.cpp / ONNX Runtime / whisper.cpp）、OCR（PaddleOCR / RapidOCR）、PDF（pdf.js / pdfcpu）、图像（libvips）、向量检索（sqlite-vec / LanceDB）、编辑器（Tiptap / Monaco）——**全部宽松许可、全部活跃**。这意味着**从零到能跑的原型，工期可以按"周"而不是"月"来算**，瓶颈从"写不出来"彻底转移到"卖给谁"。

5. **一个必须立即知道的实测发现（直接命中在研样本）**：**Windows 重命名已被免费覆盖。** `microsoft/PowerToys`（139,292★ / **MIT** / 活跃）自带 **PowerRename** 模块，批量正则重命名、预览、撤销齐全。任何以"批量重命名"为核心卖点的桌面工具（含 `renameai.online` 这类样本），在 Windows 上面对的不是竞品公司，而是**微软官方免费工具**——这条必须先过，再谈 AI 增强能不能救。

6. **开源项目本身也在做商业化，"开源"≠"可白嫖"。** Stirling-PDF 是 **open-core**（app/ 内含 proprietary 模块，NOASSERTION），n8n 是 **fair-code**（Sustainable Use License，禁止转售托管服务）。把它们当"免费竞品"来引用会得出错误结论（详见 §五）。

## 一、为什么开源维度必须进 PM 流程的三个理由

| 理由 | 说明 | 不做的后果 |
|---|---|---|
| **它是「免费替代」里最强的一档** | 产品分析框架原话：「永远把『免费替代』与『什么都不做』放进竞品格」。开源是免费替代里**功能最全、且持续演进**的一档——比系统内置还难打，因为系统内置受大厂战略左右，开源只受社区惯性左右。 | 把已被开源覆盖的赛道判成"有空间"，浪费整个立项周期 |
| **它直接决定成本结构** | 同一个功能，自研 vs 复用开源，工期差一个数量级。这不是估算问题——**组件是否存在、是否可商用、是否活跃**三件事都可一手核实。 | 成本模型里把"要自己写"当默认值，报价与工期全错 |
| **它的许可证能整体否决一个方案** | AGPL 组件进了一个 SaaS，法律后果是整条产品线开源。这种风险**必须在选型阶段排掉**，在编码后才发现等于重做。 | 产品做完才发现不能卖 |

> **一句话纪律**：**开源维度不是研究别人，是给自己排雷并找杠杆。** 它必须出现在 L1（是什么 / 替代谱系）和 L5（竞争位势），而不是当作附录。

## 二、两个用途，两套动作（先判死，再省钱）

### 2.1 防守：开源竞品雷达（5 分钟判定「这条赛道被吃干净了吗」）

**动作顺序固定，不可跳步：**

| 步 | 动作 | 输出 |
|---|---|---|
| ① | 用**功能名 + 平台**在 GitHub 搜一次（如 `duplicate file finder windows`），按 Stars 排序看前 10 | 候选清单 |
| ② | 对前 3 名拉一手数据：`https://api.github.com/repos/{owner}/{repo}`（详见 §七） | Stars / License / pushed_at |
| ③ | 过**三问**（见下表） | 覆盖度等级 L0–L4 |
| ④ | 按等级决定是否继续 | 继续 / 转向 / 砍掉 |

**开源覆盖度五级判定（本表为本次新增的收敛件）：**

| 等级 | 判据 | 对手形态 | 决策 |
|---|---|---|---|
| **L0 未被覆盖** | 搜不到 Star > 1k 的同功能项目，或只有 CLI 无 GUI | 无 | 可继续，进 §六 算复用账 |
| **L1 有库无产品** | 有成熟**库/引擎**（如 libvips、pdfcpu），但没有直接可用给终端用户的**成品** | 只给你省成本，不抢你用户 | ✅ **最佳位置**：复用它的库，去做它没做的产品层 |
| **L2 有桌面成品** | 有成熟开源 GUI 成品，但**不活跃**（`pushed_at` > 6 个月）或体验差、无中文 | 半死对手 | ⚠️ 可进场，但必须回答「为什么是现在、为什么是我」（接手空位） |
| **L3 有活跃成品** | 有 Star > 10k、**30 天内仍在提交**、功能覆盖与你要做的高度重叠的开源成品 | 活的免费对手 | 🔴 **必须转向**：只做它明确不做的那一段（结构化交付 / 责任 / 持续维护），否则别做 |
| **L4 被平台/官方覆盖** | 开源之外，还有 OS 内置或大厂官方免费工具做了同一件事 | 不可对抗 | ⛔ **直接砍**，不要再谈 AI 增强 |

> **实证校准（本次实测，仅作等级范例，不作行业结论）**：
> - **重复文件查找** → **L3**（czkawka 34,057★，2026-09-16 仍有提交）
> - **批量重命名（Windows）** → **L4**（PowerToys/PowerRename，139,292★、MIT、官方、活跃）
> - **截图** → **L4**（ShareX 39,921★ + 系统内置 + IM 内置，研究报告规范已三次验证）
> - **图像底层处理** → **L1**（libvips 11,711★ / LGPL-2.1、ImageMagick 17,614★，都是库，没有面向知识工作者的成品）
> - **本地大模型推理** → **L1**（llama.cpp / Ollama 是运行时，不是产品）

**⚠️ 雷达的三个必查陷阱（不查会误判）：**

| 陷阱 | 说明 | 正确做法 |
|---|---|---|
| 只看 Stars 不看 `pushed_at` | 高 Star + 停更 = 空位，不是威胁 | **两者一起看**。停更 > 6 个月 = 可接手信号（如 Umi-OCR 47,653★ 但已停更 10.6 个月） |
| 把 "NOASSERTION" 当"无许可证" | 多许可证 / open-core / 自定义许可都会落到 NOASSERTION | **逐组件查**（见 §四） |
| 把开源项目当"零收入 = 零威胁" | 开源能把价格打到 0，本身就是最强竞争 | 威胁评估看**它在用户手里能不能免费解决问题**，不看它赚不赚钱 |

### 2.2 进攻：可复用能力地图（落地提速）

**这张表的用法**：定了方向之后，照着能力域一栏一栏问「这一块我能不能直接用现成的」。**每命中一个 MIT / Apache 组件，就从你的工期里划掉一段。**

### 3.1 桌面应用壳（决定交付形态与包体）

| 项目 | Stars | Forks | License | 最后推送 | 状态 | 落地用法 |
|---|---|---|---|---|---|---|
| **tauri-apps/tauri** | 111,644 | 4,044 | Apache-2.0 | 2026-10-07 | 🟢 | Rust 内核 + Web 前端，**包体显著小于 Electron**；适合"轻量、隐私、本地处理"类工具 |

**PM 判读**：三者都是**宽松许可、可闭源商用**。选型不是技术问题而是**取舍问题**——Tauri 省包体、Electron 省时间、Wails 省迁移成本。**对个人开发者，"最快能跑起来"比"最优架构"重要**，Electron 的成熟生态通常是对的默认值；若产品卖点是"小而快/隐私本地"，Tauri 的包体优势直接构成卖点。

### 3.2 本地 AI 推理与模型运行时（决定"能不能离线 + 能不能不烧钱"）

|---|---|---|---|---|---|---|
| **ollama/ollama** | 182,505 | 18,145 | MIT | 2026-10-08 | 🟢 | 本地模型一键跑起来，**适合原型期与"本地方案"演示**；直接暴露 HTTP API，好集成 |
| **ggml-org/llama.cpp** | 130,558 | 24,153 | MIT | 2026-10-07 | 🟢 | 纯 C/C++ 推理内核，**可嵌进你的安装包**，无需用户另装运行时 |
| **ggml-org/whisper.cpp** | 54,210 | 6,209 | MIT | 2026-10-06 | 🟢 | 本地语音转写（会议记录 / 语音笔记类工具的核心能力） |
| **microsoft/onnxruntime** | 22,033 | 4,284 | MIT | 2026-10-08 | 🟢 | 通用模型运行时，**OCR / 分类 / 嵌入等中小模型的标准载体**；跨平台一致性最好 |

**PM 判读**：
- **这四个是"边际成本红线"的解药。** 研究报告规范已反复验证「AI 类方向的最大死因是推理边际成本 ≥ 定价」。本地推理把边际成本压到 **≈ 0**（用户承担算力），代价是精度下降与包体变大——研究报告规范已记录用户原声「**只要模型转为本地，识别能力就会大大下降**」，这是**必须提前告知用户的取舍，不是可以藏起来的缺点**。
- Ollama 与 llama.cpp 的分工：**原型期用 Ollama（快），交付期用 llama.cpp（可内嵌）**。

### 3.3 OCR / 文档理解（用户已重点研究的赛道）

| 项目 | Stars | Forks | License | 最后推送 | 状态 | 落地用法 |
|---|---|---|---|---|---|---|
| **PaddlePaddle/PaddleOCR** | 90,740 | 11,451 | Apache-2.0 | 2026-09-16 | 🟢 | 中文 OCR 事实标准；**仓库描述已于近期转向「把 PDF/图像变成给 LLM 用的结构化数据」**，含 PP-Structure / pdf2markdown 方向 |
| **tesseract-ocr/tesseract** | 76,842 | 10,823 | Apache-2.0 | 2026-09-28 | 🟢 | 老牌引擎，多语种覆盖广、体积可控；精度已被 Paddle 系超越 |
| **hiroi-sora/Umi-OCR** | 47,653 | 4,658 | MIT | **2025-11-20** | 🟡 **停更 10.6 个月** | 离线 OCR 桌面成品；**高 Star + 停更 = 可接手的空位**（研究报告规范已验证的规律） |
| **RapidAI/RapidOCR** | 8,051 | 739 | Apache-2.0 | 2026-10-07 | 🟢 | 把 Paddle 模型转 ONNX/OpenVINO/MNN 的**轻量部署套件**，是"把 OCR 塞进桌面客户端"最省事的路径 |

**PM 判读**：
- **能力层已彻底商品化。** PaddleOCR 的开源精度已被研究报告规范记录为**反超商业云**（PaddleOCR-VL 94.5 / GLM-OCR 94.62 vs GPT-5 ≈85.8 的口径）。**"识别更准"不再是可以收费的卖点**。
- **真正可复用的"高价值组合"是**：`RapidOCR（轻量部署）+ 你自己的结构化输出层`。开源给的是**文字**，用户要的是**可直接用的结果**（表格还原、公式 LaTeX、版面顺序、竖排日文），**这一层开源全部没做**——研究报告规范已独立验证同一结论。

## 四、许可证合规矩阵（落地的第一道硬门）

### 4.1 四档分级（先看这一张）

| 档 | 许可证 | 能否闭源商用 | 义务 | 本次实测命中 |
|---|---|---|---|---|
| **A 安全** | MIT、Apache-2.0、BSD | ✅ 可以 | 保留版权与许可声明 | Tauri、Electron、Wails、llama.cpp、Ollama、whisper.cpp、ONNX Runtime、PaddleOCR、Tesseract、RapidOCR、Umi-OCR、pdf.js、pdfcpu、PowerToys、Chroma、LanceDB、sqlite-vec、Tiptap、Monaco |
| **B 可用需注意** | MPL-2.0（文件级）、LGPL（库级）、EPL | ✅ 通常可以 | **修改过的那些文件** / 库本身需开源；静态链接需评估 | OCRmyPDF（MPL-2.0）、libvips（LGPL-2.1） |
| **C 高风险** | **GPL-2.0 / GPL-3.0** | ⚠️ 通常不可以（链接即传染） | 整个衍生作品需以 GPL 开源 | **Pandoc（GPL-2.0）**、**ShareX（GPL-3.0）**、**Espanso（GPL-3.0）** |
| **D 禁用级** | **AGPL-3.0** | ❌ 不可以 | **网络服务也触发**开源义务 | **Cherry Studio（AGPL-3.0）**；另有研究报告规范已记录的 **PyMuPDF / MuPDF（AGPL-3.0）** |
| **? 待核实** | NOASSERTION / open-core / fair-code | 视具体条款 | 逐组件查 | **Stirling-PDF（open-core）**、**n8n（fair-code）**、ImageMagick（自有许可）、czkawka（仓库 NOASSERTION，核心 crates 实测 MIT） |

### 4.2 三条铁律

1. **AGPL 是唯一"碰到了就必须重做"的许可证。** 它连"通过网络提供服务"都算分发。**任何要上 SaaS 的产品，选型阶段第一件事就是把 AGPL 组件挑出来。**
2. **"用命令行调用" 与 "链接进代码" 是两种法律事实。** Pandoc（GPL）之所以还能出现在桌面工具里，是因为它可以作为**独立可执行程序被调用**（聚合而非衍生）。**这条边界必须让法务确认，不能自行推定。**
3. **NOASSERTION ≠ 无许可证。** 多许可证、open-core、自定义许可都会落到这个值。**必须逐个组件查**——项目主页 LICENSE、`package.json` / `Cargo.toml` / `crates.io` 的 `license` 字段往往比仓库根 LICENSE 文件更准（研究报告规范已验证此路径）。

### 4.3 open-core 与 fair-code：新的中间态（必须单独识别）

| 形态 | 代表 | 特征 | 对你的含义 |
|---|---|---|---|
| **open-core** | **Stirling-PDF**（93,746★） | 核心开源 + **部分模块 proprietary**（实测 app/ 内含 common/core/proprietary/saas 四模块）；官方同时卖 SaaS（stirling.com） | **不能把整个项目当免费竞品**——它在功能完整度上是竞品，在成本上是零；但你**也不能整体复用**，只能挑开源部分的组件 |
| **fair-code** | **n8n**（206,843★） | Sustainable Use License：允许自用与内部业务，**禁止未经许可把产品本身作为托管服务转售** | 想在产品里嵌入 n8n 并对外收费，**必须先核实条款**，不能默认可行 |

> **这条是本次最容易被忽略、但后果最重的发现**：这两个项目 Stars 极高，如果只按"Star 高 + 开源 = 免费竞品"来判断，会同时犯两个错——**低估竞争（它功能很全）**、**高估可复用性（你不能整体用）**。

## 六、用开源降低落地成本：可复算的量化方法

### 6.1 自建 vs 复用：四栏对照（每个能力域填一遍）

| 栏 | 填什么 | 例（OCR 能力） |
|---|---|---|
| **① 复用方案** | 用哪个开源、什么许可 | RapidOCR（Apache-2.0） |
| **② 复用成本** | 集成工时 + 模型/包体代价 + 学习成本 | 集成 3–5 人日；包体 +XX MB（需实测） |
| **③ 自建成本** | 从零实现所需工时 + 数据/训练成本 | 训练一个可比的 OCR 引擎：**不可行**（需标注团队与算力） |
| **④ 差额与风险** | 省下多少 + 许可/维护风险 | 省下的不是"工时"，是**"这条路根本走不通"**——这栏常被低估 |

> **这一栏的用法**：**当 ③ 栏填"不可行"时，说明这个能力域不构成你的护城河，只能复用**。反过来，如果某个能力域你**只能自建**（开源没有），那才可能是差异化所在——**但必须先用 §2.1 的雷达确认它不是"被覆盖了"**。

### 6.2 三个可复算的算式

**算式 1 · 工期压缩比**
```
工期压缩比 = 自建工时 / (集成开源工时 + 联调工时)
```
> 纪律：分子分母都必须给出**假设 → 依据 → 推算 → 结果**四段，并标置信度。不允许写"大约省一半"。（预估规范见 `产品分析框架/SKILL.md` §4.5/§4.6）

**算式 2 · 许可风险敞口（一票否决用）**
```
若产品含 AGPL 组件 且 产品对外提供网络服务 → 风险 = 不可承受（整线开源）
```
> 这不是打分项，是**否决项**。命即停。

**算式 3 · 开源替代后的边际成本**
```
复用本地开源推理后：边际成本/次 ≈ 0（用户承担算力）
对照 云端 API：边际成本/次 = 单次 token 成本 × 调用次数
```
> **这是"本地化"唯一的商业理由**：它把 AI 产品的边际成本从"随用量上升"变成"固定"。研究报告规范的「边际成本红线」一节说的就是这件事——**本地开源是唯一能让 AI 工具挂得起年费的技术路径**。

### 6.3 复用开源时必须同时计入的三项隐性成本（不许漏）

| 隐性成本 | 说明 | 不计的后果 |
|---|---|---|
| **维护跟随成本** | 上游更新、破坏性变更、安全补丁要跟 | 半年后版本锁死，无法升级 |
| **包体 / 性能代价** | 每个组件都加体积；Tauri 之所以被选就是为省这个 | 产品卖点"小而快"被自己吃掉 |
| **许可与供应链合规** | 逐组件许可核查 + 供应链风险（上游停更/被投毒） | 法律风险 + 交付风险 |

### 7.2 GitHub 数据采集三禁令（继承 `研究报告规范/SKILL.md`，此处仅摘要，细则以该文件为准）

1. **禁止直接比较不同版本的累计下载量**——Release `download_count` 是自发布起累计，**必须 ÷ 在架天数**得到"日均下载"才可比。
2. **禁止把仓库 `language` 字段当技术栈**——本地化文件多时会被误判（czkawka 实测被识别为 `Fluent`）。
3. **禁止把 `NOASSERTION` 当"无许可证"**——必须逐组件查。

**两条替代通路**（GitHub 匿名配额 60 次/小时且全 IP 共享，极易耗尽）：
- **WebFetch 走独立出口**：`https://api.github.com/repos/{owner}/{repo}` —— 不受本地 IP 限流影响。**这是本次 29 个项目全部采集所用的方法**（⚠️ 单版本 release 对象可能极大导致截断，查 release 请用 `/releases/tags/{tag}`）。
- **第三方无鉴权 API**：`flathub.org/api/v2/stats/{app_id}`（Linux 真实装机量）、`crates.io/api/v1/crates/{name}`（库的真实嵌入量 + license）、`api.npmjs.org/downloads/point/last-month/{pkg}`（npm 下载量）、`community.chocolatey.org`（Windows 包下载量）。

### 7.3 反模式（本次实测暴露的高发错误）

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| **只搜中文关键词** | 会漏掉海外主流项目（如 libvips、pdfcpu 在中文圈几乎无讨论） | 中英各搜一遍 |
| **按 Stars 排序就下结论** | 高 Star 可能是停更的墓志铭，也可能是 open-core 的营销资产 | Star + `pushed_at` + License 三者一起看 |
| **把开源当"不存在"** | 最常见的错误：做出来才发现免费替代早就有 | **每个方向第一步就跑雷达** |
| **把开源当"全免费"** | 忽略 open-core / fair-code / GPL 传染 | 逐个过 §4.1 |
| **复用后不记录版本与许可** | 半年后无法升级、无法举证合规 | 交付前建**开源依赖清单**（组件 / 版本 / 许可 / 用途） |
