## 〇、结论先行（TL;DR）

1. **目录里只有两类东西**：① **公共底座**（6 份 .md，方法论的原始载体，**不会被自动加载**，是给人读、给 skill 引用的）② **skill 运行时单元**（4 个文件夹，**会被 WorkBuddy 自动加载并执行**）。
2. **4 个文件夹才是「活的」** —— 每个文件夹里的 `SKILL.md` 通过 Windows 目录链接（junction）挂在 `~/.workbuddy/skills\` 下，你说话时模型会自动读它、按它执行。根层那 6 份大文档**不会**被自动读。
3. **一份内容只有一个真身。** 全盘没有第二份副本：skill 本体与它的权威详版**同目录**存放，`~/.workbuddy/skills\` 下那 4 个目录只是链接。
4. **`研究报告规范` 与其他三个不是一类。** 前三个（产品分析框架 / C端方向方法论 / 个人开发者方法论）回答「**怎么想**」，研究报告规范回答「**产出什么形态 + 已沉淀的赛道基准数据**」。
5. **⚠️ 唯一的不可逆风险**：用 `rm -rf` 删 `~/.workbuddy/skills\` 下的链接，会**穿透链接删掉本目录的真实文件**。删链接只能用 `rmdir`。
6. **不能「不建文件夹、只保留文件」**：skill 加载约定要求「目录 + `SKILL.md`」，而本机唯一稳定可用的链接形式是**只能指向目录**的 junction。把内容平铺成文件 = 放弃这 4 个 skill 的自动加载。详见 §六。

## 二、公共底座：6 份根层文档（人读，不自动加载）

这 6 份是**方法的原始载体**。它们的作用有三：① 给人从头读一遍建立认知 ② 给 skill 当权威引用源（skill 只承载关键路径，长尾细则指回这里）③ 是内容资产的本体。

### 2.1 `产品机会发现方法论.md`（609 行）

**干什么**：回答「**怎么从一个想法都没有，到一个能做的方向**」。这是**探索侧**的完整方法。

**核心内容**：PM 三种真实工作模式 → 日常 routine 与判断力训练 → 探索无效的根因诊断 → **五段式探索流水线**（定约束 → 采信号 → 快筛 → 证伪 → 立项）→ 8 类信号源 → 4 种机会原型 → **机会库（Opportunity Backlog）长机制** → 反模式清单 → 四周探索日历。

**什么时候翻它**：手上没有具体标的、想找新方向；或者想搞明白「有经验的 PM 每天到底在干什么才有那种判断力」。

**关键判断**：① 方向不是「想」出来的，是「筛」出来的——探索能力体现在**淘汰效率**，不体现在灵感多。② **顺序反着来：先写死约束，再找方向**。约束是最锋利的筛子。③ 主判定式：`方向价值 ≈ 使用频次 × 痛点硬度 × 现有替代的糟糕度 × 分发可得性`。

### 2.3 `产品盈利可行性问题域.md`（616 行）

**干什么**：补上通用框架**最大的一个洞**——「这东西好不好」≠「我靠它能不能养活自己」。

**核心内容**：覆盖边界与缺口图 → **22 个必答提问域（6 大模块）** → **C 端 12 维分析框架** → **B 端 12 维分析框架** → C×B 对比矩阵 → 个人开发者专项 → 接进现有流水线的 SOP 补丁 → 盈利模型 / 路线判定 / 退出条件。

**关键判断**：① 四层现实约束——**钱怎么进来 / 钱怎么花出去 / 人怎么进来 / 出了事怎么办**。② C 端与 B 端判据不能通用：**C 端卖「省时间/爽」，B 端卖「不出事/可交代」**；C 端瓶颈在分发，B 端瓶颈在决策链与销售人力。③ 个人开发者的正确起点是「收钱路径明确 + 边际成本可控 + 分发渠道我自己就泡在里面」的**三重交集**。

**这份在三处都有反映**：它后来被拆成了两个方向切片（`C端方向方法论\` 与 `个人开发者方法论\`），是那两个文件夹的**共同上游**。**注意**：这里有一个已记录的口径问题——C 端 skill 用的是「盈利可行性 11 问」，个人开发者 skill 用的是「12 问」，而本文是 22 域。**三处编号体系不同是设计，不是笔误**（11 问是 C 端专用的收敛版）。

**干什么**：**跨方向的公共资产**——开源这件事在每条产品方向上都是**必须过的两道关**。数据全部为 **GitHub REST API 一手实测，采集日 2026-10-08**，29 个项目。

**核心内容**：为什么要进 PM 流程 → **两个用途两套动作（先判死，再省钱）** → 可复用能力地图（29 项目按能力域分组）→ **许可证合规矩阵** → 已研究赛道的开源覆盖度实测 → 用开源降低落地成本的量化方法 → 开源调研 SOP → 按场景速查表。

**关键判断（四条硬结论）**：

| # | 结论 |
|---|---|
| ① | **顺序固定：先判死，再省钱。** 先问「这条赛道被开源吃干净了吗」，答"是"直接砍；反了会做出一堆"成本极低但收不到钱"的方案 |

### 2.5 `产品问题识别方法论.md`（681 行，2026-10-10 新增）

**干什么**：补上此前**完全缺失的一层**——「什么算痛点、什么算痒点、优化点、机会点，怎么判、从哪采、怎么变成需求」。原有 4 份底座对「痛点/痒点/爽点」**只有一张三行表**，且**「优化点」这一整类不存在**；这份文档把它展开成一套可操作的判定体系。

**核心内容**：**五类问题分类学**（痛点/痒点/爽点/**优化点**/**机会点**）→ **不适感轴模型**（唯一硬判据 = 「不做会损失什么」）→ **四把判定尺子**（损失性质 / P0–P5 六级强度刻度 / 频次×人群 / 现有替代糟糕度）→ **九维打分卡（满分 95）** → **五大采集面 × 20 个具体动作**（自己摩擦 / 差评求助 / 手工痕迹 / 已付费不满 / 结构窗口）→ **追问话术卡**（只问过去不问未来）→ **问题卡字段** → **三关→两关转化链路**（点→需求→方向）→ **六把换维度刀**（方向→新场景）→ SOP 7 步。

**什么时候翻它**：手上有零散用户抱怨不知怎么定级；想系统"采问题"而不是等灵感；想把"痛点分析"从形容词变成能打分的动作；想找下一代场景或新切入点。

**关键判断（五条）**：

| # | 结论 |
|---|---|
| ① | **唯一硬判据是「不做会损失什么」，不是「用户说喜不喜欢」。** 痛点句式含"不得不"，痒点/爽点通常是虚拟语气 |
| ② | **只有痛点能直接收钱**；痒点负责拉新留存、爽点是放大器、优化点基本不能独立收费 |
| ③ | **识别靠行为证据**：已付钱 > 已花时间手工做 > 已在找替代 > 嘴上抱怨（"你会用吗"= 0 信息量） |
| ④ | **类型会迁移**：同一个问题换人群/换时刻/换技术阶段会改变类别——"优化点在 C 端是痒点，在 B 端是痛点" |
| ⑤ | **新场景不是想出来的，是换维度重扫出来的**：换人群 / 时刻 / 载体 / 约束 / 能力 / 交付，六把刀 |

**与既有文档的边界**：本文管**「值不值得做」的判定尺度**，`产品机会发现方法论.md` 管**「怎么筛怎么验」的流转流程**（五段式流水线 / 4 原型 / 证伪实验），两者在采集与证伪处**存在有意为之的重叠**（视角不同：问题判定 vs 方向筛选）；口径分歧时以本文定尺度、以机会发现方法论的流程为准。转化链路的**下游**是 `产品盈利可行性问题域.md`（做得起做不起）。

### 2.6 `产品用户视角问题域.md`（391 行，2026-10-10 新增）

**干什么**：回答 PM 最常被问、也最常被糊弄过去的那个问题——「**从用户角度考虑**」到底是考虑哪几个方面。它把此前**散落**在 `产品分析框架` L2、`C端方向方法论` L2、`产品盈利可行性问题域` 里的用户相关维度，聚合成一套**可逐格打勾的视角坐标系**。原先没有任何一处文档回答"完整的用户视角要覆盖哪些坐标"。

**核心内容**：四种伪视角（替用户想 / 问用户要 / 用自己代替用户 / **用数据代替用户**）与三角验证（原话 × 行为 × 数据，冲突以行为为准）→ **五角色模型**（使用者 / 付费者 / 决策者 / 影响者 / 阻挠者，含 C 端角色折叠 vs B 端角色分离对照、角色冲突矩阵）→ **12 维视角坐标系**（每维含「必答问题 / 典型错误答案 / 取证路径」三件套）→ **四个视角转换动作**（用户的一天 / 第一次 / 第 100 次 / 放弃者）→ **三种用法**（找需求 / 做设计 / 做决策）→ **用户视角的七条边界**（什么时候不该听用户的）→ 12 维 × 4 问检查表 + 五角色问法对照表。

**12 个维度**：① 身份与角色 ② 场景与时刻 ③ 目标任务 ④ 现有替代 ⑤ 认知与心智 ⑥ 成本结构 ⑦ 情绪与身份感 ⑧ 决策与预算 ⑨ 信息环境与信任 ⑩ 约束条件 ⑪ 生命周期阶段 ⑫ 边缘与例外。

**什么时候翻它**：评审时被问"你有没有从用户角度想"但答不具体；做访谈前不知道要问哪些方面；想有一套能打勾的清单而不是靠"同理心"；设计阶段自查界面的用户合理性。

**关键判断（六条）**：

| # | 结论 |
|---|---|
| ① | **「从用户角度考虑」不是态度，是可检查的坐标清单**——态度无法验证，坐标可以逐格打勾 |
| ② | **用户至少是五个角色**，且常常不是同一个人（B 端必然分离，C 端也常分离）。**只说"用户"等于没说** |
| ③ | **12 维缺一维，视角就只是一个侧面**；每维都有"典型错误答案"（"所有办公族"/"随时会用"/"更方便"= 这维没做） |
| ④ | **三角验证，冲突以行为为准**：原话解释、数据定位、行为裁决 |
| ⑤ | **第一次与第 100 次的诉求方向相反**——新手要引导、熟手要加速，解法是分层不是折中 |
| ⑥ | **用户视角用于"发现问题"，不用于"决定做什么"**——用户是问题的权威，不是解法的权威 |

**与既有文档的边界**：本文提供**视角坐标系**（看的位置），`产品问题识别方法论.md` 提供**判定尺度**（看到的东西算什么、算多重）。`产品分析框架` L2「给谁用、什么时候用」的一句话提纲（用户分层 / JTBD / 频次 / 替代谱系 / 切换成本）在本文展开为 12 维完整版——**L2 只保留提纲，细则指向本文**，避免两边各写一套。

## 三、skill 运行时单元：4 个文件夹（会被自动加载）

**这是这个目录跟普通资料库最不一样的地方。** 每个文件夹里的 `SKILL.md` 是 WorkBuddy 的 skill 定义文件（带 YAML frontmatter，含 `name` / `description` / `agent_created: true`），模型会在匹配到场景时**自动读取并按其执行**。

### 3.1 `产品分析框架\` → skill 名 `product-analysis-framework`

**一句话**：回答「**分析任何产品该问什么、看哪些面、按什么顺序**」的元方法。不限品类，**不内置任何产品数据**（避免过期与虚构），**不产出具体报告**。

| 文件 | 大小 | 作用 |
|---|---|---|
| `SKILL.md` | 33 KB | 决策主干：七条核心原则 + 10 问快扫（15 分钟）+ **七层提问法（L0–L7）** + 数据获取与测算方法论 + 常见误判 + 产出模板 + **执行流程 SOP（7 步）** + 环境注意 |
| `references\产品分析框架-提问手册.md` | 33 KB | 长尾细则：每层判定工具箱、追问话术、取证路径、填写示范。SKILL 里指过来（也可经 `~/.workbuddy/skills/product-analysis-framework/references/...` 访问，同一份文件） |

**七层提问法（L0–L7，实际 8 层）**：

| 层 | 问什么 |
|---|---|
| L0 | 口径与边界——**不写这层，后面全是废话** |
| L1 | 是什么（What）：一句话定义 / 品类 / 内核 / Non-scope |
| L2 | 给谁用、什么时候用（Who & When）：用户分层 / JTBD / 频次 / 替代谱系 / 切换成本 |
| L3 | 为什么成立（Why）：痛痒爽 / 卖点对撞 / 需求强度 / 天花板 |
| L4 | 怎么赚钱（How Money）：收费对象 / 计费 / 墙型 / 续费理由 / ARPU / 漏斗 |
| L5 | 竞争位势（Where）：四层竞争 / 对比矩阵 / 差异层级 / 竞品盲区 / 系统威胁 / 开源覆盖度 |
| L6 | 能不能持续（Sustainability）：护城河 + 时间窗 / 团队 / 平台与技术风险 / 生命周期 |
| L7 | So What：抄什么 / 别做什么 / 从哪进场 / 最小验证 |

**七条核心原则**：① 先问口径再问结论（不知计数口径，任何数字都不可比）② **价值不由功能数量决定**——功能是成本，不是价值 ③ **永远把「免费替代」与「什么都不做」放进竞品格**（最强的一档免费替代是开源）④ 频次决定商业模式（低频收不了订阅）⑤ 看趋势不看快照（必须回答「它会被什么吃掉」）⑥ 结论必须可执行 ⑦ **拿不到数据就推算，不许绕开**——禁的是无依据的数字，不是估算本身。

**执行流程 SOP（7 步，这是它最实操的一节）**：

| 步 | 动作 | 要点 |
|---|---|---|
| 1 | 定目的与口径 | 先写 L0，30 秒完成 |
| 2 | **跑开源雷达**（被特意提前到第 2 步） | 5 分钟跑覆盖度五级判定；**命中 L4（被 OS / 官方免费覆盖）直接停手**，不必进入测算。**整个流程里性价比最高的一步** |
| 3 | 采数与测算 | 一手优先：API 实测 > 官网/定价页 > 商店榜单 > 用户评论 > 二手报道；每个数字标「源级别 + 采集日 + 链接」。**缺失数据不许跳过**——这条最容易被执行成偷懒 |
| 4 | 七层扫描填表 | 每层必须有判定性指标；只有描述就是没做，退回补数。**L1 / L2 / L5 三层必须带开源结论** |
| 5 | 交叉验证 + 反方证据 | 每条关键结论至少 2 条独立来源，并**主动**去找差评 / 竞品对照，单列 |
| 6 | 收敛 | 先写 TL;DR，再倒推章节（结论先行） |
| 7 | 落盘 | `.md` 格式，**默认动作、不必等他开口**；方法论 → `调研\方法`，工具/竞品 → `调研\工具`，小众单品 → `调研\小众`，论坛帖 → `调研\小众软件` |

**两套判定工具不要混用**（SKILL 里专门提醒过这条）：

| 场景 | 用哪套 |
|---|---|
| **找方向**（多候选横向筛选） | 三问快筛（判需求真伪）+ 九维打分卡（定优先级）+ 一票否决（砍掉不可做的） |
| **看单标的**（纵深判断） | **八把尺子** |

> 两者重叠的维度（需求硬度、机会象限）**是同一判断的快版与慢版，同一场景不要混用**。

**它会按顺序调谁**：本框架（问什么）→ **开源公共文档**（先判死再省钱）→ **方向 skill**（C端 / 个人开发者，这一刀怎么切、什么时候直接杀）→ **研究报告规范**（报告模板 + 基准数据）。四者叠加，不重复造轮子。

**原型 → 验证的映射**（拿到机会原型后怎么验）：

| 原型 | 验证方式 |
|---|---|
| ① 替代升级型 | 直接测付费 |
| ② 手工自动化型 | 测复用率 |
| ③ 能力窗口型 | 只能测速度（窗口期短） |
| ④ 细分人群型 | 测人群规模与付费力 |

**它的环境注意里存着一条有用的修复**：Windows 本机 Bash 报 `ls` / `dirname: command not found`（退出码 127）时，**根因不是 coreutils 缺失，而是 WorkBuddy 的 shell 初始化 shim 清空了 `PATH`**。命令前加 `export PATH="/usr/bin:/bin:$PATH";` 即可恢复——**实测有效，且能处理中文路径**。退路是 Python `pathlib` / `shutil`。

### 3.3 `个人开发者方法论\` → skill 名 `solo-dev-pm-methodology`

| 文件 | 作用 |
|---|---|
| `SKILL.md`（29 KB） | **约束模型 + 执行流程**：六条先验 + 四个「结构性做不到」+ 执行 SOP + **四道闸门顺序否决** + **退出机制** + 12 维打分卡 + 盈利可行性 12 问 + 形态选择 + **合规底线 13 条** + 三重交集收敛 + 输出模板 |
| `个人开发者方向-PM方法论集成.md`（46 KB / 635 行） | 权威详版（自包含）。需要通道费率表、合规逐条追问、原型→验证映射时读它（§3.1 / §5 / §10.3） |

**定位**：与 `C端方向方法论\` 是**同一批源文档的另一条切线**。判断「这个方向是不是 C 端能做的」用 C端 skill；判断「**我一个人做不做得动**」用这个。**两者可叠加**。

**核心判据**：

- **个人开发者不是「小号的公司」**——公司的约束是**资源**，个人的约束是**时间、资质、承受力**。用公司标准评估一个人的生意，会永远选到「市场最大」而不是「我这条命能跑通」的方向。
- **四道闸门，顺序否决，不可跳**：**① 收得到钱 → ② 扛得住成本 → ③ 送得到人 → ④ 算得过账**。前两道不过，后面分析全部作废。
- **时间预算决定「每年只能认真做一件事」**：在职副业每周 8–15 小时，其中 **30%–50% 被上线后的维护/客服/运营吃掉**。
- **不可能三角**：高频迭代 / 深度销售 / 大规模投放，同时只能占两角。个人最优解 = **高频迭代 + 社区分发（放弃投放）**。
- **头号杀手不是竞品，是客服**：200 个付费用户每人每月问一次 ≈ 每工作日 10 次支持请求 = 一个人的全部业余时间。

### 3.4 `研究报告规范\` → skill 名 `product-research-report`

**一句话**：这份与另外三个**类别不同**。前三者回答「怎么想 / 按什么顺序判 / 什么时候杀」，这份回答「**产出什么形态的报告**」+「**这个赛道已测过哪些数、可直接复用**」。

| 文件 | 大小 | 作用 |
|---|---|---|
| `SKILL.md` | **173 KB**（单文件，无配套） | 三合一：报告工作流 + 报告模板 + **已沉淀的赛道基准数据仓库**。体量最大的一个 |

**为什么它这么大**：它不是一份轻量 skill 定义，而是**一份带执行流程的历史数据仓库**。内容可分五类：

| 类别 | 内容 |
|---|---|
| **数据采集 SOP** | GitHub API（`stargazers_count` / `forks_count` / `pushed_at` / `license`…）/ Releases API 下载量求和 / Discourse `.json`。**关键坑：论坛帖楼层正文只有 JSON 版完整**——逐页 WebFetch `/topic/{id}/{floor}` 会被前端按需渲染吞掉正文 |
| **赛道基准数据** | 系统工具（数据恢复 / 分区扩容 / 磁盘清理）、备份×克隆、万兴科技专项、重复文件查找、Mac 清理、PDF/版式文档、截图/屏幕捕捉、扫描 OCR App、C 端桌面 OCR、CrystalDiskInfo —— **均标注 2026-09 实测**，含公司层财务锚点 |
| **专用分析方法** | 单产品「功能点全景分析」法 / 护城河「时间窗」判断法 / 付费墙位置三类 + 商业模式识别 / 单品收入还原法 / 水印双引擎模型 / 口径歧义破解法 / 「能力市场」五层切分 + 商品化塌方检测 / 「免费单品工具」四通道变现解剖法 |
| **量化与开源** | 量化对比框架（营收 / 规模 / 活跃 / ROI，含 ARPU 断层与人均产出两个派生指标）/ ROI 三情景 / 下载÷Star 比 / GitHub 采集三条禁令 + 两条替代通路 |
| **落盘规范** | **格式铁律：一律 `.md`，不产 docx / pdf / xlsx / html**；内联可视化只是阅读辅助，其数据必须同步写进 md，不允许「只在对话里、不在文档里」的结论。目录分流与文件命名规则也在这里定义 |

**硬性要求（你的偏好，已固化进去）**：① 结论先行（开篇 TL;DR 3–5 条编号判断）② **漏斗形分层** ③ **必须含真实数据**，数据不足标口径 ④ **表格化**，避免长段落 ⑤ 文末附「数据来源与口径说明」表。

**它最值钱的两个派生指标**（用于商业化对比）：

- **ARPU 断层**——同赛道 ARPU 差异由「付费理由强度 × 计费结构 × 人群净值 × 计价货币」四项决定，**不由功能数量决定**。实证：Raycast ≈¥75 vs uTools ≈¥2.1（36 倍），后者用户多 10 倍但营收更低
- **下载 ÷ Star 比**——`包月下载量 ÷ GitHub Stars`。>5,000 = 真·基础设施；50–5,000 = 正常组件；**<50 = 高星但极少被真正集成**（低比值 ≠ 差代码，而是「未被大厂占位的机会区」）

**一条它敢直接给的反直觉结论**：**独立 mini-tool 的期望 ROI 常低于 1**，除非拿到规模、走 B 端或出海——这个负结论本身往往是最有价值的输出。

## 六、能不能「不建文件夹、只保留文件」？（2026-10-08 评估）

**结论：分两层看，不能两全。**

| 诉求 | 可行性 | 依据 |
|---|---|---|
| `调研\方法\` 下把这些内容平铺成 `.md` 文件 | ✅ **可以**，零技术障碍 | 就是普通文件读写 |
| 平铺之后，4 个 skill **仍能被 WorkBuddy 自动加载** | ❌ **不行** | 加载约定是 `~/.workbuddy/skills\{skill名}\SKILL.md` —— **必须是「目录 + 约定文件名」** |

也就是说：**「只保留文件」= 主动放弃这 4 个 skill 的自动加载能力**，它们退化为需要手动点名的普通文档。

### 6.1 为什么文件夹是硬性的

skill 能被自动加载，靠的是三条链上每一环都成立：

```
~/.workbuddy\skills\product-analysis-framework\     ← ① 必须是一个「目录」
        │  内容只有一个 SKILL.md                       ← ② 文件名必须是 SKILL.md
        ▼
（junction 目录链接）                                   ← ③ 本机唯一可用的链接形式
        ▼
调研\方法\产品分析框架\SKILL.md                           ← 本体
```

- ①② 是 WorkBuddy 的加载约定：`skills\` 下**每个子目录**若含 `SKILL.md` 即视为一个 skill，**目录名就是 skill 名**；目录内没有 `SKILL.md` 就没有 skill。
- ③ 经实测是本机**唯一稳定可用**的链接形式（见 6.2）。
- 而 **junction 只能指向目录**（NTFS 硬限制）。所以只要链路上任何一环要求「指向单个文件」，整条链就不成立。

### 6.2 实测：文件级链接在本机不可用（2026-10-08）

曾考虑一条折中路径：调研侧平铺成文件，应用层留 4 个实体文件夹，各放一个指向平铺文件的**文件符号链接**充当 `SKILL.md`。实测否决：

| 测试项 | 结果 |
|---|---|
| 同盘硬链接 `mklink /H` | ✅ 命令成功（但硬链接**必须同卷**，C:\ 与 D:\ 之间用不了） |
| 跨盘硬链接 `mklink /H`（C→D） | ❌ `系统无法将文件移到不同的磁盘驱动器。` |
| 跨盘符号链接 `mklink`（C→D） | ⚠️ **命令报 rc=0「创建成功」，但文件实际不存在**（`lexists=False`、目录列表为空、读取报 WinError 2） |
| 对照：目录联接 `mklink /J`（C→D） | ✅ 成功，链接内文件**可正常读取** |

**即：文件级链接在本机要么不可用、要么不可靠；目录级 junction 稳定可用。** 那条折中路径走不通。

| 3 | **4 个 skill 全部失效** | 只平铺这两个，就与另两个（C端方向方法论 / 个人开发者方法论）结构不一致；全平铺则 4 个 skill **全部**失去自动加载 |
| 4 | **相对路径要修** | 如 `研究报告规范\SKILL.md` 里的 `..\产品分析框架\references\产品分析框架-提问手册.md` —— 平铺后 `..\产品分析框架\` 不再存在（**这类失效不报错，只是静默指向错处**） |
| 5 | **换机/同步更脆弱** | 现在是「拷目录 + 建 4 条 junction」；平铺后没有任何链接可用，skill 能力只能手工重建，且重建说明已随 SOP 删除 |

### 6.4 我的判断

**不建议平铺。** 这两个 skill 的价值恰恰在「被自动加载」——你不需要记得去读它们，模型匹配到场景时会自动读。平铺成文件后，它们变成两份**需要每次主动点名**的文档，实际使用率会掉到接近零，等于**静默废弃**两个 skill，而约 470 KB 内容资产还留在磁盘上占位置。

如果你觉得这个目录「看起来不像文档库、层级太绕」，更对症的做法是**用本文件把结构讲清楚**（已做），而不是把 skill 打散——因为 **skill 文件夹不是包装层，是运行载体**。
