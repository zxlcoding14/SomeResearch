## 〇、结论先行（TL;DR）

1. **个人开发者不是「小号的公司」，约束结构完全不同。** 公司的约束是资源（预算、人力、渠道），个人的约束是**时间、资质与承受力**。用公司标准评估一个人的生意，会永远在选择「市场最大」的方向，而不是「我这条命能跑通」的方向。
2. **第一约束不是需求，是「能不能合法收到钱」和「能不能长期承受隐性成本」。** 这两件事在**写代码之前**就该确认；否则做出来的东西再好，也收不到钱，或赚的钱被客服与合规吃光。
3. **四道闸门，顺序否决，不可跳**：① **收得到钱** → ② **扛得住成本** → ③ **送得到人** → ④ **算得过账**。前两道不过，后面的分析全部作废。
4. **时间预算决定「每年只能认真做一件事」。** 在职副业每周 8–15 小时，其中 30%–50% 会被上线后的维护 / 客服 / 运营吃掉。所以**选错方向的机会成本，远高于做得慢**。
5. **不可能三角：高频迭代 / 深度销售 / 大规模投放，同一时间只能占两角。** 个人的最优解是「**高频迭代 + 社区分发（放弃投放）**」。
6. **个人开发者的天然优势在 C 端与「自助型小微 B」**（无需销售团队、无需现场交付）；天然劣势在**需要人力与资质的一切环节**（招投标、等保、私有化实施、7×24 SLA）。
7. **个人开发者的头号杀手不是竞品，是客服。** 200 个付费用户若每人每月问一次，就约等于每工作日 10 次支持请求——一个人的全部业余时间。
8. **【否定性结论】大多数「看起来能做」的方向，死在成本和分发上，而不是死在需求上。** 正确起点是「**收钱路径明确 + 边际成本可控 + 分发渠道我自己就泡在里面**」的**三重交集**，而不是「需求最有想象力」的那一个。

## 一、方向定义：个人开发者的真实约束

### 1.1 一句话定义

> **一个人，用自己的时间与少量资金，独立完成「做出产品 → 收到钱 → 持续交付」全链路。**
> 关键在**「全链路」**：任何一环需要他人配合或额外资质，这个方向对个人就不成立。

### 1.2 最容易犯的元错误

| 元错误 | 表现 | 后果 |
|---|---|---|
| **用公司标准评估一个人的生意** | 总在选「市场最大 / 竞品最少」的方向 | 选到需要团队与资质的方向，结构性做不动 |
| **把「我能不能做出来」当成主要问题** | 只评估技术可行性 | 做出来了但收不到钱 / 送不到人 |
| **把「成本」等同于「服务器那点钱」** | 漏掉客服 / 运维 / 机会成本 | 账面盈利、实际亏时间 |
| **把「慢」当成主要风险** | 追求功能完备再上线 | 永远停留在「调研 / 开发阶段」 |

### 1.3 时间预算现实换算

| 现实 | 含义 |
|---|---|
| 每周可投入时间 ≈ 8–15 小时（在职副业） | 每月 ≈ 35–65 小时 |
| 一个可用 MVP 通常需要数月 | 意味着**必须选「最小形态」**（单点工具 > 套件 > 平台） |
| 上线后维护 / 客服 / 运营会吃掉 30%–50% 的可用时间 | 实际能用于「做新功能」的时间只剩一半 |
| 因此：**能同时维护的产品数量 ≈ 1 个** | 同时维护 2 个以上会全部做不好；选方向时必须一次选对 |

> **结论**：个人开发者的约束不是「想不出好点子」，而是**每年只能认真做一件事**。所以「选错方向的机会成本」远高于「做得慢」。

### 1.4 不可能三角

> **同一时间只能占两角，第三角必然放弃：**

```
        高频迭代（快）
           /    \
          /      \
  深度销售 ────── 大规模投放
```

| 选择 | 意味着 | 适合的产品 |
|---|---|---|
| 高频迭代 + 大规模投放 | 需要全职 + 预算，**个人基本不可得** | — |
| 高频迭代 + 深度销售 | 需要大量销售时间，**产品做好但没人买** | 高客单价小 B |
| 深度销售 + 大规模投放 | 需要人力与预算 | — |
| **高频迭代 + 社区分发（放弃投放）** | ✅ **个人最优解** | C 端工具、开发者工具 |

### 1.5 【否定性结论】个人开发者的三个「结构性做不到」

| # | 结构性做不到 | 为什么不是努力问题 |
|---|---|---|
| 1 | **需要现场交付 / 招投标 / 私有化实施** | 需要团队、资质与账期承受力，一个人物理上做不到 |
| 2 | **需要 7×24 SLA 的基础设施类产品** | 稳定性承诺需要轮值与备份人力 |
| 3 | **需要持续人工介入（审核 / 定制 / 深度服务）** | 收入增长会被人力成本同比吃掉，边际成本不为零 |

## 二、分层概览：四道闸门（顺序否决，不可跳）

> **用法**：从上往下依次过。**任一道不过，先解决它，不要往下分析**——这是最容易被跳过、也最致命的一条。

| 闸门 | 要回答的问题 | 不过则 | 判据工具 | 详见 |
|---|---|---|---|---|
| **闸门 1 · 收得到钱** | 我有合法主体与通道吗？品类被通道接受吗？ | 项目不成立，换方向（**不是努力问题，是结构问题**） | 主体与通道检查表 · 通道对照表 | §3.1 |
| **闸门 2 · 扛得住成本** | 客服 / 运维 / 合规的隐性成本，我一个人的时间承受得住吗？ | 缩形态（自助化 / 降低支持面）或换方向 | 全成本清单 · 边际成本红线 · 客服承载上限 | §3.2 |
| **闸门 3 · 送得到人** | 前 100 个用户我能零预算触达吗？ | 通用框架已判**一票否决** | 增长引擎选择表 · 首 100 路径 · CAC 实测 | §3.3 |
| **闸门 4 · 算得过账** | 盈亏平衡用户数 × 我的渠道能力，可达吗？ | 调客单价 / 调成本结构；不可调则杀 | 生存线公式 · 回本周期 · 退出信号 | §3.4 |

**与「七层提问法 / 五段式流水线」的映射（便于和已有框架对接）**

| 四道闸门 | 对应七层提问法 | 对应五段式流水线的哪一段 |
|---|---|---|
| 闸门 1 收得到钱 | L4 怎么赚钱 + 新增 L4.6 交付与合规 | ① 定约束（**必须在动手前**） |
| 闸门 2 扛得住成本 | 新增 L4.5 盈利模型 + L4.6 交付与合规 | ③ 快筛否决项 + ④ 证伪（成本实验） |
| 闸门 3 送得到人 | L2 给谁用 + L5 竞争位势 | ③ 快筛（一票否决） |
| 闸门 4 算得过账 | 新增 L4.5 盈利模型 | ⑤ 立项（生存线测算） |

## 三、逐闸门展开

### 3.1 闸门 1 · 收得到钱（动手前必须有答案）

#### A. 主体与通道

| 必答问题 | 追问 |
|---|---|
| 我以什么身份收钱？（自然人 / 个体工商户 / 有限公司 / 海外主体） | 有没有能力开对公账户？能不能开发票？ |
| 走哪个收款通道？（自有支付 / Merchant of Record / 应用商店内购 / 线下转账） | 该通道**需要什么资质**、抽成多少、几天到账？ |
| 支付通道会不会因为我的品类被拒？（AI / 工具类等） | 有没有备用通道？ |
| 收款通道与分发渠道是否绑定？（上架商店是否必须走平台内购？） | 平台抽成后，我的定价还成立吗？ |

> **死信号**：说不出「钱从哪个口子进来」；通道需要资质而我完全不具备。
> **好信号**：通道明确、费率已核算进定价、到账周期可接受。

**通道对照表（费率一律「需核实」，采集日 2026-10-08，使用时必须回官方页重核）**

| 通道类型 | 常见计费结构（参考区间·需核实） | 主要门槛 | 适合谁 |
|---|---|---|---|
| 国际卡收单（Stripe 类） | 约 2.9% + $0.30 / 笔 | 需可接收外币的主体；不代扣税 | 有海外主体或能接外币 |
| Merchant of Record（Paddle / Lemon Squeezy 类） | 约 5% + $0.50 / 笔 | 门槛低，**由平台代扣全球税** | **个人开发者首选**（省掉全球税务负担） |
| 应用商店内购 | 15% / 30%（小企业计划常见 15%） | 必须走平台 IAP；审核政策风险 | 纯 App 分发 |
| 国内聚合支付（微信 / 支付宝） | 约 0.6% / 笔 | **需商户资质**（个体户或公司） | 面向国内 C 端 / 小微 B 端 |
| 平台分成（市场 / 插件商店） | 视平台政策而定 | 依赖平台 | 插件 / 模板类 |
| 人工转账 / 对公汇款 | 0%（银行手续费另计） | 无法规模化，纯手工 | 早期 B 端验证 |

#### B. 定价策略与结构

| 必答问题 | 追问 |
|---|---|
| 我用哪一种定价逻辑？（价值定价 / 竞品锚定 / 成本加成 / 损失规避） | 用户能算清账吗（「省我 10 小时/月」比「功能更强」好卖）？ |
| 是不是三档结构（够用 / 好用 / 全都要）？ | 中间那档是不是我真正想卖的？低价档是不是只为锚定？ |
| 计费单位选对了吗？（买断 / 订阅 / 按量 / 混合） | 与**使用频次**匹配吗？（低频收订阅 = 必然流失） |
| 定价与**边际成本**的关系？ | 每多一个用户，我多花多少钱？定价能覆盖住吗？ |
| 要不要区域定价 / 学生价 / 年付折扣？ | 折扣会不会打穿价值感知？ |

> **死信号**：定价是「看着竞品随便定的」；客单价 < 单用户边际成本。

#### C. 支付摩擦与税费

| 必答问题 | 追问 |
|---|---|
| 退款政策是什么？退款率预期多少？ | 有没有把退款率计入营收模型？ |
| 会不会遇到拒付（chargeback）？怎么处理？ | 拒付率过高的后果（通道封禁）知道吗？ |
| 要不要开发票？开票成本与人工成本谁承担？ | **B 端客户一定要发票**，这点常被 C 端出身的人忽略 |
| 跨境业务涉及哪几种税？（VAT / Sales Tax 等） | 用 MoR 通道能不能把这块外包出去？ |

#### D. ARPU 提升机制

| 必答问题 | 追问 |
|---|---|
| 怎么让老用户付更多？（席位扩容 / 用量阶梯 / 增值包 / 服务） | 有没有「越用越贵但越划得来」的结构？ |
| 有没有年付 / 多年付？ | 年付折扣换现金流，划算吗？ |
| 免费用户里有多少比例可能升级？ | 触发升级的那个「时刻」是什么？ |

> **C 端 vs B 端的 ARPU 提升路径不同**：C 端靠「**升级**」（个人版 → 专业版），B 端靠「**扩容 + 续约**」（5 席位 → 50 席位）。C 端 ARPU 天花板明显低于 B 端，但 B 端的获客成本也高数倍。

### 3.2 闸门 2 · 扛得住成本

#### A. 全成本清单（必须逐条填数）

| 成本类别 | 具体项 | 性质 |
|---|---|---|
| **一次性投入** | 研发工时（折算机会成本）、设计、商标注册、软著登记、必要设备 | 沉没 |
| **每月固定** | 服务器 / 云资源、域名、SSL、开发者证书（如 Apple 年费）、代码签名、第三方 API 月费、工具订阅（设计 / 监控 / 客服系统） | 固定 |
| **每单变动** | 支付手续费、模型调用费（AI 类**最大变量**）、带宽 / 存储、发票与税务成本、退款 | 变动 |
| **隐性（最常被漏）** | **客服与支持时间**、运维与故障处理、内容审核、合规维护、迭代维护、社区运营 | 隐性 |
| **时间的机会成本** | 我每周投 N 小时，若去做别的能挣多少 | 隐性（个人开发者的真实成本） |

> **纪律**：把「客服时间」按小时折算成钱写进去。个人开发者最常见的幻觉是「成本只有服务器那点钱」。

#### B. 盈亏平衡与回本周期

```
月毛利/单        = 客单价(月) − 单用户变动成本
盈亏平衡付费用户数 = 月固定成本 ÷ 月毛利/单
回本周期(单用户)  = 单用户获取成本 ÷ 月毛利/单      ← 必须 < 12 个月，越短越好
```

| 必答问题 | 追问 |
|---|---|
| 我每月固定成本是多少？（写数字） | 有多少是「不赚钱也得付」的？ |
| 单用户月毛利是多少？ | 涨价 20% 或降本 20%，哪个更容易？ |
| 要多少付费用户才能不亏？ | 这个数，**按我的渠道能力，多久能到**？ |
| 多久能回本？ | 如果 24 个月才能回本，我撑得住吗？ |

> **个人开发者专用换算**：买断 ¥99 的产品，要覆盖每月 ¥500 的固定成本 → **每月需卖出约 5 单以上**（未计手续费与退款，需自行代入实际费率）。**先算这个数，再去想「怎么卖到 5 单」——比先想「做什么功能」重要得多。**

#### C. 边际成本可控性（AI 类方向的头号杀手）

| 必答问题 | 追问 |
|---|---|
| 每多一个用户，我多花多少钱？ | 是**近似 0**（纯本地工具）还是**线性增长**（云端 / 模型调用）？ |
| 重度用户会不会把我的成本拖爆？ | 有没有用量上限 / 阶梯价 / 降级策略？ |
| 模型 / API 供应商涨价 30%，我还赚钱吗？ | 有没有可替换方案？ |
| 缓存 / 本地推理能不能降本？ | 降本后体验损失多少？ |

> **新增一票否决**：**边际成本 ≥ 定价的方向，直接杀**（或必须重做定价结构）。这是 AI 时代个人开发者最常踩的坑：**免费用户把 API 额度吃光。**

#### D. 支持成本与承载能力（隐性成本里最要命的一项）

| 必答问题 | 追问 |
|---|---|
| 每天 / 每周大概多少支持请求？ | 一人能不能扛住？扛不住的临界点是多少用户？ |
| 支持渠道有哪些？（邮件 / 群 / 工单） | 有没有把常见问题做成文档来自助化？ |
| 有没有 SLA 承诺？ | 承诺了做不到，会不会引发差评 / 退款？ |

> **个人开发者的头号杀手不是竞品，是客服。** 量级推演示例（**非实测，需自行修正**）：200 个付费用户若每人每月问一次 ≈ 每工作日约 10 次支持请求——这已是一个人的全部业余时间。

#### E. 迭代节奏与稳定性

| 必答问题 | 追问 |
|---|---|
| 产品会退化吗？（依赖的 OS / API / 平台政策会变） | 每年要花多少时间做「维护性开发」而不是新功能？ |
| 出故障了怎么办？ | 有没有监控、备份、回滚方案？ |
| 版本节奏定多快？ | 一个人做得过来吗？ |

### 3.3 闸门 3 · 送得到人

#### A. 增长引擎选择

| 引擎类型 | 适用 | 特征 | 适合个人开发者？ |
|---|---|---|---|
| **内容 / SEO**（教程、对比评测、开源引流） | C 端工具、开发者工具 | 慢但复利，成本 = 时间 | ✅ **最匹配** |
| **社区运营**（垂直论坛、群、Discord） | 细分人群 | 深度但天花板低 | ✅ 匹配 |
| **应用商店 ASO / 榜单** | 移动端 / 插件市场 | 有平台红利也有政策风险 | ⚪ 可做，被动 |
| **产品自传播（PLG）** | 有分享 / 协作属性的产品 | 需要产品内嵌传播机制 | ✅ 若能设计 |
| **付费投放** | C 端规模化 | 需要预算 + 转化数据 | ❌ 个人慎入（除非 ROAS 已实测为正） |
| **KOL / 测评** | 消费级工具 | 一次性峰值，衰减快 | ⚪ 可小试 |
| **B 端销售（SLG）** | 企业客户 | 客单价高、周期长、需人力 | ❌ 一人公司极难 |

> **判定口径**：`我能不能在 2 周内、零预算、让 20 个目标用户开口说话？` 答不出 → 通用框架已判定为**一票否决**（分发不可得）。本闸门只是把它**展开成渠道选择与执行路径**。

#### B. 首个 100 / 1000 用户的具体路径

| 必答问题 | 追问 |
|---|---|
| 前 100 个用户，**具体从哪来**？（指名到社群 / 名单 / 关键词） | 我能说出 3 个具体的群名或版块吗？ |
| 从 100 到 1000，靠什么机制放大？ | 是内容复利、口碑推荐，还是渠道投放？ |
| 获客成本（CAC）怎么实测？ | 有没有做过一次真实的获客动作（哪怕只是发一个帖子）来测？ |
| 转化漏斗每一层的数字？ | 曝光 → 访问 → 试用 → 付费，哪一层最漏？ |

#### C. 激活与留存

| 必答问题 | 追问 |
|---|---|
| 用户第一次用，多久能感受到价值？（Aha moment 是什么） | 能不能压缩到 3 分钟内？ |
| 留存曲线长什么样？（次日 / 7 日 / 30 日） | 是「微笑曲线」（回升）还是持续下滑（= 没有真实价值）？ |
| 月流失率（churn）多少？ | 年付客户的续费率比月付高多少？ |
| 什么行为与留存强相关？ | 能不能主动把用户推向那个行为？ |

> **死信号**：只谈下载量 / 注册量，从不谈留存。**下载量是虚荣指标，留存才是命。**
> **审计口径**：留存必须按**自然日 / 自然周分群**看，不能只看总体平均（会被新增用户稀释）。

### 3.4 闸门 4 · 算得过账

| 必答问题 | 判定 |
|---|---|
| 盈亏平衡付费用户数是多少？ | 用 §3.2 B 公式算出具体数字 |
| 我的渠道能力，多久能到这个数？ | 答不出 → 回到闸门 3 补测 |
| 单用户回本周期多长？ | 必须 < 12 个月；> 24 个月基本不可承受 |
| 涨价 20% 或降本 20%，哪个更容易？ | 优先降本（客单价受心理价位压制） |
| **「时间换钱」的账算清了吗？** | 每月净收入是否显著高于投入时间的机会成本？ |

**两个盈利模型（按路线选一个套）**

```
【C 端路线】
年营收   = 可触达人数 × 触达转化率 × 激活率 × 付费率 × 客单价
年毛利   = 年营收 × (1 − 支付费率) − 变动成本合计
可行条件 = 年毛利 > 年固定成本 + 时间机会成本

【B 端路线（仅限自助型小微 B）】
年营收   = 新签客户数 × 年客单价 + 存量客户 × 年客单价 × 续费率 + 扩容收入
年毛利   = 年营收 − (销售人力 + 实施交付 + 支持服务 + 云成本)
可行条件 = 年毛利 > 固定成本，且 单客户 CAC 回收周期 < 12 个月
```

**退出信号（什么时候该停——提前写死）**

| 信号 | 含义 |
|---|---|
| 上线 3 个月，付费用户 < 5 且无增长 | 不是分发问题，就是价值问题 → 复盘后停或换 |
| 客服时间 > 开发时间 | **形态错了**（支持面太宽），不是努力不够 |
| 每月净收入 < 服务器成本 × 3，持续 6 个月 | 商业模型不成立 |
| 依赖的单一平台改政策导致分发腰斩 | 平台风险已实现，需重建渠道 |
| 自己已经不想做这件事了 | 「愿不愿意做 2 年」这一问的答案变了 → 诚实退出 |

## 四、形态选择：个人开发者做 / 不做对照表

| 适合（起点） | 原因 | 不适合 | 原因 |
|---|---|---|---|
| **单点高频 mini-tool（买断）** | 卖点单一、支持面窄、边际成本 ≈ 0 | 需要现场实施的重行业 SaaS | 交付成本 = 团队级 |
| **浏览器插件 / 编辑器插件** | 自带分发渠道（商店），入口天然高频 | 需要资质的领域（金融 / 医疗 / 教育） | 牌照门槛 |
| **模板 / 预设 / 素材包** | 零边际成本、可买断 | 需要内容审核的 UGC 平台 | 审核成本与合规义务 |
| **轻量 SaaS（自助型）** | 无销售人力 | 依赖大规模 GPU 训练的方向 | 资本门槛 |
| **开发者工具 / API / 库** | 开发者是付费意愿最高、最不需要教育的人群 | 需要 7×24 SLA 的基础设施类 | 稳定性承诺个人扛不住 |
| **垂直小人群工具** | 竞品盲区、大厂看不上 | 通用大而全平台 | 冷启动几乎必败 |

**形态阶梯（从最小起步）**

| 形态 | 启动成本 | 适合谁 | 风险 |
|---|---|---|---|
| 单点工具（mini-tool） | 低 | 个人开发者、无销售团队 | 天花板有限，易被内置 |
| 工作流套件 | 中 | 有产品组合经验的小团队 | 功能蔓延，定位模糊 |
| 平台 / 生态 | 高 | 有资金、渠道、BD 能力 | 冷启动极难，几乎必败于个人 |

> **判定口诀**：`低频 + 无持续成本 → 只做买断单点工具；高频 + 有持续成本 → 可做订阅；需要教育市场 → 不做。`

## 五、合规底线清单（动手前先过）

- [ ] **主体**：明确用什么身份收款；能不能开票（有 B 端客户就必须解决）
- [ ] **通道**：确认通道接受我的品类、费率、到账周期
- [ ] **知识产权**：产品名先查商标；软著按需登记；**确认在职作品归属与竞业限制**
- [ ] **开源许可**：列出所有依赖及其许可证，排除 GPL/AGPL 传染风险与「禁商用」素材
- [ ] **模型 / API ToS**：确认允许我包装成产品对外售卖
- [ ] **数据合规**：隐私政策、用户协议、最小必要采集；跨境数据传输
- [ ] **内容合规**：AI 生成内容标识 / 备案（按最新规定核查）；UGC 审核能力
- [ ] **税务**：合法申报口径（**咨询专业人士，本文不给结论**）

**合规要点逐条展开**

| # | 要点 | 必答问题 | 追问 |
|---|---|---|---|
| 1 | 主体选择 | 自然人（无法开票 / 难收外币） / 个体户（低成本合规） / 有限公司（能开票、能签 B 端合同、可开对公户） | 有没有能力开对公账户？ |
| 2 | 软著登记 | 要不要做？ | 上架国内应用商店、走政府 / 企业采购常需要 |
| 3 | 商标 | 注册了吗？ | ⚠️ 先查再定名，被抢注后改名成本极高 |
| 4 | 职务作品 | 代码版权归属清晰吗？ | ⚠️ **在职开发的作品可能属于职务作品**，需确认劳动合同约定 |
| 5 | 竞业限制 | 有没有风险？ | 做的东西与原公司业务重合吗？ |
| 6 | 开源传染 | 用了哪些库？各自许可证？ | GPL/AGPL 会不会要求我开源整个产品？ |
| 7 | 素材授权 | 图片 / 音效 / 字体授权范围覆盖我的使用方式吗？ | 有些素材明确禁止商用 |
| 8 | 模型 ToS | 允许我把它包装成产品卖吗？ | 很多模型服务条款禁止「以本服务为卖点转售」 |
| 9 | 个人信息 | 涉及个人信息处理吗？ | 需不需要隐私政策、单独同意、处理者告知？ |
| 10 | 跨境 | 面向境外用户吗？ | GDPR / CCPA 等适用吗？ |
| 11 | AI 内容 | 有 AI 生成内容吗？ | 国内可能涉及**生成式 AI 服务备案 / 算法备案 / 深度合成标识**（按最新规定核查） |
| 12 | UGC | 有 UGC 吗？ | 内容审核义务与成本能承担吗？ |
| 13 | 平台政策 | 我依赖哪些平台？（商店 / 云 / 模型 / 支付） | 任一个改政策，我会怎样？有没有备用方案？ |

## 六、个人开发者专用筛具与一票否决

### 6.1 打分卡（个人开发者加固版 · 12 维，满分 135）

| 维度 | 权重 | 5 分锚点 | 1 分锚点 |
|---|---|---|---|
| 使用频次 | ×3 | 每天 / 每周多次 | 一次性 |
| 痛点硬度 | ×3 | 不做直接损失钱或触发合规风险 | 只是「更方便」 |
| **分发可得性** | ×3 | 能直接触达并让 20 人开口 | 完全不知道人在哪 |
| 现有替代糟糕度 | ×2 | 只能手工或付费买别扭的老工具 | 系统内置已够用 |
| 付费方明确度 | ×2 | 有预算科目 / 决策人清晰 | 无任何付费先例 |
| 持续交付成本 | ×2 | 有真实云 / 模型 / 内容成本 → 订阅成立 | 纯一次性交付 → 只能买断 |
| 你方独占优势 | ×2 | 有数据 / 身份 / 渠道别人没有 | 无 |
| 窗口期长度 | ×1 | 大厂 2 年内不会做 | 下个系统版本就被内置 |
| 合规 / 平台风险 | ×1 | 无单一 API 依赖 | 依赖单一平台政策 |
| **收款可行性**（新增） | ×3 | 通道明确、资质具备、费率可接受 | 无合法收款路径 |
| **隐性成本可控性**（新增） | ×3 | 可完全自助，边际成本 ≈ 0 | 每单需人工介入 |
| **客体匹配度**（新增） | ×2 | 形态与我的时间 / 资质完全匹配 | 需要团队或资质 |

**计分**：满分 = (3+3+3+2+2+2+2+1+1+3+3+2) × 5 = **135**。
**阈值**：≥ 70%（≈95 分）→ 进入证伪环节；≤ 50%（≈68 分）→ 直接杀；中间区间 → 只做**最低成本**的补充采集，不投入实验资源。

### 6.2 一票否决（不论总分多高，触发即杀）

| # | 否决项 | 为什么不可救 | 对个人开发者的致命度 |
|---|---|---|---|
| 1 | **收款路径不成立** —— 通道需要我不具备的资质，或品类被通道明令禁止 | 产品再好也无法变现 | ★★★（**个人最高发**） |
| 2 | **边际成本 ≥ 定价** —— 每多一个用户就多亏一份钱 | 规模越大死得越快，商业模式本身不成立 | ★★★ |
| 3 | **客服 / 合规成本超出个人承载上限** —— 单用户需要人工介入，或触发的合规义务需要专职人力 | 收入增长会被成本同比吃掉 | ★★★ |
| 4 | **B 端方向要求我方不具备的资质或现场交付能力**（招投标资质、等保、私有化实施） | 结构性做不到，不是努力问题 | ★★★ |
| 5 | **分发不可得** —— 需求再好也不属于你 | 2 周内零预算触达不到 20 个目标用户 | ★★★ |
| 6 | **使用频次 = 一次性，且无持续交付成本** | 订阅不成立，只能买断，天花板极低 | ★★ |
| 7 | **依赖单一平台 / 单一 API，且一个版本更新就可能被内置** | 生命周期不可控 | ★★★ |
| 8 | **触碰合规红线**（金融 / 医疗 / 未成年人 / 爬虫 / 版权 / 隐私数据） | 直接排除整类方向 | ★★ |
| 9 | **答不出「去掉 AI 之后还剩多少价值」**（AI 类专用） | 大概率只是 prompt 包装 | ★★★ |

> 前 4 条是**个人开发者专项新增**（通用框架原本只有后 5 条）。

### 6.3 盈利可行性 12 问（时间紧只答这 12 个）

| # | 问题 | 答不出来的后果 |
|---|---|---|
| 1 | 钱从哪个通道进来？我具备资质吗？ | 做出来也收不到钱 |
| 2 | 定价多少？依据是什么（价值 / 竞品 / 人力替代成本）？ | 定价靠猜 |

| 6 | 前 100 个用户具体从哪来（指名到社群 / 名单）？ | 分发不可得 = 一票否决 |
| 7 | 转化漏斗每层的数字？（曝光→访问→试用→付费） | 不知道瓶颈在哪 |
| 8 | 次日 / 7 日 / 30 日留存多少？月流失率多少？ | 看不清产品是否真有价值 |

| 10 | 用了哪些开源库 / 第三方 API？许可证允许我商用吗？ | 法律风险 |

| 12 | **（走 B 端时）** 使用者 / 决策者 / 付款者是谁？钱从哪个科目出？ | **用户喜欢但签不下单** |

## 七、个人开发者高频反模式（穷举）

| # | 反模式 | 为什么错 | 替代做法 |
|---|---|---|---|
| 1 | 把「开源 + 赞助」当商业模式 | 赞助收入极不稳定，且与「付费买断」互相掐死付费意愿 | 开源社区版 + 商业版双轨，或纯商业闭源 |
| 2 | 认为「上架就有人买」 | 商店是渠道不是分发；无推广 = 零曝光 | 上架前先攒 100 个种子用户 |
| 3 | 用「功能多」当卖点 | 功能是成本；一个人维护不动 | 单点做到最好 |
| 4 | 拿「AI」当卖点 | 用户不为技术付钱，为结果付钱；模型能力下放会抹平 | 卖可感知的结果（快 N 倍 / 少做 N 步） |
| 5 | 定价过低求销量 | 低价需要海量分发，恰好是个人最缺的 | 提高客单价，缩小目标人群 |
| 6 | 免费额度给太大 | 边际成本失控 + 免费用户永不变现 | 免费版限功能，付费版限用量 |
| 7 | 同时开两个项目 | 时间切片导致两个都做不好 | 一次只做一个 |
| 8 | 只算服务器成本 | 漏掉客服、运维、机会成本 | 全成本清单逐条填数 |
| 9 | 先做产品再想收款 | 可能做了个收不到钱的东西 | **闸门 1 前置** |
| 10 | 按大厂打法定计划 | 进度永远完不成，挫败后放弃 | 按每周 8–15 小时的真实预算排期 |
| 11 | 用「需求最有想象力」选方向 | 想象力与「我这条命能跑通」无关 | 用四道闸门 + 三重交集来选 |

## 八、退出机制：什么时候该停

> **必须在开工前写死，否则会无限期投入。**

| 信号 | 含义 | 动作 |
|---|---|---|
| 上线 3 个月，付费用户 < 5 且无增长 | 不是分发问题，就是价值问题 | 复盘后停或换 |
| 客服时间 > 开发时间 | 形态错了（支持面太宽） | 缩形态或停 |
| 每月净收入 < 服务器成本 × 3，持续 6 个月 | 商业模型不成立 | 停 |
| 依赖的单一平台改政策导致分发腰斩 | 平台风险已实现 | 重建渠道，或停 |
| 自己已经不想做这件事了 | 「愿不愿意做 2 年」的答案变了 | 诚实退出 |

**「愿不愿意做 2 年」这一问为什么关键**：它不靠新鲜感，靠兴趣与客户关系。**这条比「我能不能做出来」更常被忽略，但决定能否活到收钱那天。**

## 九、选路：个人开发者该走 C 端还是 B 端

| 维度 | C 端 | B 端 |
|---|---|---|
| 增长瓶颈 | **分发** | **决策链 + 销售人力** |
| 销售人力 | 几乎不需 | 必需（除自助型小微 B） |
| 客单价 | 低（¥9–¥999/年量级，需实测） | 高（¥千–¥百万/年） |
| CAC | 低 | 高 |
| 交付成本 | 近 0（自助） | 高（实施 / 培训 / 对接） |
| 合规门槛 | 较低 | 高（等保 / 信创 / 私有化 / 审计） |
| 现金流 | 即时到账 | **账期风险**（3 个月以上账期 + 一人公司 = 现金流断裂） |
| 失败主因 | 无人知道 / 免费替代够用 | 用户喜欢但签不下单 / 交付拖垮 |
| **个人开发者可行性** | ✅ **主战场** | ⚠️ **仅「自助型小微 B」可行**；重 B 不可行 |

**B 端销售模式对照（个人只看这一列）**

| 模式 | 特征 | 个人开发者可行性 |
|---|---|---|
| **自助式（PLG + Self-serve）** | 客户自己注册付费，无需销售 | ✅ **个人唯一可行路径** |
| 轻销售（Inside Sales） | 线上沟通、远程演示 | ⚪ 一人勉强可做，但极耗时间 |
| 现场销售（Field Sales） | 上门、招投标 | ❌ 需要团队 |
| 渠道 / 代理 | 靠伙伴卖 | ⚪ 需先有产品与伙伴网络 |
| 政府采购 / 集采 | 招标、资质、账期 | ❌ 个人基本无缘（无资质、账期长） |

> **一句话选路**：**C 端拼分发，B 端拼信任。** 个人开发者的天然优势在 C 端（无需销售团队）与技术型小微 B（无需现场交付）；天然劣势在需要人力与资质的一切环节。

## 十、可执行位置判断（收敛）

### 10.1 值得做的方向画像（三重交集）

> **收钱路径明确** × **边际成本可控** × **分发渠道我自己就泡在里面**

| 条件 | 具体判据 |
|---|---|
| 收钱路径明确 | 通道明确、资质具备或可得、费率可核算进定价；有真实价格锚点（竞品订阅价 / 代做报价 / 采购预算） |
| 边际成本可控 | 每用户变动成本 ≈ 0，或有可靠的用量限制 / 降级策略 |
| 分发渠道我泡在里面 | 我本人就在目标人群的社区里；能指名说出 3 个具体社群 / 名单 |
| （加固）形态匹配 | 单点工具 / 插件 / 模板 / 轻量自助 SaaS；无需现场交付与资质 |
| （加固）支持面窄 | 常见问题可自助化，客服时间可控 |
| （加固）我愿意做 2 年 | 不靠新鲜感，靠兴趣与客户关系 |

### 10.2 不要碰的方向画像（负面清单）

| # | 特征 | 为什么 |
|---|---|---|
| 1 | 需要现场实施 / 招投标 / 私有化交付 | 结构性做不到 |
| 2 | 需要 7×24 SLA 或稳定性强承诺 | 一人无法轮值 |
| 3 | 需要持续人工介入（审核 / 定制 / 深度服务） | 边际成本不为零 |
| 4 | 需要我不具备的资质（金融 / 医疗 / 教育牌照、等保） | 门槛即天花板 |
| 5 | 收款通道明确拒绝我的品类 | 闸门 1 不过 |
| 6 | 云端 AI 无限用量、无任何限额 | 边际成本失控 |
| 7 | 客户账期 ≥ 3 个月 | 一人公司现金流断裂 |
| 8 | 需求真实但我完全不知道人在哪 | 分发不可得 |
| 9 | 需要大额前期投入（算力 / 内容 / BD 预算） | 超出资源边界 |
| 10 | 需要教育市场才被理解的卖点 | 需要教育才被理解的卖点 ≈ 不存在 |

### 10.3 从哪进场 / 最小验证

| # | 问题 | 判定 |
|---|---|---|
| 1 | 用户装它只为做**哪一件事**？ | 说不出来 = 还没想清楚，别开工 |
| 2 | 它明确**不做什么**？（Non-scope） | 防止功能蔓延 |
| 3 | 变现的**付费墙**卡在哪一层？与频次匹配吗？ | 位置决定商业模式类型 |
| 4 | 是否有**真实的持续交付成本**？ | 没有 → 只能买断 |

**最小验证：证据强度阶梯（只认行为，不认口头）**

| 强度 | 实验 | 做法 | 测的是 | 适用原型 |
|---|---|---|---|---|
| 弱 | 问未来意愿 | 「你会用吗 / 你觉得有用吗」 | 意愿（**几乎无效**） | — |
| ↓ | 假门测试（Fake Door） | 落地页 + 按钮 +「即将上线」 | 需求强度（**不能测付费**）；注意伦理 | ③ 能力窗口型 |
| ↓ | 留邮箱 / 预约 | 「留下邮箱第一时间通知」 | 明确意向 | — |
| ↓ | 人肉代做（Concierge） | 手工交付 5 个真实用户，观察是否复用 | **真实使用行为** | ② 手工自动化型 |
| **强** | 预售 / 直接收钱 | 明码标价，要求现在付款或付定金 | **付费意愿（唯一强信号）** | ①② 替代升级 / 手工自动化 |
| 补充 | 定向下访谈 20 人 | **只问过去行为，不问未来意愿** | 人群规模与付费力 | ④ 细分人群型 |

**四种机会原型 → 验证方式映射**

| 原型 | 信号特征（怎么认出来） | 该测什么 | 典型形态 | 主要风险 |
|---|---|---|---|---|
| **① 替代升级型** | 存在一个**还在稳定收钱但体验陈旧**的老工具 | 付费意愿已被验证，只需测「愿不愿迁移」 | 单点工具，主打「一键导入 / 迁移」 | 低估迁移成本；老工具降价反击 |
| **② 手工自动化型** | 大量教程 / 模板 / 脏脚本 / 外包代做 | 人肉代做：自动化后是否真的更快、是否复用 | 小工具 / 插件 / CLI | 自动化后价值缩水；用户其实享受手工过程 |
| **③ 能力窗口型** | 新模型 / 新 API / 新 OS 能力出现 | 假门 + 48 小时拼装 Demo（**不能慢慢验证**） | 轻量 Demo / 插件 | 窗口极短、大厂跟进最快 |
| **④ 细分人群型** | 大厂通用产品在该人群明显不适配 | 深访 20 人 + 小规模付费测试 | 垂直单点工具 | 付费能力不足；易被通用产品一个开关覆盖 |

**判定门槛（写死，不许临场放宽）**

| 结论 | 条件 |
|---|---|
| **立项** | ≥5 个真实用户持续使用（非一次性）；或 ≥3 个明确的付费信号（含预付、定金、书面意向） |
| **待观察** | 有使用但无付费信号 → 补做收费实验，2 周内无改善则杀 |
| **杀掉** | 无人持续使用；或用户明确表示「免费可以，付费不要」 |

**时间盒（写死，防止无限期投入）**

| 周次 | 动作 | 时间盒 | 交付物 |
|---|---|---|---|
| W1 前 | 定约束（**含主体与收款通道、可承受的支持量上限**） | 0.5 h | 一页约束清单 |
| W1 后 | 集中采信号（**只采不判**） | 4 h | 机会库 ≥20 条带出处原话 |
| W2 前 | 快筛 + 打分卡 + 一票否决 | 1 h | 收敛到 3 个方向 |
| W2–W3 | 3 个方向**并行**各跑 1 个证伪实验（付费实验 × 成本实验） | 各 ≤6 h | 每方向 1 个结论 |
| W4 | 只留 1 个，定义最小可做形态 + 生存线测算 | 2 h | 立项备忘 / 杀因记录 |

> 「成本实验」= **真的交付一次**，记录真实耗时与真实成本——这是个人开发者最该做、却最少做的实验。

## 附 · 口径说明与缺口声明

**口径说明**

- **【2026-10-08 口径修正】本文不含外部数据，是「文档层的边界」，不是「产出的限制」。** 用本文做**可行性判断**时，产出**必须包含数据与测算**：拿不到的数不许只写缺口——先给获取路径；确实取不到，就按「合理预估五法」（自上而下 / 自下而上 / 类比推算 / 锚点反推 / 区间优先）给出有依据的推算，写成 **假设 → 依据 → 推算 → 结果** 四段，附**置信度**与**敏感度**。**禁止的是「无依据的数字」，不是「估算」本身。** 交付须含附录三件套：A 数据明细（指标 / 数值 / 口径 / 来源级别 / 采集日）、B 测算过程与三重敏感度（定价 ±20% / 模型成本 ±30% / churn ±50%）、C 缺口声明与应查未查清单。完整方法见 skill `product-analysis-framework` §四，以及本文 §3.2 B / §3.4 的个人开发者专用测算式。
- 本文全部内容为**方法框架与判定标准**，不含任何市场规模、用户量、营收等外部量化数据。
- §3.1 通道对照表、以及各处出现的比例（15%/30% 抽成、约 0.6% 聚合支付、LTV:CAC > 3、回本周期 < 12 个月、客服吃掉 30%–50% 时间等）均为**行业常见区间或经验值**，采集日 2026-10-08，**未经官方页核实**。使用时必须回到对应官方页面重新确认，并记录采集日期与币种。
- 涉及合规与税务的内容仅用于提示「这是一个必须提前确认的问题」，**不构成法律或税务建议**，具体须咨询专业人士并查最新规定。
- §9 中 B 端合规门槛（等保 / 信创 / 算法备案 / 生成式 AI 备案等）涉及**动态变化的法律法规**，本文只列「要知道有这件事」，不提供合规结论。

**缺口声明**

- 【未实测】个人开发者的真实时间分配比例（「维护 / 客服吃掉 30%–50%」）为经验估计，**未做样本量化的实测统计**。建议自行记录 1 个月真实工时分布后修正。
- 【未实测】§3.2 D 中「200 个付费用户 → 每工作日约 10 次支持请求」为量级推演示例，非实测数据。
- 【未取得】各支付通道的**当期**费率与资质要求未逐一核对官方页；本文给出的仅为结构与量级，不可直接引用。
- 【推断】四道闸门的顺序为归纳产物，实践中闸门 3 与闸门 4 常需迭代（分发能力可影响可承受的客单价结构）。
- 【未覆盖】本文不含：融资与股权结构、并购与退出、多产品矩阵运营、团队组建与股权激励——这些超出「个人开发者做出可盈利产品」的范围，如需可另立文档。
