## 〇、结论先行（TL;DR）

> ## **会员体系的技术难点不在「怎么收钱」，而在三件事：权益位解耦、锁能力不锁数据、退款不锁死用户。数据统计的难点则相反 —— 不在「埋什么」，而在「不埋什么」：它天然要往服务端传数据，而 ⑩ 篇定的纪律是服务端不存用户数据。这两条的边界必须先划清。**

**1｜会员体系：真正决定成败的是「权益位模型」，不是 SKU 数量。**

| 反面做法（常见） | 正确做法（本文） |
|---|---|
| `if user.isVIP { 解锁 }` | `if store.isUnlocked(.aiCoach) { 解锁 }` |
| 新增权益要改所有 UI 代码 | 新增权益只改一张映射表 |
| 无法做单点解锁 | 支持「只买食谱包」等未来形态 |

> **一句话**：**用「权益位（Entitlement）→ 需求」的解耦模型，而不是「会员 = 全解锁」的布尔值。** 这决定了产品未来能不能长出第二种变现形态。

**2｜三条容易被做反的会员规则（本文的核心判断）**

| # | 规则 | 做反的后果 |
|---|---|---|
| **M-1** | **锁能力，不锁数据** —— 订阅到期后，用户已保存的自定义食谱、历史饮食记录**仍然可见（只读）** | 到期即隐藏用户自己创作的数据 → 差评 + 退款 + 投诉 |
| **M-2** | **退款/撤销售权，但不锁死已记录数据** | 同上 |
| **M-3** | **免费层永不受会员状态影响** —— 体重记录与趋势图的代码路径上**不得出现任何权益判断** | 违反 ⑧ 篇红线 #2 → 口碑自杀 |

**3｜【否定性结论】不需要第三方统计 SDK，也不需要 IDFA，连接入 ATT 弹窗都不需要。**
- **依据**：Apple 原生已免费覆盖大部分需求 —— **App Store Connect App Analytics**（曝光/下载/转化/留存/订阅报告，**零埋点**）+ **MetricKit / Xcode Organizer**（崩溃/卡顿/启动/耗电，**零 SDK**）。
- **推论**：自建埋点只需覆盖「产品行为事件」这一层，**约 20 个事件 / 3.5 人日**。
- **不接 IDFA 的额外收益**：**不触发 ATT 授权弹窗** → 不损失首启转化率。而个人开发者的分发是 ASO + 内容（⑨ 篇 §1.2 不可能三角已定「放弃大规模投放」），**本来就不需要广告归因**。

**4｜数据统计与 B-1 纪律的边界（本文最重要的口径）**

| 类别 | 例子 | 能不能上报 |
|---|---|---|
| **用户数据**（个人敏感信息） | 体重数值、BMI、热量、食物名、餐次内容、昵称、宠物名 | ❌ **绝对禁止** |
| **行为事件**（匿名、无 PII） | 「记录了一次体重」「点击了小组件」「打开了付费墙」 | ✅ 允许 |
| **允许的属性形式** | 布尔值、枚举、计数、区间桶 | ✅ |
| **禁止的属性形式** | 精确数值、自由文本、设备指纹、IDFA、位置 | ❌ |

> **一句话判据**：**传「发生了一次记录」，不传「记录的是 62.4kg」。** 计数可以，数值不行。

**5｜成本结论：整套会员体系 + 数据统计的月度增量 ≈ ¥0。** 会员体系的成本只体现为 **Apple 抽成 15%**（小企业计划），数据统计全在免费额度内。**这是「薄服务端」策略的又一次红利。**

## 一、会员体系技术方案

### 1.1 商品配置（IAP）

**复刻简化为 3 档**（⑧ 篇实测官方有 8 个 SKU，含季卡与品牌 SKU —— 首版不需要那么复杂）。

| 档位 | 价格 | Apple 商品类型 | 订阅组 | 建议 |
|---|---|---|---|---|
| 月卡 | **¥12.00/月** | 自动续期订阅 | 同一组 `vip_main` | 提供价格锚点（衬托年卡） |
| 年卡 | **¥88.00/年** | 自动续期订阅 | 同一组 `vip_main` | **主推档（高亮）** |
| 永久 | **¥168.00** | **非消耗型（Non-Consumable）** | 独立（不进订阅组） | 一次性买断 |

**配置要点（App Store Connect 侧）**

| 项 | 设置 | 理由 |
|---|---|---|
| 订阅组 | 月卡与年卡**必须同组** | 同组才能升级/降级/交叉续期（换档不重复扣费） |
| 永久版类型 | **非消耗型**，**不要用「非续期订阅」** | 非续期订阅会被 Apple 视为订阅、有到期语义；非消耗型才是「一次买断」 |
| 家庭共享 | **开启**（订阅） | 免费扩大付费覆盖面；代价是「一订阅多设备」，见 §1.7 |
| 价格点 | 确认 ¥12 / ¥88 / ¥168 为有效价格点 | 需在 App Store Connect 实际核对（不同区域点数不同）【待核】 |
| 商品 ID | 用语义化命名：`vip.monthly` / `vip.yearly` / `vip.lifetime` | 便于与权益位映射 |

> **⚠️ 关于「改价」**：App Store 现在支持直接调整价格点，但对**已订阅用户**的续订价格上调会触发**用户同意流程**（不强制、可拒绝并到期终止）。⑧ 篇记录的「官方建两个年卡 SKU（¥88 / ¥68）」是历史做法的遗留 —— **新 App 不需要这么做，直接用调价能力即可**【待核当前政策细节】。

### 1.2 权益位模型（**本节是会员体系的核心**）

**先定义权益位，再定义「商品 → 权益位」的映射，最后 UI 只依赖权益位。**

```swift
// 权益位：产品能力的原子单位
enum Entitlement: String, CaseIterable, Codable {
    case aiPhoto        = "ai.photo"            // AI 拍照识别
    case aiCoach        = "ai.coach"            // AI 营养师 / 个性化指导
    case aiAutoLog      = "ai.autolog"          // AI 自动打卡
    case recipeFull     = "content.recipe.full"     // 完整食谱内容
    case recipeCustom   = "content.recipe.custom"   // 食谱自定义（替换食材）
    case themePremium   = "theme.premium"       // 高级皮肤
    case adsFree        = "ads.free"            // 免广告
}
```

**商品 → 权益位 的映射（放本地 plist + 服务端可覆盖）**

| 商品 ID | 授予的权益位 |
|---|---|
| `vip.monthly` | 全部 7 项 |
| `vip.yearly` | 全部 7 项 |
| `vip.lifetime` | 全部 7 项 |
| `addon.recipe`（未来） | 仅 `recipeFull` + `recipeCustom` |
| `ads.quarter`（可选，仿官方 ¥12.80 季卡） | 仅 `adsFree` |

**UI 侧的使用方式（唯一正确写法）**

```swift
// ✅ 正确：问权益位
if store.isUnlocked(.aiCoach) { showCoach() } else { showPaywall(.coach) }

// ❌ 错误：问「是不是会员」
if store.isVIP { showCoach() }
```

**服务端侧**：⑩ 篇定的 M 档服务端**不需要知道权益位** —— 因为 AI 用量墙是按「免费 3 次/日 · 会员 20 次/日」的**两档限额**执行，而这个额度由客户端在请求中携带的 `tier` 声明（`free` / `vip`）。
> **⚠️ 这里有一个安全权衡（必须明示）**：客户端声明的 `tier` **可被篡改**（越狱设备可以伪造 `vip` 来绕过限额）。
> **为什么可以接受**：① 篡改 `tier` 只能让攻击者多拿几次 AI 调用，**拿不到任何付费内容**（食谱等敏感内容如果走服务端，可由服务端校验）；② 全局熔断（⑩ 篇 §3.3）是最终兜底；③ **为这个场景上「服务端订阅校验」的复杂度，对个人开发者不划算**。
> **升级路径**：若 V1 发现被滥用，再引入 App Store Server API 做服务端校验（⑩ 篇 §3.5 的 L 档）。

### 1.3 StoreKit 2 实现细节（**8 个易错点**）

```swift
// ① 商品拉取（启动时 + 进入付费墙前各一次）
let products = try await Product.products(for: ["vip.monthly", "vip.yearly", "vip.lifetime"])

// ② 购买
let result = try await product.purchase()
```

| # | 易错点 | 正确做法 | 不做的后果 |
|---|---|---|---|
| **1** | **`Transaction.updates` 监听注册太晚** | **在 App 启动时（`App.init` 或首个 Scene 出现前）就启动监听 Task**，不能只在下单流程里 | 用户在**设置里取消订阅 / 家庭共享批准 / 跨设备续期**时，App 不知道 → 权益状态错乱 |
| **2** | **忘记 `finish()`** | 每笔 verified 交易处理后**必须 `await transaction.finish()`** | 每次启动重放同一笔交易（可能反复写库） |
| **3** | **不处理 `.pending`** | `.pending` = 等待家长批准 / 等待支付确认 → **必须提示用户「等待批准」**，不是失败 | 用户以为买失败了，重复购买 |
| **4** | **放过 `.unverified`** | `case .unverified` **必须拒绝并记日志** | 可能接受伪造交易（虽然难，但没理由不防） |
| **5** | **把权益判断写在 View 里** | 统一走 `EntitlementStore`（`@Observable`），**View 不直接读 StoreKit** | 状态分散，无法统一降级 |
| **6** | **没有「恢复购买」入口** | 会员中心必须有「恢复购买」按钮（`AppStore.sync()`） | **Apple 审核必拒** |
| **7** | **试用资格判断缺失** | 用 `product.subscription?.isEligibleForIntroOffer` 判断是否还能试用 | 老用户点试用无反应，用户困惑 |
| **8** | **权益缓存不做「先读缓存再刷新」** | 冷启动**先读本地缓存**（瞬时出 UI）→ 异步查 `currentEntitlements` 刷新 | 每次启动付费墙闪一下「未解锁」 |

**标准实现骨架**

```swift
@Observable
final class EntitlementStore {
    private(set) var active: Set<Entitlement> = []
    private var updatesTask: Task<Void, Never>?

    func bootstrap() async {
        await loadCached()                      // ① 先出 UI
        await refresh()                         // ② 再对齐权威
        updatesTask = Task.detached {           // ③ 启动即监听
            for await result in Transaction.updates {
                guard case .verified(let tx) = result else { continue }
                await self.apply(tx)
                await tx.finish()               // ④ 必须 finish
            }
        }
    }

    private func refresh() async {
        var fresh: Set<Entitlement> = []
        for await result in Transaction.currentEntitlements {
            guard case .verified(let tx) = result else { continue }
            guard tx.revocationDate == nil else { continue }     // ⑤ 退款/撤销
            fresh.formUnion(Entitlements.map(productID: tx.productID))
        }
        active = fresh
        await cache(fresh)
    }

    func isUnlocked(_ e: Entitlement) -> Bool { active.contains(e) }
}
```

### 1.4 试用与促销

| 手段 | 实现 | 建议 |
|---|---|---|
| **介绍性优惠**（免费试用 7 天 / 首期折扣） | App Store Connect 配置，客户端**无需代码**，仅需用 `isEligibleForIntroOffer` 控制文案 | **MVP 不做，V1 再上** —— 理由见下 |
| **促销优惠**（签名优惠码） | **需要服务端生成签名**（`SKPaymentQueue` 时代的遗留需求 → StoreKit 2 用 `Product.PurchaseOption.promotionalOffer`） | V2，且这是订阅服务端化的真实触发点之一 |
| **优惠码（Offer Code）** | App Store Connect 生成，用户手动兑换 | 适合内容分发（KOL 送码），**零成本** |

> **⚠️ 为什么 MVP 不做免费试用**：试用期需要**主动提醒用户「试用快结束了」**，否则必然产生「忘记取消 → 扣款 → 申请退款 → 差评」的链式反应。对个人开发者，**每一笔退款背后都是一次客服**（⑨ 篇指出上线后 30%–50% 时间被维护/客服吃掉）。**先做「直接付费」，等有精力做触达再做试用。**

### 1.5 付费墙的技术实现

**三类触发点**

| 类型 | 触发 | 示例 |
|---|---|---|
| **功能墙** | 用户主动点击会员功能 | 点「AI 营养师」→ 弹付费墙（`trigger=.coach`） |
| **体验墙** | 非会员遇到广告位替代 | 分析页底部预留广告位 → 显示「开通会员免广告」卡片 |
| **时机墙** | 完成高光动作后 | 首次达成目标 / 首次连续 7 天打卡后 |

**频次控制（防止骚扰，也是隐性审核风险点）**

```
本地记录：lastShownAt / shownCountToday / dismissedCount
规则：
  ① 同一天最多展示 2 次（功能墙不计数，用户主动点的必须展示）
  ② 时机墙：「连续 7 天打卡」这类高光时刻，每人只触发一次
  ③ 用户连续 2 次关闭 → 7 天内不再主动弹（只保留被动入口）
```

**A/B 变体（与配置中心联动）**

| 变体 | 差异 | 观测指标 |
|---|---|---|
| A（对照） | 三档平铺，年卡不特别高亮 | `paywall_shown → purchase_completed` |
| B | 年卡默认选中 + 「省 ¥56/年」标注 | 同上 + `product_id` 分布 |

> **实现**：`variant` 由服务端 `/v1/config` 下发（⑩ 篇 §3.2 的 M 档服务端），本地缓存，随埋点一起上报。

### 1.6 权益缓存、恢复与降级

**权益来源优先级（三层）**

```
① 实时：Transaction.currentEntitlements（权威）
② 缓存：本地 subscription 表（用于冷启动瞬时展示）
③ 默认：免费（无缓存且查询失败时）
```

**降级矩阵（必须实现的行为）**

| 场景 | 体验 | 数据处置 |
|---|---|---|
| 订阅到期 | 会员功能入口置灰 + 一句温和提示 | **用户自己保存的自定义食谱仍可见（只读）** ← M-1 规则 |
| 用户主动退款 | 同上（`revocationDate != nil`） | 同上 |
| 无网络 | 用缓存权益（保持已解锁状态） | 不受影响 |
| StoreKit 查询失败 | 用缓存权益，**不降级** | 不受影响 |
| 重装 App | `AppStore.sync()` 自动恢复（**基于 Apple ID，不需要我的账号体系**） | 数据从 CloudKit 拉回 |

> **★ 关键洞察**：**StoreKit 2 的 `currentEntitlements` 是基于 Apple ID 的** —— 所以**换设备、重装、家庭共享都能自动恢复权益，不需要我们自建账号体系**。这是「免登录 + 订阅制」能同时成立的底层原因（⑩ 篇 §2.6.4）。

### 1.7 风控

| 风险 | 机制 | 应对 | 等级 |
|---|---|---|---|
| **IAP 破解**（LocalIAPStore 等） | 伪造购买回调 | **StoreKit 2 天然免疫**：JWS 由 Apple 私钥签名，`case .verified` 在本地验签，无法伪造 | ✅ 已解决 |
| **退款套利**（买 → 用 → 退） | 端侧只能在 `sync` 时感知 `revocationDate` | MVP 端侧检查；**V1 加 S2S 通知做实时感知**（⑩ 篇 §3.5） | 中 |
| **家庭共享滥用** | 一个订阅多设备 | 接受（本就是 Apple 允许的形态）；用「AI 用量墙按 device 计」限制单设备滥用 | 低 |
| **越狱设备伪造 `tier`** | 绕过 AI 限额 | 见 §1.2 的权衡；全局熔断兜底 | 低 |
| **收据重放** | — | StoreKit 2 不存在此问题（无收据文件） | ✅ 已解决 |

> **结论**：**StoreKit 2 把「支付安全」这一整类问题从开发者身上拿走了。** 这是选 StoreKit 2 而非第三方支付 SDK 的核心理由（也满足 Apple 审核要求）。

### 1.8 价格、抽成与收入口径

| 档位 | 标价 | Apple 抽成（小企业 15%） | 实收 |
|---|---|---|---|
| 月卡 | **¥12.00** | **¥1.80** | **¥10.20/月** |
| 年卡 | **¥88.00** | **¥13.20** | **¥74.80/年** |
| 永久 | **¥168.00** | **¥25.20** | **¥142.80** |

**关于抽成**

| 情形 | 费率 | 说明 |
|---|---|---|
| 年收入 < **$100 万**（约 **¥710 万**） | **15%** | **App Store 小企业计划，需主动申请**【官方】 |
| 普通 | 30% | — |
| 订阅满 1 年后的续订 | 15% | 即使不在小企业计划也适用 |

> **行动项**：**App 上线前就申请小企业计划**（免费申请，通过后立即生效）。这是最多可省 **15% 收入**的一步，成本为零。

**年卡的单位经济（用于判断定价是否成立）**

```
年卡实收 ¥74.80/年
年成本 ≈ 分摊的 AI 调用（¥100–1,500/月 ÷ 付费用户数） + 云成本（¥0）
假设付费率 2%、1,000 用户 → 20 付费用户，年卡占 60% = 12 人
AI 月成本 ¥300（1,000 用户规模）÷ 12 人 ≈ ¥25/人/月 → ¥300/年
```

> **⚠️ 这里出现一个真实矛盾，必须指出**：若 AI 成本被少数重度用户吃满，**¥88/年的定价在重度用户上会亏损**。
> **解法（三选一，⑧ 篇已埋线）**：① 用量墙（免费 3 次/日、会员 20 次/日）；② 台词 24h 缓存（命中即零成本）；③ 模板兜底。
> **判据**：这不是「AI 太贵」的问题，是「**没有用量墙**的 AI 太贵」的问题 —— 与 ⑧ 篇的一票否决项一致。

### 1.9 会员中心页面规格（补齐 ⑧ 篇 P10）

## 二、数据统计技术方案

### 2.1 三层架构（**先穷尽 Apple 免费能力，再自建**）

```
┌─ L1 获客与转化 ────────────────────────────────────────────┐
│  App Store Connect · App Analytics      ¥0 · 零埋点         │
│  曝光 / 产品页浏览 / 下载 / 转化率 / D1·D7·D30 留存          │
│  订阅报告（订阅数·续订率·流失）· 渠道来源（Campaign 链接）    │
└────────────────────────────────────────────────────────────┘
┌─ L2 质量与性能 ────────────────────────────────────────────┐
│  MetricKit + Xcode Organizer            ¥0 · 零 SDK         │
│  崩溃 / 卡顿 / 启动时长 / 耗电 / 磁盘写入 / 自定义指标        │
└────────────────────────────────────────────────────────────┘
┌─ L3 产品行为 ──────────────────────────────────────────────┐
│  自建轻量埋点（复用 ⑩ 篇 M 档服务端）    ¥0（免费额度内）    │
│  约 20 个事件：记录/宠物/饮食/付费漏斗/小组件                 │
│  ⚠ 无 PII、无 IDFA、可关闭                                  │
└────────────────────────────────────────────────────────────┘
```

> **为什么要这样分层**：**L1 与 L2 是「不花钱就能拿到」的数据，很多人却用第三方 SDK 去重新采集一遍** —— 既增加包体、又要写隐私政策、还要处理数据出境合规。**先用满 Apple 给的，再自建缺的。**

### 2.2 指标体系（定义清楚才算「统计」）

**北极星指标（唯一）**

> **周记录天数（Weekly Logging Days, WLD）** —— 每周每用户产生体重记录的天数。
> **理由**：它同时刻画「频次」与「留存」，且**不依赖任何敏感数值**（只数天数，不看体重）。这与产品定位（「打开就记」）完全对齐。

**分层指标**

| 层 | 指标 | 口径 | 数据来源 |
|---|---|---|---|
| 获客 | 曝光 / 产品页浏览 / 下载量 / 下载转化率 | Apple 定义 | L1 |
| 激活 | **首日完成首次记录率**、Onboarding 完成率、跳过身高率 | 自定义 | L3 |
| 留存 | D1 / D7 / D30 | Apple 定义 | L1 |
| **参与** | **WLD（北极星）**、宠物互动次数/人、饮食记录率、**小组件点击打卡占比** | 自定义 | L3 |
| 变现 | 付费墙展示→购买转化率、ARPU、退款率、**试用转化率** | 组合 | L1 + L3 |
| 质量 | 崩溃率、启动时长 P90 | Apple 定义 | L2 |

> **⚠️ 口径纪律**：**每个指标必须写清楚「分母是什么」**。例如「饮食记录率」= 有饮食记录的天数 ÷ 有体重记录的天数？还是 ÷ 活跃天数？**不写清分母的指标会在三个月后变成无法解释的数字。**（`产品分析框架` 的口径陷阱）

### 2.3 事件设计规范

|---|---|---|
| `weight_value` / `bmi` / `kcal` | 个人敏感信息（PIPL 第 28 条） | `daily_count`（计数）/ 区间桶 |

### 2.4 上报机制

**架构：本地队列 → 批量 → 采样 → 单次请求**

```swift
actor TelemetryQueue {
    private var buffer: [Event] = []
    private let flushThreshold = 20        // 满 20 条
    private let flushInterval: TimeInterval = 30   // 或 30 秒
    private let sampleRate: Double = 1.0   // 高频事件可单独降采样

    func enqueue(_ e: Event) {
        buffer.append(e)
        if buffer.count >= flushThreshold { Task { await flush() } }
    }

    func flush() async {
        guard !buffer.isEmpty, isEnabled, hasConsent else { return }   // ← 尊重开关
        let batch = buffer.prefix(100)
        buffer.removeFirst(batch.count)
        do {
            try await api.post("/v1/telemetry", body: Batch(events: batch))
        } catch {
            persistOffline(batch)          // 失败落本地，下次启动重试
        }
    }
}
```

| 设计点 | 取值 | 理由 |
|---|---|---|
| 批量大小 | 20 条 / 100 条上限 | 减少请求数（成本） |
| 间隔 | 30 秒 + 退到后台时立即 flush | 平衡时效与耗电 |
| 离线 | 落本地队列，上限 500 条（FIFO 丢弃） | 防无限增长 |
| **降采样** | 高频事件（`pet_line_shown`）**采样 50%** | 控制请求量与存储 |
| 重试 | 指数退避，最多 3 次 | 防雪崩 |
| 请求头 | `X-App-Version` / `X-Session-Id` | 与 ⑩ 篇契约一致 |

**服务端处理（复用 M 档，不建数据库）**

```
POST /v1/telemetry   →  校验 App Attest token（可放宽）
                     →  写入日志服务（Cloudflare Analytics Engine / 腾讯云 CLS）
                     →  返回 204
❌ 不写数据库  ❌ 不关联用户  ✅ 仅事件流
```

> **⚠️ 「日志服务」算不算违反 B-1 纪律？** **不算，但要说清界限**：B-1 禁止的是**持久化用户数据（可关联到人的敏感信息）**。这里写入的是**无 PII 的匿名事件流**，且**不含任何体重/饮食/健康数值**。**界限就是 §2.3 的隐私红线表** —— 只要红线守住，事件日志与「用户数据库」是两个东西。
> **可核对性**：把这条写进隐私政策（「我们收集匿名的功能使用统计，用于改进产品，不包含您的体重与健康数据」）。

### 2.5 隐私合规

| 项 | 要求 | 实现 |
|---|---|---|
| **告知** | 隐私政策列明「收集哪些事件、用途」 | 明确写出事件类别（不啰嗦逐条） |
| **同意** | 首次启动的隐私弹窗**不强制勾选统计** | 统计为「非必要」，默认开启但可关（境内实践）或默认关闭需主动开（更保守） |
| **开关** | 设置页提供「分享使用数据」开关 | 关闭后 `TelemetryQueue.flush()` 直接 return（**立即生效，清空队列**） |
| **不追踪** | **不采集 IDFA、不做跨 App 追踪** | → **无需 ATT 弹窗**（关键收益） |
| **数据出境** | 若用境外日志服务，需评估 | 境内上架优先选境内日志服务（与 ⑩ 篇 §3.1 的选型一致） |
| **留存期** | 事件日志设 TTL（如 90 天） | 避免无期限累积 |

> **★ 关键决策：不做 ATT = 不弹窗 = 不损失转化。** iOS 的 ATT 弹窗会让相当比例的用户关闭追踪，且弹窗本身是首启体验的噪音。**个人开发者的分发靠 ASO + 内容，不靠广告投放 → 完全不需要 IDFA → 完全不需要 ATT → 少一个弹窗。**

### 2.6 渠道归因（**无需 IDFA 的方案**）

**方案：App Store Campaign 链接（官方免费）**

```
https://apps.apple.com/app/id<APP_ID>?pt=<PROVIDER_TOKEN>&ct=<CAMPAIGN_NAME>

示例：
小红书     → ?pt=12345678&ct=xiaohongshu_2026q4
少数派     → ?pt=12345678&ct=sspai_article
即刻       → ?pt=12345678&ct=jike_post
```

- **`pt` / `ct` 是 Apple 官方支持的归因参数**，数据直接出现在 **App Analytics → 来源** 报表里。
- **零 SDK、零成本、无隐私问题**（Apple 侧聚合，不暴露到个人）。
- 配合 ⑨ 篇 §1.2 的「内容分发」策略：**每篇内容带一个专属 `ct`**，就能知道哪个渠道真的带来下载。

> **这解决了「没有 IDFA 怎么做渠道归因」的疑虑** —— 对「ASO + 内容」的分发模型，**Apple 官方的 Campaign 链接已经够用**，不需要第三方归因 SDK。

### 2.7 看板与成本

| 看板 | 工具 | 成本 | 内容 |
|---|---|---|---|
| 获客与变现 | **App Store Connect**（网页 + App） | **¥0** | 曝光/下载/留存/订阅趋势 |
| 质量 | **Xcode Organizer** | **¥0** | 崩溃/卡顿/启动/耗电 |
| 产品行为 | 日志服务 SQL 查询 → 导出 CSV → 表格工具 | **¥0**（免费额度） | 事件计数、漏斗、活跃 |
| 北极星 | 每周手工算一次（或脚本） | **¥0** | WLD |

> **诚实提示**：自建埋点的代价不是钱，是**「没有开箱即用的漏斗/留存图」** —— 需要自己写查询。**对个人开发者，这反而是可接受的**：因为每周真正要看的指标不超过 10 个，**看板越简单越会被真的看**。

### 2.8 与用户数据的边界（B-1 纪律的最终裁定）

| 问题 | 裁定 |
|---|---|
| 体重数据能上报吗？ | ❌ 不能。留在设备 + CloudKit |
| 「记录了几次」能上报吗？ | ✅ 能（计数） |
| 掉秤幅度能上报吗？ | ⚠️ 只能传**区间桶**（`down_big/down_small/flat/up`） |
| 用哪一档断食能上报吗？ | ✅ 能（模式是枚举，非健康数值） |
| 用户点的哪个食谱能上报吗？ | ⚠️ 传 `plan_index`（序号），**不传食谱名** |
| 崩溃日志能上报吗？ | ✅ 能（MetricKit，Apple 已做去标识） |
| AI 请求失败能上报吗？ | ✅ 能（只传 `route` + `error_code`，**不传请求内容**） |

> **一句话总结这条边界**：**「行为」可以统计，「内容」不可以。** 前者用于改进产品，后者属于用户的隐私。

## 三、配置中心（`等层面`的延伸）

会员体系与数据统计都依赖一个共同能力：**不改 App 就能调整线上行为**。用 ⑩ 篇 M 档服务端的一个路由即可。

```
GET /v1/config      （强缓存 + ETag + 本地兜底）

{
  "config_version": 7,
  "paywall": { "variant": "B", "max_shows_per_day": 2, "cooldown_days": 7 },
  "quota":   { "free_per_day": 3, "vip_per_day": 20, "global_daily_cap": 2000 },
  "telemetry": { "enabled": true, "sample": { "pet_line_shown": 0.5 } },
  "feature_flags": { "ai_vision": false, "recipe_custom": true, "trial_offer": false },
  "min_app_version": "1.0.0"
}
```

| 用途 | 解决什么 |
|---|---|
| 付费墙变体 | A/B 测试**不发版** |
| AI 用量墙阈值 | 成本失控时**立即调低**（不用等审核） |
| 功能开关 | 新功能**灰度发布**（`feature_flags`） |
| 埋点采样率 | 请求量突增时降采样 |
| `min_app_version` | 协议不兼容时强制升级 |

**纪律**：配置下发**必须有本地缓存 + 兜底默认值**，服务端不可用时**用上次缓存**（不能因为配置拉不到就白屏）。

## 附 B · 测算过程与敏感度（与实测严格分开）

### B.1 抽成与实收

- **假设**：通过 App Store 小企业计划（15%）。
- **推算**：
```
月卡：¥12.00 × (1 − 0.15) = ¥10.20
年卡：¥88.00 × (1 − 0.15) = ¥74.80
永久：¥168.00 × (1 − 0.15) = ¥142.80
```
- **结果**：见附 A。
- **置信度**：**高**（费率与定价均为官方公开值）
- **敏感度**：若未申请小企业计划（30%）→ 年卡实收 **¥61.60**，**减少 ¥13.20/年（−17.6%）** → **不改变商业模式成立性，但直接少赚近 1/5** → **申请小企业计划是高优先级动作**。

### B.2 年卡单位经济（AI 成本分摊）

- **假设**：1,000 用户；付费率 **2%**（⑧/⑨ 篇口径）；年卡占付费用户 60%；AI 月成本 ¥300（1,000 用户规模）。
- **推算**：
```
付费用户      = 1,000 × 2% = 20 人
年卡用户      = 20 × 60% = 12 人
AI 月成本     = ¥300
全量分摊      = ¥300 ÷ 20 = ¥15.00/人/月 → ¥180.00/人/年
仅年卡分摊    = ¥300 ÷ 12 = ¥25.00/人/月 → ¥300.00/人/年
年卡实收      = ¥74.80/年
```
- **结果**：**年卡实收 ¥74.80 < 全量分摊成本 ¥180.00** → **表观亏损**
- **⚠️ 但这个结论是错的，错在假设**：上式假设「所有 AI 成本由付费用户承担」，而实际是**免费用户也贡献 AI 成本，且成本被用量墙封顶**。
  **修正算法（按用量墙封顶）**：
```
免费用户：3 次/日 × 30 天 = 90 次/月（但实际使用率 << 100%）
会员用户：20 次/日 × 30 天 = 600 次/月上限
以 ⑨ 篇口径：单次 ≈ ¥0.01 → 会员上限 = ¥6.00/月 = ¥72.00/年
年卡实收 ¥74.80 − 上限成本 ¥72.00 = ¥2.80/年  ← 仍然极薄
```
- **结论（重要）**：**年卡 ¥88 在「会员把限额用满」的极端情形下几乎没有毛利。** 因此：
  - **用量墙必须真的生效**（不能形成虚设）；
  - **AI 成本必须靠缓存与模板兜底压到远低于上限**（⑨ 篇 K-4）；
  - **若 V1 发现重度用户吃满，应下调会员限额或改用「按次包」**。
- **置信度**：**低–中**（付费率、调用量、单次成本均为假设）
- **敏感度**：单次成本 ¥0.003（而非 ¥0.01）→ 年卡上限成本降至 **¥21.60/年**，**毛利转正且健康** → **结论对「单次成本」高度敏感** ⇒ **应把「实测单次 token 成本」列为最高优先级待查项**（附 C #1）。

### B.3 埋点成本（是否违反 B-1 的判定）

- **命题**：埋点上报是否违反「服务端不存用户数据」纪律？
- **判定过程**：
```
若上报 = 用户数据（体重/饮食/健康数值）  → 违反 ❌
若上报 = 匿名行为事件（计数/枚举/布尔）  → 不违反 ✅
依据：B-1 禁止「持久化可关联到人的敏感信息」，而非「一切日志」
```
- **结果**：**不违反，但以 §2.3 的隐私红线表为硬边界**。
- **置信度**：中（口径判断，最终需法务确认）
- **风险边界**：一旦把 `weight_value` 混进事件 → **立即从不违反变为违规** → 因此**服务端必须做事件 schema 白名单校验（拒绝未知字段）**，这从「开发自觉」变为「技术强制」。
