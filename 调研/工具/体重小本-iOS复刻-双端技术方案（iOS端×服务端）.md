## 〇、结论先行（TL;DR）

> ## **技术方案必须分两端看 —— 不是因为「有服务端要用」，而是因为两端的约束条件根本不同：iOS 端的边界是「系统能力 + 审核」，服务端的边界是「Key 安全 + 边际成本」。⑨ 篇把两者混在一张表里，掩盖了一个必炸的坑。**

**1｜【修正性结论】⑨ 篇的「不写后端」需要改成「不自建后端基础设施」。**
- **问题**：⑨ 篇 §3.4 把「LLM API」列在客户端运行成本里，技术栈清单里 AI 一栏直接写「国产低价 LLM API」。**但 iOS 客户端调用第三方 API 必须携带 API Key，而 App 二进制里的字符串是可被提取的**（`strings` 命令 / 抓包 / 越狱设备）。
- **后果**：Key 泄露 → 被爬虫盗刷 → **账单无上限**。这不是「可能」，是**上线后必然发生的时序问题**（行业惯例：公开 App 内嵌 Key 的中位存活期以天计）。
- **修正**：**LLM 调用必须经过一个极薄的服务端代理（BFF）**。它不存用户数据、不做业务逻辑，只做三件事：**保管 Key / 计量用量 / 转发请求**。
- **一句话结论**：**「零后端」在「纯记录工具」上成立；一旦引入云 AI，就必须有一个最小后端 —— 代价约 ¥0–¥36/月，不是可选项，是安全性要求。**

**2｜服务端分四档，本方案推荐 M 档（一个 Edge Function）。**

| 档 | 形态 | 服务端职责 | 适用 | 增量成本 |
|---|---|---|---|---|
| **S** | 无服务端 | 无 | 极简 MVP（无 AI，对应 ⑨ 篇 §6.2 的 C2 路线） | **¥0** |
| **M** ✅ | 1 个 Serverless 函数 | AI 代理 + 用量墙 + 内容分发 | **A 档完整 MVP / V1** | **¥0–¥36/月** |
| **L** | Serverless + 数据库 | + 订阅 S2S 通知 + 遥测 + CMS | 有内容运营 / 多端计划 | ¥100–¥500/月 |
| **XL** | 自建容器 + DB + 运维 | 全量 | 团队产品 | ¥11.5 万–24.3 万/月【前序测算】 |

**3｜用户数据 100% 留在 CloudKit，服务端不碰。** 这条边界同时解决三件事：**零存储成本**（数据占用用户 iCloud 空间，非开发者配额）、**零备案风险**（服务端不落库个人信息）、**合规等级最低**（PIPL 下「不存储」比「加密存储」的责任轻一个量级）。

**4｜订阅校验在 MVP 阶段可以完全端侧完成。** StoreKit 2 的 `Transaction` 已由 Apple 私钥签名（JWS），**设备本地即可验证签名链**，无需服务端。只有「退款 / 撤销的实时同步」才需要 App Store Server Notifications V2（归入 L 档，V1 引入）。

**5｜两端各有一个「必踩的坑」，本文已给规避方案。**
- **iOS 端**：**Live Activity 有 8 小时活跃上限** —— 而轻断食最高档是 23:1（23 小时）。**18:6 以上档位会超限被系统回收**（⑨ 篇未覆盖此点，见 §2.6.2）。
- **服务端**：**App 备案与服务端选址强耦合** —— 境内上架需备案，而备案要求填写服务器位置。**选境外 Serverless（Cloudflare / Vercel）会让备案卡住**（见 §3.1）。

## 一、两端职责划分（先定边界，再谈技术）

### 1.1 能力归属决策表

> **判据**：一个能力放端侧还是服务端，看四个问题 —— ① 是否离线可用？② 数据是否敏感？③ 是否高频变更？④ **是否持有密钥或成本？**

| 能力 | 归属 | 判据 | 理由 |
|---|---|---|---|
| 体重记录 / 趋势分析 / BMI | **端侧** | 离线 + 敏感 + 高频 | 核心链路，断网也必须能用 |
| 数据存储与跨设备同步 | **端侧（CloudKit）** | 敏感 | 开发者不接触数据，合规负担最低 |
| 健康数据互通 | **端侧（HealthKit）** | 敏感 + 系统权限 | 必须走系统授权，不落第三方 |
| 桌面小组件 / 实时活动 | **端侧（WidgetKit / ActivityKit）** | 系统能力 | 无服务端替代方案 |
| 语音打卡（ASR） | **端侧（Speech）** | 敏感 + 成本 | 本地识别，音频不上传 |
| 订阅购买与权益校验 | **端侧（StoreKit 2）** | 系统能力 | JWS 本地可验签 |
| 订阅退款 / 撤销实时同步 | **服务端**（L 档） | 需服务端接收 | 需 App Store Server Notifications |
| 食物库（1,700 条基础库） | **端侧（SQLite）** | 离线搜索 | 打包进包，保证离线搜 |
| 食物库热更 / 食谱内容（88 套） | **服务端**（M 档） | **高频变更** | 避免「改一条食谱就要发版」 |
| **AI 台词 / 营养师 / 拍照识别** | **服务端**（M 档） | **持有密钥 + 有成本** | **Key 不能进客户端；用量墙必须服务端** |
| 推送提醒 | **端侧（本地通知）+ CloudKit 订阅** | 避免自建 | `UNUserNotificationCenter` + `CKSubscription` 均由 Apple 服务器代发 |
| 社区 / UGC 共享 | **不做** | 见 §八 | ⑧ PRD 已砍 |

### 1.2 边界图

```
┌─────────────────────────── iOS 端（App + 3 个 Extension） ───────────────────────────┐
│                                                                                      │
│   SwiftUI Views ──► @Observable Store ──► Services（领域层，纯函数）                  │
│                                              │                                       │
│              ┌───────────────────────────────┼───────────────────────────────┐       │
│              ▼                               ▼                               ▼       │
│      SwiftData（本地主库）            SystemBridge                  AIClient（薄）   │
│              │                    Widget / Activity / Health              │       │
│              │                    Speech / StoreKit 2 / LocalNotification │       │
│              │                                                            │       │
└──────────────┼────────────────────────────────────────────────────────────┼───────┘
               │ CloudKit 私有库（Apple 托管）                                │ HTTPS
               ▼                                                            ▼
      ┌──────────────────┐                                    ┌──────────────────────┐
      │  Apple 托管服务   │                                    │  服务端（M 档）       │
      │  CloudKit / APNs  │                                    │  1 个 Edge Function   │
      │  StoreKit 服务    │                                    │  ├ AI 代理 + 用量墙   │
      │  ⚠ 不存开发者数据 │                                    │  ├ 内容分发（版本化） │
      └──────────────────┘                                    │  └ LLM API Key 保管   │
               ▲                                              │  ⚠ 不存用户数据       │
               └────────────── 用户数据不经过服务端 ───────────└──────────────────────┘
```

> **看图要点**：**中间那条竖线（用户数据）和服务端之间没有连线** —— 这是刻意的。用户数据只走 CloudKit，服务端只处理「无状态的 AI 请求」与「静态内容」。**这个边界一旦守住，服务端就从「数据库 + 运维」退化成「一个函数」，成本与合规同时归零。**

### 1.3 三条边界纪律（写进代码 review 清单）

| # | 纪律 | 违反后果 | 检查方式 |
|---|---|---|---|
| **B-1** | **服务端不得持久化任何用户数据**（体重 / 饮食 / 健康 / 照片） | 从「不落库」变成「落库」→ 备案 + PIA + 泄露责任全上线 | 服务端代码里**不允许出现 DB 写入**；只允许 KV 计数（匿名 device_id + 日期） |
| **B-2** | **客户端不得内嵌任何第三方 API Key** | 被盗刷，账单无上限 | CI 里加密钥扫描（gitleaks / trufflehog），命中即构建失败 |
| **B-3** | **AI 能力必须可降级**（缓存 / 模板 / 隐藏） | 服务端故障 = 核心功能不可用 | 每个 AI 调用点必须有一条不依赖网络的 fallback 路径 |

### 2.3 架构分层与并发模型

**数据流（单向，禁止双向绑定回写）**

```
用户操作 → View ──intent──► @Observable Store ──call──► Service（纯函数/actor）
                                 ▲                          │
                                 └──────── 结果 + 事件 ──────┘
```

**并发模型（Swift Concurrency，最容易出错的地方）**

| 层 | 隔离方式 | 规则 |
|---|---|---|
| View / Store | `@MainActor` | UI 状态只在主线程改；`@Observable` 类默认 MainActor |
| Service | `actor` 或纯函数 | 无状态计算用纯函数（可单测）；有缓存用 `actor` |
| 数据层 | **`@ModelActor`** | ⚠ **`ModelContext` 不是 Sendable**，跨线程必须用 `@ModelActor` 隔离，**禁止把 `Model` 对象跨 actor 传递**（只传 `PersistentIdentifier` 或值类型 DTO） |
| 网络 | `async/await` + `URLSession` | 所有请求必须带超时；不阻塞主线程 |

> **⚠ 最高频的坑**：把 SwiftData 的 `@Model` 对象直接传给后台任务 → 崩溃或数据竞争。**正确做法**：Model → DTO（`struct`，Sendable）→ 后台处理 → 回来按 `PersistentIdentifier` 重新 fetch。

**依赖注入**：用 `Environment` + 构造函数注入（**不引第三方 DI 框架**）。所有 Service 走 protocol，便于测试替身（例如 `AIClientProtocol` 的 mock 版本）。

### 2.4 数据层实现（SwiftData + CloudKit）

**ModelContainer 配置**

| 场景 | 配置 | 说明 |
|---|---|---|
| 主 App | `ModelConfiguration(cloudKitDatabase: .private("iCloud.com.xxx.weightbook"))` | 私有库，跨设备自动同步 |
| Widget | **App Group 共享容器（只读）** | `ModelConfiguration(groupContainer: .identifier("group.xxx"))` |
| 首次启动 | 无 iCloud 账号时自动降级为纯本地 | **必须有这条分支，否则崩溃**（⑨ 篇 G2 验收项） |

**⚠ App Group 共享的技术选型（⑨ 篇 K-5 的补充）**

⑨ 篇原方案是「小组件经 App Group 的 UserDefaults 读快照」。**这里给一个更优解 + 一个降级路径**：

| 方案 | 做法 | 优点 | 风险 |
|---|---|---|---|
| **A（首选）** | SwiftData 的 `ModelConfiguration(groupContainer:)` 让 Widget 直接读共享容器 | 数据始终一致，无需桥接 | **CloudKit 同步 + 多进程访问有已知冲突风险**【待实测】 |
| **B（降级）** | 主 App 在每次数据变更后，把「今日 + 本周」摘要写入 App Group `UserDefaults` | 零风险、实现简单 | 只读快照，非完整数据（但小组件本就只需要摘要） |

**决策规则**：先用 A 做 PoC（0.5 人日）；**若出现同步异常或 Widget 读不到数据，立即切 B**，不要在 A 上纠缠超过 1 人日（对应 ⑨ 篇 R2 风险）。

**9 张表的端侧落地**（模型定义照 ⑧ PRD §6.2，此处只补实现约束）

| 表 | 端侧实现要点 |
|---|---|
| `user` | **单行表**（App 只有 1 个用户）；`unit_pref` / `decimal_pref` 存 UserDefaults 副本供 Widget 读 |
| `weight_record` | 索引 `(measured_at)`；**单位只存 kg**（⑨ 篇 K-1 纪律） |
| `food` | 1,700 条种子数据 → 首次启动**批量导入**（须放后台 + 进度提示）；`alias` 建 FTS 索引或内存前缀索引 |
| `meal_record` / `meal_item` | `UNIQUE(user_id, date, meal_type)`；`food_name` **必须冗余存储**（防食物库热更后历史记录变样） |
| `water_record` / `fasting_record` | 轻量，直接 SwiftData |
| `recipe_plan` / `recipe` / `recipe_meal` | **服务端下发内容，端侧只缓存**（见 §3.4）；带 `content_version` 字段用于增量更新 |
| `pet` / `pet_event_log` | `pet_event_log` 是「它记得」的数据基础；**建议加保留期**（如只留 90 天）避免无限增长 |
| `subscription` | 端侧缓存权益；**权威来源是 StoreKit 2，不是这张表**（表只是缓存，可随时重建） |

**食物库的端侧形态（关键决策）**

- **打包形态**：预置 SQLite 文件随包发布（不解析 JSON 建库，省首次启动时间），首次启动**直接复制**到 App 目录。
- **热更形态**：服务端下发增量 patch（新增 / 修改条目），端侧合并进本地库。**MVP 可不做热更**（V1 再加），但**表结构要预留 `source` / `updated_at` 字段**，否则以后没法做增量。

### 2.5 网络层（AIClient 的定位）

**网络层只做一件事**：调服务端的 AI 代理与内容接口。**不直连任何第三方服务。**

```
AIClient（协议层）
 ├─ generatePetLine(context) -> String        // 台词，带缓存
 ├─ askNutritionist(question) -> String       // 营养师（V1）
 ├─ recognizeFood(imageData) -> [FoodGuess]   // 拍照识别（V1）
 └─ fetchContentManifest() -> Manifest        // 内容版本清单
```

**必备实现细节**

| 项 | 要求 | 理由 |
|---|---|---|
| 超时 | 台词 3s / 营养师 15s / 识别 20s | 超过即走 fallback，不让用户等 |
| 重试 | 仅对 5xx 与超时重试 1 次（指数退避） | 4xx 重试无意义 |
| 缓存 | 台词 `NSCache` + 磁盘，键 = `场景+日期` | 命中即不请求（⑨ 篇 K-4 成本控制） |
| 幂等 | 请求带 `X-Request-Id`（UUID） | 服务端据此去重，防止重试双计数 |
| **降级** | 网络失败 → 模板池 / 隐藏入口 | **B-3 纪律的落地点** |
| 无 Key | **客户端二进制内不含任何 LLM Key** | B-2 |

### 2.6 系统集成实现要点（⑨ 篇 K-5 的下钻）

#### 2.6.1 桌面小组件

| 项 | 实现 |
|---|---|
| 尺寸 | Small（今日体重 + 打卡按钮）/ Medium（+ 本周迷你柱图）/ Lock Screen（单数值） |
| 刷新 | `TimelineProvider` 每 30min 一条 entry；**主 App 数据变更后主动 `WidgetCenter.shared.reloadAllTimelines()`** |
| 一键打卡 | `AppIntent`（iOS 17）；**在 Widget 进程内写完 → 尝试落共享容器或写 App Group 队列，主 App 启动时消费队列** |
| ⚠ 坑 | Widget **不能弹 UI**，录入需要数值 → **一键打卡只做「用上次值 + 当前时间快速记一条」**，复杂录入跳主 App |

#### 2.6.2 实时活动（**本方案最重要的技术风险点**）

**⚠️ 系统硬限制（⑨ 篇未覆盖）**：iOS 对 Live Activity 有**活跃时长上限（约 8 小时）**，超时后系统会结束它；结束后还会在锁屏保留一段时间，然后移除。

**这与轻断食档位直接冲突**：

| 断食档位 | 时长 | 是否超 Live Activity 上限 | 处置 |
|---|---|---|---|
| 12:12 | 12h | **超**（12 > 8） | 见下方策略 |
| 14:10 | 10h | **超** | |
| 16:8 | 8h | **临界** | |
| 18:6 | 6h | 不超 ✅ | 正常使用 |
| 20:4 | 4h | 不超 ✅ | |
| 23:1 | 1h | 不超 ✅ | |

> **注意方向**：断食的**时长**从 12h（12:12，禁食 12 小时）到 1h（23:1，禁食 1 小时）—— **越是「温和档位」，禁食时长越长，越容易超限**。这与直觉相反。

**处置策略（三选一，建议组合）**

| 策略 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **① 分段续期** | 在活动进行到约 7 小时时，主 App **不能**自动续（无后台执行保证）→ 改为**依赖用户再次打开 App 时重建** | 简单 | 不打开就断 |
| **② 降级为本地通知** | 长档位（12:12 / 14:10）**不启动 Live Activity**，改用本地通知在关键节点提醒 | 100% 可靠 | 失去锁屏常驻 |
| **③ 接受系统回收** | 让它被回收，锁屏以「活动已结束」呈现 | 零成本 | 体验断裂 |

> **建议**：**默认全档位都尝试启动 Live Activity（保体验），同时在 8 小时节点排一条本地通知兜底**（「你的禁食已完成，记得来打卡结束」）。**这需要把系统限制写进产品文案预期**（不要让用户以为锁屏会一直亮着）。
> **待核**：确切的小时数上限与 iOS 版本差异需在真机验证【待核·官方文档】。

#### 2.6.3 HealthKit

| 项 | 实现 |
|---|---|
| 写入 | `HKQuantityType(.bodyMass)`，单位 `.gramUnit(with: .kilo)` |
| 读取 | 需 `NSHealthShareUsageDescription`；**读取他人数据需逐项授权** |
| 授权 | **首次引导页要解释「为什么需要」**；被拒后**不得反复弹窗**，改为设置页常驻入口 |
| 权限声明 | `PrivacyInfo.xcprivacy` 必须声明访问理由（审核常见拒审点，⑨ 篇 R3） |
| 冲突 | HealthKit 与 App 内的记录可能重复 → **按 `measured_at` + 来源去重**（App 内记录优先生效） |

#### 2.6.4 StoreKit 2（端侧完成权益校验）

```
购买：Product.purchase() → 得到 VerificationResult<Transaction>
     → switch .verified(let tx) → 读 tx.expirationDate / tx.revocationDate
     → 写 subscription 缓存表 → 广播权益变更
恢复：AppStore.sync() → 遍历 Transaction.currentEntitlements
权益：SubscriptionService.isVIP（读缓存，冷启动异步刷新）
退款：查 tx.revocationDate != nil → 视为失效（端侧只能在 sync 时感知）
```

> **关键点**：`.verified` 表示 StoreKit **已在设备本地完成 Apple 签名链校验**，无需自建服务端验证。**这就是「MVP 不需要订阅服务端」的技术依据。**
> **红线**：`weight_record` 与趋势图的读取路径上**不得出现任何 `SubscriptionService` 调用**（⑧ PRD 红线 #2）。

#### 2.6.5 本地通知 + CloudKit 订阅（零推送服务端）

| 场景 | 实现 |
|---|---|
| 断食结束提醒 | `UNTimeIntervalNotificationTrigger`（本地，无需服务端） |
| 断更提醒（>3 天） | 本地通知，按「上次记录时间 + 72h」排期 |
| 跨设备提醒 | `CKSubscription` 静默推送（**由 Apple 服务器发出，无需自建推送服务端**） |

> **结论**：**推送不需要服务端**。这消除了个人开发者最常见的「我是不是还得搞个推送服务」的顾虑。

## 三、服务端技术方案

### 3.0 先回答：到底要不要服务端

> **判据**：**只要「有云 AI 功能」或「有需要热更的内容」，就必须要服务端。二者皆无 → 真的可以零后端。**

| 你的路线 | 有无云 AI | 有无热更内容 | 需要服务端？ | 档位 |
|---|---|---|---|---|
| 极简 MVP（⑨ 篇 §6.2，C2 路线） | ❌ 无（宠物用纯模板） | ❌ 无（食物库不需要，食谱砍掉） | **不需要** | **S** |
| A 档完整 MVP（⑨ 篇 §四） | ✅ 宠物台词 | ✅ 食谱内容 | **需要（最小）** | **M** |
| V1（+ 营养师 + 拍照识别） | ✅✅ 高频 AI | ✅ | 需要（+ 监控） | **M/L** |
| 有多端 / 内容运营计划 | ✅ | ✅ | 需要（完整） | **L** |

**本方案推荐：M 档起步，架构上预留 L 档。**

### 3.1 技术选型对比（**含一个决定性的合规约束**）

| 方案 | 类型 | 免费额度 | 付费 | 备案影响 | 结论 |
|---|---|---|---|---|---|
| **腾讯云函数 SCF** | 境内 Serverless | 100 万次/月 | 约 ¥1.33/GBs | ✅ **利于备案** | ✅ **境内上架首选** |
| **腾讯云开发 CloudBase** | 境内 BaaS | 有基础额度 | 约 ¥19.90/月起 | ✅ | 若还需数据库/存储可选 |
| **阿里云函数计算 FC** | 境内 Serverless | 有免费额度 | 按量 | ✅ | 与腾讯云等价，看熟悉度 |
| **Cloudflare Workers** | 境外 Edge | **10 万次/日** | $5/月（**¥35.50/月**） | ⚠ **可能阻碍备案** | 出海首选，境内慎用 |
| **Vercel / Netlify Edge** | 境外 Edge | 较宽松 | $20/月（**¥142.00/月**） | ⚠ 同上 | 同上 |
| **Supabase** | 境外 BaaS | 有免费版 | $25/月（**¥177.50/月**） | ⚠ 同上 | **本方案不需要数据库 → 不必选** |

> **⚠️ 【关键约束】备案 × 服务端选址（⑨ 篇未覆盖）**
> 境内 App Store 上架的 App 需完成 **App 备案**（工信部，2023 年起强制），备案**需填报服务器信息**。**若服务端为纯境外 Serverless，备案流程会受阻或需要额外说明。**
> **因此本方案的推荐路径是**：
> - **计划境内上架** → 服务端选**境内 Serverless**（腾讯云函数 / 阿里云 FC）→ 备案顺畅，成本相当。
> - **先出海（美区 / 港区）** → Cloudflare Workers 可用，开发体验最好，免费额度最大。
> **⚠️ 本条为合规判断，具体口径需以当季备案要求为准【待核】，不构成法律建议。**

                    │  POST /v1/ai/line         ← 宠物台词（带缓存头 + 用量墙）    │

### 3.3 职责一：AI 代理与用量墙

**为什么必须服务端（三条不可替代的理由）**

| # | 理由 | 不做会怎样 |
|---|---|---|
| 1 | **Key 保管** | 客户端内嵌 Key → `strings` 可提取 → 盗刷 |
| 2 | **用量墙** | 客户端计数可被绕过（改系统时间 / 重装 / 改包） |
| 3 | **Prompt 与模型版本控制** | 放客户端 → 调优需发版审核（1–3 天）；放服务端 → 改完即生效 |

**用量墙设计（服务端强制）**

```
键：  usage:{device_hash}:{yyyymmdd}     值：调用次数         TTL：48h
限额（建议，可配）：免费 3 次/日 ｜ 会员 20 次/日 ｜ 全局熔断 2000 次/日

请求到达：
  1. 校验 App Attest token → 得 device_hash
  2. INCR 当前计数
  3. if count > 限额 → 429 + { fallback: true }   ← 客户端据此切模板池
  4. 转发 LLM（带超时 3s + 上游 5xx 重试 1 次）
  5. 记录 token 消耗（用于成本监控），返回
```

| 设计点 | 说明 |
|---|---|
| **device_hash** | `SHA256(App Attest keyId + 服务端 salt)` —— **不可逆，不构成个人信息**，符合 B-1 纪律 |
| **全局熔断** | 防「云函数被刷爆」的兜底：日调用超阈值直接返回 fallback，**保护账单** |
| **失败也计数？** | ✅ 计数（防重试放大），但**上游失败返回 `fallback: true` 而非报错** |
| **缓存命中不回源** | 客户端命中缓存时不发请求，服务端请求量自然下降 |

**Prompt 托管**：Prompt 模板存服务端配置（环境变量或 KV），**不下发到客户端**。这样调优、A/B、切换模型都无需发版。

### 3.4 职责二：内容分发（食谱库 + 食物库热更）

**为什么要放服务端**：⑧ PRD 的食谱内容有 **17 个方案 / 88 套食谱**，且**会持续调整**。打包进 App 意味着「改一条食谱 = 发版 + 审核」，**迭代速度被审核周期锁死**。

**版本化内容协议**

```
GET /v1/content/manifest
{
  "content_version": 12,
  "updated_at": "2026-10-15T10:00:00Z",
  "recipes": { "url": ".../recipes.json", "etag": "abc123", "bytes": 184320 },
  "food_patch": { "from": 11, "url": ".../food_patch_12.json", "bytes": 4096 },
  "min_app_version": "1.0.0"
}
```

| 设计点 | 说明 |
|---|---|
| **强缓存** | 内容走 CDN，`Cache-Control: public, max-age=86400` + ETag → **服务端实际请求量极低** |
| **端侧策略** | 冷启动异步拉 manifest；`content_version > 本地` 才下载；**失败就用本地缓存，绝不阻塞 UI** |
| **食物库增量** | 基础 1,700 条随包（保离线），**新增条目走 patch**（不重新下全量） |
| **内容与主线解耦** | 食谱内容**可完全由 AI 生成 + 人工校验后上传**（⑨ 篇 T4.4），无需改客户端代码 |
| **兜底** | 服务端挂了 → 客户端用本地缓存的上一版内容，**功能不中断** |

### 3.5 职责三：订阅服务端校验（V1，归 L 档）

**MVP 不需要**（§2.6.4 已论证：StoreKit 2 本地验签足够）。**V1 引入的原因只有一个：实时感知退款 / 撤销。**

```
App Store Server Notifications V2 → POST /v1/appstore/notify
  事件类型：DID_RENEW / EXPIRED / REFUND / REVOKE / GRACE_PERIOD_EXPIRED
  处理：验签（Apple 根证书）→ 维护「已退款 device / 交易号」黑名单（KV，非用户表）
  用途：① 拒绝对已退款用户提供 AI 服务  ② 防「买 → 退款 → 继续用」套利
```

> **注意 B-1 纪律**：这里**只存交易号黑名单，不存用户身份与订阅画像**。交易号可关联到人 → 因此**必须标注为「不含其他个人信息的独立凭证」，并在隐私政策中列为「为实现交易安全所必需」**【待法务确认】。

### 3.6 鉴权与防滥用

| 层 | 机制 | 目的 |
|---|---|---|
| **身份** | App Attest（`DCAppAttestService.attestKey` → 服务端调 Apple 校验 → 签发 device token） | 证明请求来自**正版、未被篡改**的 App |
| **凭证** | device token 短期有效（如 24h）+ 服务端签名 | 防伪造请求 |
| **传输** | HTTPS + 证书固定（`URLSessionDelegate` 做 pinning，可选） | 防中间人 |
| **频控** | 用量墙 + 全局熔断（§3.3） | 保护成本 |
| **降级路径** | App Attest 不可用（越狱设备 / 模拟器）→ 降级为「设备标识 + 更低限额」 | **不粗暴拒绝，只降权** |

> **⚠ 注意**：App Attest **不是万能的**（有设备限制、有 rate limit）。它的作用是**把盗刷成本从「复制一个 Key」提高到「逆向并伪造 attestation」** —— 这已经足够让 99% 的脚本小子转向别处。**不要为它投入过多工时（建议 ≤1 人日）。**

### 3.7 服务端数据与合规边界

| 项 | 承诺 | 落实方式 |
|---|---|---|
| 用户数据 | **不落库** | 服务端无 DB，只有 KV 匿名计数（TTL 48h） |
| AI 请求内容 | **不留存**（透传） | 关闭上游供应商的「训练用数据」开关；服务端不做请求体持久化 |
| 日志 | **不记请求体**，只记 `请求ID / 路由 / 状态码 / 耗时 / token 数` | 日志字段白名单 |
| 图片（拍照识别） | **不落存储，内存处理后丢弃** | 不写对象存储 |
| 备案 | 境内 Serverless → 备案可按常规流程 | §3.1 |
| 隐私政策 | 必须写明「AI 功能会将您输入的文字/图片发送至第三方模型服务」 | 单独告知 + 单独同意 |

> **一句话**：**服务端的合规优势来自「它什么都不存」。** 这是把服务端做薄的隐藏收益，很多人做反了 —— 一上来就上数据库，把合规成本拉满。

### 3.8 可观测性与成本监控

| 项 | 做法 | 阈值告警 |
|---|---|---|
| 调用量 | 按路由 + 日聚合 | 日调用 > 均值 3 倍 |
| **token 成本** | 每次记录 `prompt_tokens + completion_tokens`，日汇总换算金额 | **日成本 > ¥50【建议值】→ 告警** |
| 错误率 | 5xx / 上游超时比例 | > 5% 持续 10min |
| 熔断状态 | 全局熔断是否触发 | 触发即告警（说明被刷或有 bug） |
| 客户端版本分布 | 按 `X-App-Version` 统计 | 用于决定强制升级 |

> **成本监控是本节最重要的部分**：AI 类产品的死亡方式几乎都是「账单先爆炸，人后知道」。**日成本告警必须在 V1 上线前就位**（⑨ 篇风险 R4 的落地手段）。

### 3.9 部署与发布

| 项 | 做法 |
|---|---|
| 形态 | 单函数 + 环境变量（`LLM_API_KEY` / `SALT` / 限额配置） |
| 环境 | `staging` / `production` 两套，独立 Key 与配额 |
| 发布 | CLI 一键部署（`wrangler deploy` / `serverless deploy` / SCF 控制台 + CI）；**无需容器、无需 K8s** |
| 回滚 | 保留上一版本；Serverless 平台天然支持版本切换 |
| 域名 | 自有域名 + HTTPS（Serverless 平台自带证书）；**CloudKit 不需要额外域名** |

### 4.2 请求 / 响应规格

**① 宠物台词（`POST /v1/ai/line`）**

```jsonc
// Request
{
  "trigger": "weight_down",        // weight_down|plateau|missed_days|milestone|daily_open
  "now_kg": 62.4,
  "prev_kg": 63.1,
  "streak_days": 12,
  "total_lost_kg": 4.6,
  "nickname": "小张",
  "pet_name": "团子",
  "personality": "gentle",         // friendly|energetic|gentle
  "locale": "zh-Hans"
}
// Response 200
{
  "line": "比上次轻了 0.7kg，连续 12 天没断，团子都替你高兴。",
  "cached": false,
  "source": "llm",                 // llm|template
  "fallback": false
}
// Response 429（超限额 —— 客户端应静默切模板池）
{ "fallback": true, "reason": "quota_exceeded", "retry_after": 3600 }
```

**② 内容清单（`GET /v1/content/manifest`）** —— 见 §3.4。

**③ 错误响应（统一结构）**

```jsonc
{ "error": { "code": "QUOTA_EXCEEDED", "message": "...", "request_id": "..." } }
```

### 4.3 错误码

| HTTP | code | 客户端动作 |
|---|---|---|
| 400 | `INVALID_PAYLOAD` | 上报，走 fallback（不重试） |
| 401 | `INVALID_TOKEN` | 重新走 App Attest 注册，重试 1 次 |
| 403 | `APP_NOT_GENUINE` | 降权（切低限额模式），不阻断 |
| 404 | `NOT_FOUND` | 走 fallback |
| 429 | `QUOTA_EXCEEDED` | **静默切模板池 / 隐藏入口**（不提示用户「你超额了」） |
| 500 | `INTERNAL` | 重试 1 次 → fallback |
| 503 | `UPSTREAM_UNAVAILABLE` | 重试 1 次 → fallback |
| — | 超时 | 直接 fallback，不重试 |

> **设计原则**：**AI 是「锦上添花」，任何错误都不应该让用户看到报错弹窗。** 所有错误路径的终点都是「模板台词」或「隐藏该功能」。

### 4.4 版本协商与强制升级

| 头 | 方向 | 用途 |
|---|---|---|
| `X-App-Version` | 客户端 → 服务端 | 服务端识别旧版并兼容响应结构 |
| `X-Client-Platform` | 客户端 → 服务端 | 未来多端扩展 |
| `X-Content-Version`（响应） | 服务端 → 客户端 | 内容增量更新 |
| `X-Min-Supported-Version`（响应） | 服务端 → 客户端 | **低于此值弹「需更新」**（仅在协议不兼容时使用，不要滥用） |

**兼容纪律**：**服务端只做向后兼容的变更**（加字段可，删字段/改语义不可）；确需破坏性变更时，用 `/v2/` 路径而非改 `/v1/`。

### 4.5 离线降级矩阵

| 能力 | 离线 | 服务端故障 | 超限额 |
|---|---|---|---|
| 体重记录 / 趋势 / BMI | ✅ 全功能 | ✅ 全功能 | ✅ 全功能 |
| 饮食记录（食物库搜索） | ✅ 本地库 | ✅ 全功能 | ✅ 全功能 |
| 食谱浏览 | ⚠ 用本地缓存 | ⚠ 用本地缓存 | ✅ 全功能 |
| **宠物台词** | ➡ **模板池** | ➡ **模板池** | ➡ **模板池** |
| AI 营养师 / 拍照识别 | ➡ 入口置灰 | ➡ 入口置灰 | ➡ 入口置灰 |
| 订阅 / 权益 | ✅ 本地缓存权益 | ✅ 本地缓存权益 | ✅ 不涉及 |

> **这张表的战略含义**：**核心链路（记录 + 趋势 + 饮食 + 食谱）在「离线 / 服务端挂 / 超限额」三种最坏情况下全部可用。** 这是「AI 是可选增强」的架构级证明 —— **服务端从「单点故障」降级为「体验增强器」。**

## 附 B · 测算过程与敏感度（与实测严格分开）

### B.1 服务端工时测算

- **假设**：熟悉 TypeScript / Node 的开发者；使用 AI 编码助手；Serverless 平台已有账号。
- **依据**：3 个 AI 路由（转发 + 校验）+ 2 个内容路由（静态 JSON 返回）+ 4 个中间件 + 部署配置。
- **推算**：
  ```
  路由与转发逻辑        = 0.5 人日
  App Attest 校验       = 0.5 人日
  用量墙 + 熔断         = 0.3 人日
  内容版本协议          = 0.2 人日
  部署 / 环境 / 联调    = 0.5 人日
  ─────────────────────────────
  合计                  = 2.0 人日（熟悉平台的前提下可压到 1.5）
  ```
- **结果**：**1.5–2.0 人日**
- **置信度**：**中**（基于典型 Serverless 项目的经验分解，非本项目实测）
- **敏感度**：±50% → **0.75–3.0 人日** → 对 90 人日总量影响 **+0.8%～+3.3%**，**不改变任何排期结论**。

### B.2 成本增量测算（M 档 vs S 档）

- **假设**：1,000 用户；AI 调用 5 次/人/月（缓存后未命中 30%）。
- **推算**：
  ```
  S 档（无服务端）月成本 = Apple ¥58.58 + 域名 ¥0 + LLM ¥0（无 AI）= ¥58.58/月
  M 档（最小后端）月成本 = Apple ¥58.58 + 域名 ¥10–30 + 服务端 ¥0–35.50 + LLM ¥100–1,500
                        = ¥170–¥1,630/月
  增量 = ¥111.42–¥1,571.42/月（其中绝大部分是 LLM，服务端本身仅 ¥0–¥35.50）
  ```
- **结果**：**「加最小后端」的纯基础设施增量 ≈ ¥0–¥35.50/月**（其余增量来自 AI 能力本身）
- **置信度**：中（调用量为假设）
- **敏感度**：服务端请求量 ×100 → 仍仅 ¥35.50–¥355/月，**量级不翻转** ✅

### B.3 「零后端」修正的论证

- **原命题（⑨ 篇）**：不写后端，`SwiftData + CloudKit` 免登录同步。
- **反例**：客户端要调用 LLM API → 必须携带 Key → Key 在 App 二进制内 → 可被提取。
- **修正后命题**：
  - **用户数据层：零自建后端成立**（CloudKit 承担，且优于自建）。
  - **AI 能力层：零自建后端不成立**（需要一个 BFF）。
- **修正的边界**：**如果产品不含云 AI（⑨ 篇 C2 极简路线），「零后端」完全成立** —— 所以这不是「⑨ 篇错了」，而是「⑨ 篇的表述在引入 AI 的档位下不成立」。**本文按档位给出了适用条件（§3.0）。**
