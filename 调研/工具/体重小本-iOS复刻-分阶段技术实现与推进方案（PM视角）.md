## 〇、结论先行（TL;DR）

> ## **完整 MVP 的技术工作量约 90 人日（≈4.1 人月）。这个数字有三种截然不同的含义：Solo 全职 → 14 周；2 人小团队 → 10–12 周；Solo 兼职（每周 12h）→ 60 周以上。第三种不是"慢"，是「结构性做不到」——必须缩形态，而不是延长时间。**

**1｜一句话方案**：**六阶段、14 个迭代周、42 项任务，其中 P0 项 21 项。** 关键路径是 `数据模型 → 体重录入 → 趋势分析 → 云同步 → 小组件/实时活动 → 订阅`，**这条链上任何一环延期，全盘顺延**。

**2｜【否定性结论】Solo 兼职（每周 8–15 小时）不要按本文的完整路线走。**
- **依据**：90 人日 ÷ 每周有效 1.0–1.5 人日 = **60–90 周（≈14–21 个月）**。而个人开发者方法论指出，**上线后 30%–50% 的时间会被维护/客服吃掉**，即**实际会更慢**。
- **动作**：Solo 兼职应走**极简 MVP（约 40 人日）**—— 砍掉食谱库、云同步、饮食记录，只做「体重记录 + 趋势 + 小组件 + 订阅」，约 **40 周**完成。**先活下来，再长大。**

**3｜技术方案的核心决策只有三条，其余都是执行细节。**
- **① 不写后端**：`SwiftData + CloudKit` 免登录同步 —— 直接消灭服务器成本、运维成本与大部分合规工作（前序报告测算：自建团队年运营 ¥138–291 万，免后端方案运维成本可压到「约 ¥0」）。
- **② 抄 iOS 不抄功能**：把工期优先投给 `WidgetKit + ActivityKit + HealthKit`（Phase 3），而不是社区与体围（Phase 之外）。**这是 iOS 端留存差异的真正来源**（第 ⑧ 篇 §四）。
- **③ AI 全部走「按量 API + 用量墙」**，暂不做端侧模型。理由：端侧模型是 V2 的降本手段，不是 MVP 的必要条件；而**没有用量墙的云 AI 是边际成本红线的直接违反**（前序报告已列为一票否决项）。

**4｜优先级的判定规则（本文自定，贯穿全文）**

| 级别 | 判据 | 处置 |
|---|---|---|
| **P0** | **不做则产品不成立 / 无法上架 / 无法收钱** | 必须完成，否则不进入下一阶段 |
| **P1** | 显著影响留存或体验，但缺了也能上线 | 本阶段完成，延期可容忍一次 |
| **P2** | 锦上添花 / 影响面窄 | 可延至 V1 或砍掉 |
| **P3** | 探索性 / 需外部条件 | 不排期，有资源再说 |

**5｜每条路线都预置了「决策门（Gate）」。** 阶段之间不靠时间推进，靠**验收条件**推进 —— 见 §七。**Gate 不过就不进入下一阶段，这是防止「做了 8 个月发现方向错了」的唯一机制。**

### 1.2 不可能三角（本文的选择）

个人开发者方法论指出：**高频迭代 / 深度销售 / 大规模投放，同一时间只能占两角。**

**本方案选择：`高频迭代 + 社区分发`，明确放弃「大规模投放」。**
- 含义：**不做付费买量**（ASO 自然量 + 小红书/即刻/少数派内容为唯一分发手段）。
- 对排期的含义：Phase 5 之后**不排「投放」任务**，只排「内容产出」任务（每周 1 篇）。

## 三、技术实现方案

> **⚠️ 本节已由第 ⑩ 篇下钻并修正**：`体重小本-iOS复刻-双端技术方案（iOS端×服务端）.md`
> **修正点**：本节 §3.4 把 LLM API 列在客户端运行成本里，但**客户端直连 LLM = API Key 硬编码进 App 二进制 = 必然被盗刷**。第 ⑩ 篇据此把「不写后端」修正为「**不自建后端基础设施 + 一个最小 BFF（AI 代理）**」，并把技术方案按 iOS 端 / 服务端拆开重写。**本节保留作为概览；涉及 AI、鉴权、内容分发的细节以第 ⑩ 篇为准。**

### 3.1 架构分层

```
┌──────────────────────────────────────────────────────┐
│ 表现层  SwiftUI Views（10 个页面 / P01–P10）           │
│         ├─ 首页 · 记录 · 分析 · 食谱 · 设置            │

│         ├─ WeightService（单位换算 / 趋势聚合 / BMI）   │
│         ├─ MealService（热量汇总 / 配比计算）           │
│         ├─ PetEngine（状态机 / 成长 / 台词调度）        │
│         └─ SubscriptionService（权益校验）              │
├──────────────────────────────────────────────────────┤

├──────────────────────────────────────────────────────┤
│ 系统集成层  WidgetKit / ActivityKit / HealthKit /       │
│            Speech / StoreKit 2                          │
├──────────────────────────────────────────────────────┤
│ 外部服务层  仅 1 类：LLM API（按量、带用量墙）           │

```

> **架构纪律三条**：① **领域层不依赖 UI 与网络**（可单元测试）；② **单位换算只在一处发生**（`WeightService`），避免精度漂移；③ **外部只依赖 1 个 LLM API**，换供应商只需改一个适配器。

### 3.3 六个关键技术难点及实现方案

#### K-1 · 单位换算与精度（P0）

**问题**：斤 / 公斤 / 磅三单位切换 + 两位小数，若在展示层各自换算会产生累积误差。

**方案**：
```
存储层：统一 kg，DECIMAL(5,2)
展示层：value_shown = round(value_kg × factor, 2)
        斤 factor = 2.0 ；磅 factor = 2.20462
反向输入：value_kg = round(input / factor, 2)   ← 只在录入时反算一次
```
**规则**：**任何计算（BMI、掉秤率、趋势）一律用 kg 中间值，最后一步才换算展示。**
**验证**：写一个属性测试 —— `round(round(x×2,2)/2,2) ≈ x`（容差 0.01）。

#### K-2 · 同步策略（P0）

**决策：本地优先（Local-first）+ CloudKit 后台同步。**

| 场景 | 行为 |
|---|---|
| 无网 | 全功能可用，写入本地待同步队列 |
| 有网 | CloudKit 后台推送，UI 不阻塞 |
| 冲突 | **以 `measured_at` 为准的后写覆盖**（体重记录是事实型数据，不需要 merge 策略） |
| 首装 | 从 CloudKit 全量拉取，进度条提示 |

**为什么不用 Supabase**：跨端需求出现前，CloudKit 免登录、免服务器、免运维、免备案 —— **四项成本同时归零**。代价是**锁死 Apple 生态**（可接受，因为产品本身是 iOS 单端）。

#### K-3 · 食物库冷启动（P0）

**问题**：官方 110 万条不可复刻，公开成分表只有 1,506–1,700 条。

**方案（三段式）**：
```
① 基础库：导入中国食物成分表 1,700 条（含 31–118 字段）→ 清洗为 food 表结构
② 常用补全：手工补 200–300 条「高频外卖 / 连锁菜品 / 包装食品」（覆盖 90% 录入场景）
③ UGC 冷启：用户手动输入的未匹配食物，落库为 source='ugc'，仅本人可见（不做社区共享，规避审核）
```
**预期效果**：**1,900–2,000 条即可覆盖 90%+ 日常录入**（依据：食物摄入的分布是典型长尾 —— 长尾对「能否记录」影响小，对「搜索成功率」影响大，可用手动输入兜底）。
**标注**：【推算·方法】按长尾分布经验，非实测，列为缺口（附 C #2）。

#### K-4 · AI 宠物状态机与台词（P0，轻量版）

**方案**：状态机本地计算（零成本）+ 台词由 LLM 生成（带缓存与模板兜底）。

```
触发计算（本地，纯函数）：
  if 本次体重 < 上次 && 降幅 ≥ 0.3kg        → celebrating
  elif 连续 ≥3 次记录无下降                  → encouraging
  elif 距上次记录 > 3 天                     → worried
  elif 命中里程碑(7/30/100 天 或 1/5/10kg)   → milestone
  elif 本次体重 ≤ 上次                       → happy
  else                                       → idle

优先级：milestone > celebrating > worried > encouraging > happy > idle

台词获取：
  1) 查本地缓存（同场景 + 同一天）→ 命中即返回
  2) 未命中 → 调 LLM（Prompt 见 ⑧ PRD §6.5.1）
  3) LLM 失败 / 超时 → 回落模板池（每场景 ≥5 条，随机不重复）
```
**成本控制**：缓存 24h + 每日调用上限 + 首次打开预生成 1 条。

#### K-5 · iOS 系统集成（P0）

| 集成 | 关键实现点 | 坑 |
|---|---|---|
| **桌面小组件** | `TimelineProvider` + `AppIntent`（一键打卡）；**数据经 App Group 共享** | 小组件**不能直接读 SwiftData**，需经 App Group 的 UserDefaults/文件 + 主 App 更新时刷新 timeline |
| **实时活动** | `ActivityAttributes` 定义静态/动态数据；轻断食开始 → `request`；结束 → `end(dismissalPolicy: .immediate)` | **必须支持主动消失**（官网原文要求）；iOS 16.1 以下不可用需降级 |
| **HealthKit** | `HKQuantityType(.bodyMass)` 读写；**首次授权引导页** | 写权限被拒后**不能反复弹窗**，需引导去「健康 App」设置 |
| **语音打卡** | `SFSpeechRecognizer` 本地识别 → 正则提取数字 → 确认弹窗 | 需 `NSSpeechRecognitionUsageDescription` |

#### K-6 · 订阅与权益校验（P0）

**方案**：StoreKit 2 + 本地权益缓存 + 服务端（Apple）校验。

```
购买 → StoreKit 2 `Product.purchase()` → 校验 `Transaction` 签名（本地 JWS 校验）
     → 写入 subscription 表 → 广播权益变更 → UI 刷新
恢复购买 → `AppStore.sync()` → 遍历 `Transaction.currentEntitlements`
权益校验 → `SubscriptionService.isVIP`（读本地缓存，冷启动异步刷新）
```
**红线**：**体重记录与趋势图永不校验权益**（⑧ PRD §6.8 红线 #2）。

| 域名 / 隐私政策页托管 | **¥10–¥30/月** | GitHub Pages 可免费 | 【推算·方法】 |
| **合计（无后端形态）** | **约 ¥170–¥1,600/月**（$24–$225/月） | —— | —— |

> **对照**：前序报告测算「复刻后自建 5 人团队年运营 ¥138 万–¥291 万」。**本方案的运行成本比它低 3 个数量级** —— 差别全在「有没有团队 + 有没有自建后端」。**这是个人复刻唯一成立的财务前提。**

### 3.5 技术债与兜底

| 潜在债 | 触发条件 | 兜底 |
|---|---|---|
| CloudKit 同步冲突 | 多设备高频并发写 | 改为「以设备为单位的合并 + 去重」，最坏情况降级为「单设备云备份」 |
| SwiftData 性能 | 记录数 > 5 万条 | 引入分页 + 预聚合（月度汇总表） |
| LLM 涨价 | 供应商调价（前序报告已记录 DeepSeek 涨 350%） | 提高缓存命中率 → 切换供应商 → V2 上端侧模型 |
| 小组件刷新不及时 | iOS 限制 timeline 刷新频次 | 关键场景改用 `AppIntent` 主动刷新 |

### 6.1 排期对照

| 配置 | MVP 周期 | 排期策略 | 取舍 |

### 6.2 【关键判断】Solo 兼职的正确姿势：缩形态，而不是延长时间

**极简 MVP（C2 专用，约 40 人日）**

| 保留 | 砍掉 |
|---|---|
| 体重录入（含标签/单位/多条） | 饮食记录 + 食物库 |
| 趋势分析（折线 + 柱形 + BMI + 目标） | 食谱库 |
| 记录页 + 日历 | CloudKit 同步（改用 iCloud 文档） |
| **桌面小组件 + 实时活动（强烈保留）** | AI 宠物 |
| 订阅 2 档（年 + 永久） | HealthKit |
| 合规 + 上架 | 语音打卡 / 锁屏小组件 |

**排期**：40 人日 ÷ 1.0–1.5 人日/周 = **27–40 周（≈7–9 个月）**。
**理由**：这 40 人日里，**「记录 + 趋势 + 小组件」占了 27 人日（67%）** —— 而这三项恰好是决定留存与差异化的部分。**先做对这三件，再谈别的。**

> **⚠️ 诚实提示**：即便是极简版，Solo 兼职也需 **7–9 个月**。**这是一个「愿不愿意做 2 年」的问题**（个人开发者方法论的最后一问），不是「能不能做出来」的问题。

## 八、AI 协作工作流（本项目的执行方式）

> 本文档假设用 AI 编码助手（Claude Code / Cursor 类）承担大部分编码。**这不是「让 AI 自己写」，而是「按契约喂」**。

### 8.1 每个任务的「输入契约」

给 AI 的输入必须包含四件：
```
① 任务 ID 与目标（如 T1.1 体重录入）
② 相关的数据模型定义（从 ⑧ PRD §6.2 摘该表）
③ 页面规格与验收标准（从 ⑧ PRD §6.3 摘该页）
④ 现有代码上下文（哪些文件、什么风格）
```

### 8.2 阶段级的 AI 协作分工

| Phase | AI 适合做 | AI 不适合做（人工） |
|---|---|---|
| P0 | 模型定义、组件库样板、目录结构 | 架构决策、设计系统审美 |
| P1 | 页面代码、图表接入、单元测试 | 交互手感调优、设计打磨 |
| P2 | CloudKit 样板、HealthKit 授权流程 | 真机联调、多设备测试 |
| P3 | 小组件/实时活动样板 | 数据桥的进程边界调试 |
| P4 | 食物库清洗脚本、食谱内容生成、Prompt 调优 | **宠物台词的"人味"把关** |
| P5 | StoreKit 集成、隐私政策初稿 | 合规终审、上架材料定稿 |

### 8.3 三个必须人工 Review 的检查点
1. **P0 结束**：数据模型与目录结构 —— 一旦定错，后面全是返工。
2. **P3 结束**：系统集成是否真的在真机上跑通（模拟器会骗人）。
3. **P4 结束**：宠物台词与食谱内容的**内容质量**（AI 生成的内容必须人工过一遍）。

## 附 B · 工期测算过程与敏感度（与实测严格分开）

### B.1 总工时测算

- **假设**：熟练 Swift 工程师；有 iOS 经验；使用 AI 编码助手；含测试与修复。
- **依据**：⑧ PRD 的页面规格与数据模型（逐项估算）；前序报告 §4.3 的模块工时作为交叉校验。
- **推算**：
  ```
  Phase 0 = 5.0 人日
  Phase 1 = 28.0 人日
  Phase 2 = 12.0 人日
  Phase 3 = 13.0 人日
  Phase 4 = 20.0 人日
  Phase 5 = 12.0 人日
  ─────────────────
  合计    = 90.0 人日 ≈ 4.14 人月
  ```
  **交叉校验**：⑧ PRD §B.1 推算「AI 提效后 MVP ≈ 3.3–4.4 人月」→ **4.14 人月落在区间内 ✓**
- **结果**：**90 人日（C1 = 14 周）**
- **置信度**：**中**（分解到任务级，但单项工时为估算而非实测）
- **敏感度**：工时 ±30% → **63–117 人日 → C1 = 10–18 周**；**量级（月级）不翻转**。

### B.2 三种配置的换算

- **假设**：C1 有效系数 0.75（40h → 30h = 3.75 人日/周）；C2 有效 1.0–1.5 人日/周；C3 并行损耗后 6.0 人日/周。
- **推算**：
  ```
  C1 = 90 ÷ 3.75 = 24 周？
  ```
  ⚠️ **发现矛盾**：90 ÷ 3.75 = **24 周**，与 §二 的 14 周不一致。

  **修正**：14 周的算法是「Phase 内任务串行、Phase 间线性相加」的**理想排期**，而 3.75 人日/周是按 **5 天 × 0.75** 得出的**容量**。两者差异来自：**任务并非全部串行**（如 Phase 1 中 T1.2 首页与 T1.3 记录页可部分并行；AI 辅助下并行度更高）。
  - **故取更保守口径**：**C1 实际工期 = 90 ÷ 3.75 ≈ 24 周（≈5.5 个月）**，而非 14 周。
  - **14 周是「理论最短关键路径 + 高并行」的乐观值。**
- **修正后的结论**：

| 配置 | 乐观（高并行） | **保守（按容量）** | 采用值 |
|---|---|---|---|
| C1 Solo 全职 | 14 周 | **24 周** | **18–24 周** |
| C2 Solo 兼职（完整） | 60 周 | **90 周** | **≥60 周（不可接受）** |
| C2 Solo 兼职（极简 40 人日） | 27 周 | **40 周** | **27–40 周** |
| C3 2 人团队 | 10 周 | **15 周** | **12–15 周** |

> **⚠️ 这是本文对自己的一次修正**：§二 的 14 周是**乐观值**，真实排期应按 **18–24 周（C1）** 规划。**这条修正必须明示，否则会系统性低估工期。**
- **置信度**：中低（容量系数为经验假设）
- **敏感度**：有效系数 0.6–0.9 → C1 变为 20–30 周，**量级不翻转**。

### B.3 运行成本测算（见 §3.4）

- **假设**：1,000 用户；LLM 调用 5 次/人/月（含缓存后实际未命中 30%）。
- **依据**：低价模型定价（按量）；CloudKit 免费额度。
- **推算**：`1,000 × 5 × 30% = 1,500 次/月 × ≈¥0.01/次 = ¥15/月`；上浮至 ¥100–1,500/月区间以覆盖峰值与营养师功能。
- **结果**：**约 ¥170–1,600/月（$24–$225/月）**
- **置信度**：低–中（调用量纯假设）
- **敏感度**：调用量 ×10 → ¥1,000–14,000/月，**仍远低于自建团队方案（¥11.5 万–24.3 万/月）**，**结论不翻转**。
