# 腾讯电脑管家「软件搬家」：PM 深度调研

调研日期：2026-09-24  
研究方式：公开资料桌面调研，未安装或操作客户端，未执行文件迁移。  
适用对象：PC 工具产品经理、存储治理产品负责人、软件管理团队。

> **一句话结论：这不是一个简单的“文件移动工具”，而是一个用迁移风险换取系统盘可用空间的低频、高价值、高信任成本产品。竞争力不在于能搬多少，而在于能否判断该不该搬、搬后能否持续正常使用、出问题能否恢复。**

- **【事实】**：本次成功获取的官方正文或明确标注年代的第三方正文支持。
- **【线索】**：仅搜索摘要、页面标题或未完整取得正文的信息，不作为功能已实现的证据。
- **【分析】**：基于事实的产品判断，不代表腾讯内部策略或真实业务数据。

## 1. 管理层摘要

### 1.1 五个核心判断

1. **用户买的不是“搬家”，而是“不删东西、不重装软件，也能继续工作”。** 软件搬家只是满足这一需求的一种手段。
2. **产品收益来自空间重新分配，不是创造容量。** C 盘空间可能增加，但目标盘会被占用；不等于增加内存，也不必然让电脑变快。
3. **历史设计已经形成基础闭环。** 官方文档包含磁盘占用展示、软件与大文件扫描、目标目录选择、迁移、历史与还原。[S1]
4. **真正的难点在迁移完成以后。** 启动成功不代表后续升级、修复、卸载、插件加载、开机服务都正常。
5. **优先做“安全决策与恢复”，再做“批量和增长”。** 提高搬移按钮点击率，却增加软件损坏与恢复困难，会损害电脑管家的主品牌信任。

### 1.2 对业务负责人的建议

将软件搬家放入“系统盘空间治理”整体方案，而不是孤立运营一个工具入口：

**诊断空间来源 → 推荐最合适的处理方式 → 安全执行 → 验证结果 → 控制后续增长。**

产品目标从“搬移了多少 GB”改为“帮助多少用户安全地解除空间不足，且没有引入新的使用障碍”。

### 2.1 一个重要的时效性陷阱

[S3] 页面教程正文的发布时间是 2020-11-05，但同页软件下载卡片显示 2026 年更新日期。**下载卡片更新不等于教程和产品流程同步更新。**

同样，知识库空壳页面呈现的当天日期，也不能直接视为文章发布日期。产品调研必须绑定具体版本、构建号和实际界面，不能只看网页页脚或下载时间。

### 2.2 三类“搬家”不可混为一谈

| 类型 | 用户真正想搬的东西 | 成功判断 |
|---|---|---|
| 软件搬家 | 程序主体及其路径依赖 | 能启动、运行、更新、修复、卸载 |
| 普通大文件搬家 | 视频、安装包、归档文件等 | 文件完整且仍可找到；外部引用是否受影响需说明 |
| 应用数据搬家 | 聊天记录、项目、素材库、缓存等 | 应用仍能识别数据，新数据按预期写入 |

“移动成功”在三种场景下不是同一件事。特别是数据库、项目引用文件、云同步目录中的大文件，不能因为体积大就自动判定适合直接迁移。

## 3. 用户需求：从功能视角转为任务视角

### 3.1 核心 JTBD

> 当系统盘快满、影响安装或工作时，我希望不用重新安装和配置常用软件，就能腾出足够空间，而且不会丢数据；万一不正常，还能恢复。

这是典型的“故障前后救急”需求，而不是每天主动使用的工具需求。

### 3.2 用户分层与优先级【分析】

| 人群 | 典型触发 | 最担心什么 | 适配程度 |
|---|---|---|---|
| 普通办公用户 | C 盘告警、更新失败、无法安装软件 | 不懂路径，怕误删和工作中断 | 核心人群；应提供保守推荐 |
| 多分区老电脑用户 | 系统盘小，其他分区仍空闲 | 是否需要重装系统 | 高适配，但须检查目标盘性能与健康 |
| 游戏用户 | 大型内容更新空间不足 | 重新下载耗时、反作弊或启动器异常 | 需求强，优先游戏启动器原生迁移 |
| 创作/开发用户 | 素材、SDK、模型或构建数据膨胀 | 环境变量、插件、服务和项目依赖损坏 | 收益高但风险高，需要专用适配 |
| 企业受管设备用户 | 系统盘紧张，权限受限 | 公司策略、加密、审计与业务连续性 | 不宜默认套用消费级迁移方案 |
| 无其他可用存储的用户 | 整块硬盘都满 | 无处可搬 | 不适合；应转清理、归档、卸载或扩容 |

分层不能只看软件大小，更要看“空间收益 × 数据重要性 × 依赖复杂度 × 可恢复性”。

### 3.3 需求优先级

**必需：**不丢数据、软件仍可用、空间真实释放、失败能解释、恢复路径明确。  
**重要：**知道该搬什么、知道搬多久、能理解为什么有些软件不能搬。  
**加分：**批量队列、迁移建议、增长提醒、跨版本兼容说明。  
**不宜优先：**动效、连续签到、强社交分享、与问题无关的推荐安装。

### 3.4 最容易被误判的需求

- 用户说“软件占空间”，实际可能是其数据目录或缓存占空间。
- 用户说“C 盘满了”，实际可能是更新临时文件，而非软件安装体积。
- 用户说“让电脑变快”，瓶颈可能是内存、CPU 或机械硬盘。
- 用户说“把所有东西搬走”，不意味着可以移动系统组件和整个用户配置目录。

因此，PM 首先要解决“是否该搬”的判断，而不是让所有用户更快进入搬移流程。

## 4. 产品定位与价值边界

### 4.1 在电脑管家中的位置【分析】

软件搬家属于“存储空间治理 / 软件维护”工具，和垃圾清理相邻，但价值逻辑不同：

- 清理：删除可丢弃内容。
- 卸载：移除不再需要的软件。
- 搬家：保留内容，通过改变存储位置释放源盘空间。
- 扩容：增加存储容量或重新分配分区容量。

它适合承接“清理之后还不够，但软件仍要使用”的用户，是垃圾清理的补充，而不是替代。

### 4.2 对用户的价值

1. 减少重装、重新登录、恢复偏好设置的成本。
2. 利用已有磁盘空闲空间，延后扩容支出。
3. 把专业文件系统操作转为可理解的任务流程。
4. 如果恢复机制可靠，可降低用户尝试迁移的心理成本。

### 4.3 对平台的潜在价值

建立“关键时刻能解决问题”的信任，增加用户保留电脑管家的理由，并与空间诊断、软件安装和数据管理形成闭环。

这些是合理商业假设，**不是已验证的留存提升或收入归因**。低频工具应关注问题解决和满意度，不应机械追求搬家 DAU。

## 5. 用户旅程与逐环节 PM 评估

历史公开流程：[S1][S3]

**进入工具 → 选择源盘 → 扫描软件/大文件 → 选择对象 → 选择目标目录 → 开始搬移 → 查看结果/搬移历史 → 必要时还原。**

下表中的改进项均为建议，不是对现有客户端缺陷的实测判定。

| 阶段 | 用户问题 | 历史方案依据 | PM 风险与改进 |
|---|---|---|---|
| 触发 | 为什么 C 盘满了？ | 展示磁盘占用 | 先解释占用来源，不要把所有空间问题导向搬家 |
| 发现入口 | 从哪里进入？ | 2020 教程为工具箱入口 | 不同版本入口需匹配；设置版本化帮助与站内搜索别名 |
| 扫描 | 为什么少了我想搬的软件？ | 扫描已装软件和大文件 | 区分“未识别”“不支持”“正在运行”，避免空结果无解释 |
| 选择 | 搬哪个最值得？ | 用户自主选择 | 展示可释放量、风险等级、数据是否包含、推荐理由 |
| 选目标 | 搬去哪里？ | 默认最小占用比例盘 | 增加绝对剩余空间、磁盘类型、卷状态、可写性检查 |
| 确认 | 要关软件吗？会丢东西吗？ | 公开帮助未说明全部边界 | 告知受影响程序、预计耗时区间及恢复条件 |
| 执行 | 卡住了吗？能取消吗？ | 有搬移进度步骤 | 显示阶段、已处理量；明确不同阶段的取消语义 |
| 结果 | 已经真的能用了？ | 展示完成及历史入口 | 区分“复制完成”“路径切换完成”“使用验证通过” |
| 后续 | 升级后坏了怎么办？ | 有历史/还原设计 | 提供持续可发现的恢复中心及兼容性反馈 |

### 5.1 历史设计值得借鉴的地方

- **磁盘视角接近用户心智。** 普通用户通常先感知“C 盘红了”，再考虑具体软件。
- **软件与大文件双入口覆盖不同占用来源。** 用户不必先了解程序与数据的区别才能开始查找。
- **默认目标盘减少决策成本。** 对不熟悉磁盘结构的人有帮助。
- **软件单个搬移是一种风险约束。** 可能降低故障定位与依赖冲突复杂度；此处是设计解释，不是官方给出的原因。
- **历史和还原回应了“后悔怎么办”。** 这是工具信任的重要基础。

### 5.2 需要警惕的默认策略

**占用比例最小 ≠ 最佳迁移目的地。**

示例：一个 50GB 的目标卷已用 10%，只有约 45GB 可用；一个 1TB 的目标卷已用 70%，仍有约 300GB 可用。迁移 60GB 数据时，按占用比例推荐前者是不够的。此为说明算法边界的假设示例，不是腾讯客户端实测行为。

推荐顺序应是：

1. 先排除不可写、空间不足、离线、文件系统不适配的候选。
2. 再检查性能、健康状况、是否可移动设备、是否存在企业策略限制。
3. 最后按容量余量、使用体验和用户偏好排序。

同一硬盘上的其他分区可以缓解 C 盘容量不足，但不能降低该物理硬盘故障导致的数据风险，也不意味着读写性能提升。

## 6. 技术约束如何转成产品规则

### 6.1 不能把“软件搬家”理解为剪切安装目录

软件可能依赖注册表、服务、驱动、共享运行库、快捷方式、文件关联、插件、计划任务和多用户配置。只移动可执行文件所在目录，不代表依赖随之正确迁移。

常见实现思路包括迁移目录后保留路径映射、更新配置，或使用软件自身提供的迁移接口。**本次未获取腾讯实现文档，也未观察文件系统变化，不能断言其具体采用哪一种或哪几种。**

微软文档确认：文件硬链接不能跨卷，目录 junction 可指向同一计算机上的不同本地卷，并通过重解析点实现。[S5] 因此不能笼统写成“C 到 D 搬家就是硬链接”，也不宜把各种链接机制混写。

### 6.2 如果采用路径映射，PM 必须处理的后果【建议】

- 原路径看起来仍存在，不等于源盘仍存放完整数据；展示“逻辑路径”和“实际存储位置”。
- 目标盘断开、改盘符、损坏或权限变化，可能影响软件运行。
- 清理工具、备份软件和杀毒软件可能以不同方式处理重解析点。
- 安装器可能在后续更新中重新创建目录，导致空间重新增长或路径异常。
- 用户不知道目标目录作用而误删，是恢复与教育设计要处理的问题。

上述为条件性技术风险，不能据此认定腾讯产品已出现相应缺陷。

### 6.3 推荐的迁移准入分层

| 层级 | 对象 | 建议策略 |
|---|---|---|
| 原生能力优先 | 有官方迁移接口或设置的应用 | 优先引导原生流程 |
| 已验证兼容 | 已覆盖启动/更新/卸载测试的具体应用版本 | 可推荐迁移，显示验证范围 |
| 未充分验证 | 普通桌面软件，依赖情况未知 | 说明未知风险，不默认勾选 |
| 高风险 | 驱动、安全软件、数据库、关键系统组件 | 默认禁止通用迁移，提供替代方案 |
| 数据目录 | 聊天数据、素材、项目、虚拟机等 | 按应用专门适配，不能以“非系统文件”直接放行 |

必须基于版本、安装方式、当前运行状态和目录内容判断，而非只按软件名称建静态白名单。

### 6.4 一个合理的迁移事务模型【建议】

**预检查 → 建立任务日志 → 复制到目标暂存区 → 完整性校验 → 切换路径/配置 → 功能验证 → 清理可安全删除的源副本 → 完成。**

关键约束：

- 跨卷迁移不是一次天然原子的整体操作，必须记录阶段和恢复点。
- 不在目标副本未验证前删除唯一有效源数据。
- 复制阶段取消与路径切换阶段取消，行为不同；界面必须告知。
- 迁移后程序可能产生新数据，还原必须考虑这些增量，不能简单恢复旧副本。
- 保留源副本有助恢复，但会减少即时空间收益；不能同时虚报“已释放”和“完整备份仍占源盘”。
- 重启后应能识别中断任务，说明已完成、待恢复和需要用户选择的部分。

## 7. 风险矩阵：必须比成功流程更详细

| 风险 | 用户损失 | 建议预防与恢复 | 优先级 |
|---|---|---|---|
| 搬移过程中应用仍在写入 | 文件不一致、数据损坏 | 获取占用信息，提示保存并退出；不能安全停写则拒绝 | P0 |
| 复制失败或磁盘写满 | 残留、源目标不一致 | 预估实际分配空间与余量，校验后再切换，保留有效源 | P0 |
| 断电、进程崩溃、重启 | 半迁移状态 | 持久化事务日志、幂等恢复、启动后发现中断任务 | P0 |
| 路径切换或权限异常 | 无法启动、访问被拒绝 | 校验 ACL、服务账户、路径边界；安全回滚 | P0 |
| 错搬系统/关键应用 | 系统或业务不可用 | 排除清单、版本规则、企业策略识别 | P0 |
| 迁移后更新/卸载失败 | 延迟故障，难以关联原因 | 把升级和卸载纳入兼容性测试；历史记录保留版本 | P0 |
| 还原时源盘空间不足 | 有恢复按钮却不能恢复 | 恢复预检查，告知所需容量，保留当前有效状态 | P0 |
| 目标盘掉线、改盘符 | 软件突然不可用 | 消费级默认不推荐可移动/网络目标；卷身份识别 | P1 |
| 大文件统计重复 | 高估释放空间 | 处理硬链接、重解析点、压缩/稀疏文件，不重复计算 | P1 |
| 迁移后明显变慢 | 用户认为产品损坏电脑 | 显示磁盘性能差异，必要时推荐搬数据而非程序 | P1 |
| 日志包含敏感路径 | 暴露用户名、项目名、客户资料 | 本地处理优先，上传须告知、最小化、脱敏 | P0 |

**任何风险表都不能被当作免责条款。** 对无法控制的风险，应限制支持范围，而不是让用户点“我已知晓”后继续执行危险操作。

## 8. 竞争格局：真正的竞品是所有“腾空间”方案

以下是方案级比较，不是当前版本逐项实测；本次没有足够证据对 360、联想等同类产品的具体收费、覆盖率和恢复能力做排名。

| 方案 | 优势 | 代价或边界 | 腾讯软件搬家的应对 |
|---|---|---|---|
| 垃圾清理 | 操作快，不改变常用软件路径 | 可清理量有限，缓存可能再生 | 先清理低风险垃圾，再判断是否需要搬 |
| 卸载不常用软件 | 释放明确，依赖由卸载器处理 | 不适合还要继续使用的软件 | 不应把闲置软件也默认推荐搬家 |
| 卸载后重装到其他盘 | 安装器重新建立依赖 | 耗时、重登录，配置/授权可能需恢复 | 对高风险且不支持迁移的软件推荐此路 |
| 应用自带迁移 | 应用理解自身数据结构 | 各家能力不统一，入口分散 | 有原生能力时优先转交，不盲目替代 |
| Windows 系统存储与应用管理 | 系统集成、信任成本低 | 可移动性受应用类型与系统版本限制 | 补充其未覆盖的传统软件场景 |
| 分区调整 | 可以从容量结构上解决问题 | 存在分区布局、备份与操作风险 | 不把搬家宣传成所有分区问题的终局解 |
| 同类管家搬家工具 | 功能心智接近、用户学习成本低 | 当前差异须绑定版本验证 | 比较兼容性、恢复和可解释性，而非按钮数量 |
| 专业应用迁移工具 | 可能提供更广的迁移工作流 | 能力和许可各异，需单独验证 | 普通用户强调简单可靠，复杂场景明确分流 |
| 新硬盘/外部归档 | 增加容量或转移冷数据 | 有硬件、管理和访问成本 | 整盘都满时应坦诚建议扩容而非反复扫描 |

### 8.1 腾讯的潜在差异化【分析】

电脑管家的安装软件识别、清理场景与用户触达，是软件搬家可能利用的邻接能力；但这些能力是否被本功能实际复用、效果如何，需要内部数据验证。

长期壁垒更可能来自：

1. 按应用和版本积累的兼容性知识。
2. 面向真实故障的恢复机制。
3. 空间统计准确性与推荐解释能力。
4. 软件安装、更新、卸载全生命周期适配。

不应仅以“支持的软件数量”比较产品，因为数量可能通过放宽准入得到，却把风险留给用户。

## 9. 产品改进方案：从“搬家工具”升级为“空间治理助手”

### 9.1 推荐信息架构【建议】

主入口优先采用用户语言：“释放 C 盘空间”，将“软件搬家”作为其中一项。

```text
空间诊断
├─ 可安全清理的临时内容
├─ 不常用的软件：建议卸载
├─ 大型普通文件：建议整理/迁移
├─ 已验证可迁移的软件：软件搬家
├─ 应用数据：使用应用原生或专用迁移
└─ 空间仍不足：评估扩容/归档

统一任务与恢复中心
├─ 正在执行 / 中断待处理
├─ 已完成 / 待使用验证
└─ 可还原 / 还原受阻及原因
```

### 9.2 软件列表最少应展示什么

- 软件名、版本和实际安装位置。
- 程序占用与数据占用是否分别识别。
- **预计可释放源盘空间**，而不仅是目录逻辑大小。
- 兼容性状态和不支持原因。
- 运行状态、需关闭的相关进程。
- 建议目标、容量余量及性能提示。
- 是否支持还原、还原需要满足什么条件。

优先排序依据应是“可安全释放的收益”，不只是最大的文件排最上面。

### 9.3 交互文案建议

| 不建议 | 建议 |
|---|---|
| 一键加速电脑 | 将已验证的软件迁往其他磁盘，释放系统盘空间 |
| 释放内存 20GB | 预计释放 C 盘存储空间 20GB |
| 安全无风险 | 已完成兼容性预检查；以下限制仍需注意 |
| 搬家失败 | 目标盘空间不足，尚未切换路径，原软件仍保留 |
| 搬家完成 | 路径迁移完成，请验证软件运行；实际释放 XGB |
| 全部可搬 | 已验证可迁移 / 未验证 / 不支持 |

数字为文案占位示例，不代表本次测试结果。

### 9.4 需求优先级与验收条件

| 优先级 | 需求 | 为什么先做 | 验收重点 |
|---|---|---|---|
| P0 | 版本化帮助与能力声明 | 防止用户按旧教程误操作 | 文档绑定版本，明确批量和还原范围 |
| P0 | 准入与目标盘预检查 | 把风险挡在执行前 | 所有拒绝项有原因和替代路径 |
| P0 | 事务日志与中断恢复 | 保护用户唯一数据 | 各阶段故障注入后状态可解释、可恢复 |
| P0 | 软件级结果验证 | 避免把复制完成当成功 | 启动、写入、重启、更新、卸载按支持范围验证 |
| P0 | 可发现的恢复中心 | 延迟故障需要追溯 | 支持空间不足、软件更新后的恢复判断 |
| P1 | 净收益与风险排序 | 提高有效选择率 | 预计与实际空间差异可解释 |
| P1 | 原生迁移引导 | 减少通用搬移兼容问题 | 能识别适用应用，说明需用户完成的动作 |
| P1 | 串行批量队列 | 降低多软件操作成本 | 单任务隔离失败，可跳过，不一键破坏多项 |
| P2 | 增长预防 | 减少再次紧急救火 | 用户可设置数据路径建议和低打扰提醒 |

P0/P1/P2 是建议顺序，不表示腾讯当前缺少或已拥有这些能力。

## 10. 指标体系：不要只看“搬了多少”

### 10.1 北极星指标【建议】

**每周经验证解除系统盘空间不足、且观察期内未出现已知迁移相关严重故障的去重设备数。**

其中：

- “空间不足解除”须依据产品定义的安全余量或当前任务需求判断，而非只增加任意一点容量。
- “经验证”应覆盖可获得的应用使用验证；仅无报错不代表成功。
- 观察期可以先用 7 天作为试运行口径，并单列 30 天更新/卸载故障观察。
- 未回访、无验证信号的设备标记“结果未知”，不能默认成功。

7 天和 30 天是建议观察窗口，不是腾讯现有口径。

### 10.2 漏斗与公式

| 指标 | 建议定义 | 解释 |
|---|---|---|
| 候选覆盖率 | 有至少一个合格候选的空间紧张设备 / 完成诊断的空间紧张设备 | 区分需求不存在与识别能力不足 |
| 合格用户启动率 | 启动迁移的设备 / 看见可行方案的设备 | 不把无目标盘用户纳入分母 |
| 执行完成率 | 完成路径切换的任务 / 已启动任务 | 只是工程完成，不等于业务成功 |
| 使用验证通过率 | 使用验证通过的软件任务 / 完成验证的软件任务 | 同时报出验证覆盖率，避免选择偏差 |
| 安全收益 | 已验证成功任务释放空间的中位数与分位数 | 避免大任务拉高均值 |
| 估算误差 | 实际释放量与预计释放量之差 | 扣除同期下载、系统更新等干扰 |
| 回滚成功率 | 成功恢复的任务 / 尝试恢复的任务 | 主动后悔和故障恢复分开统计 |
| 严重故障率 | 已确认数据丢失/关键软件失效任务 / 启动任务 | 核心护栏，须考虑延迟上报 |
| 30 天空间复发率 | 再次空间不足设备 / 有持续观测的已解决设备 | 观察是否只是临时救急 |

### 10.3 建议埋点

`diagnosis_completed`、`candidate_presented`、`candidate_rejected`、`migration_confirmed`、`preflight_failed`、`migration_stage_changed`、`migration_interrupted`、`migration_completed`、`validation_completed`、`rollback_requested`、`rollback_completed`。

关联字段以任务 ID、软件类别、产品/应用版本、系统版本、文件系统、源目标磁盘类型、失败阶段和错误码为主。默认不上传完整路径、文件名、文档内容、聊天数据或注册表明文。

### 10.4 指标反作弊与正确解释

- 已释放空间应以源卷实际变化结合任务归因核对，不能直接相加文件逻辑大小。
- 原路径映射可能让扫描重复看到数据，应去重。
- 用户取消未必是坏事：如果是看懂风险后放弃，可能是正确决策。
- 还原率低也不一定是好事：可能只是用户找不到还原入口。
- 更高的成功率可能源于更严格的准入，必须同时报告覆盖率。

## 11. 商业化与增长判断

### 11.1 适合的增长方式【建议】

- 在用户主动清理且空间仍不足时展示建议。
- 基于真实空间不足提示，不制造焦虑、不把普通使用量包装成严重故障。
- 在软件安装阶段提供合理目录建议，降低后续搬家需求。
- 维护按版本编写的搜索帮助，承接“软件搬家在哪里、能不能恢复”等意图。

### 11.2 不适合的商业化方式

- 故障发生后把还原能力作为临时付费墙。
- 先给过度安全承诺，再为数据恢复收费。
- 使用搬家结果页强制推荐无关软件。
- 默认选择商业合作磁盘或服务，而非安全合适的目标。

如果探索付费，宜围绕企业策略、批量部署、审计和高级支持；基础安全保障与承诺内恢复不应被削弱。**本次未核实腾讯现有收费政策，此处仅为策略建议。**

### 11.3 简化投入产出判断

净收益可用“问题解决带来的保留价值与支持成本节省，减去研发适配、兼容性维护和故障赔付/品牌损失”衡量。

软件搬家的成本往往不在一次开发，而在操作系统、软件安装器、应用版本持续变化后的适配维护。若缺少长期维护资源，应缩小支持范围，而非广泛承诺通用迁移。

## 12. 下一步验证计划：把桌面调研变成可立项证据

### 12.1 第一阶段：现状核实

在隔离测试设备/虚拟机中验证；对磁盘性能、可移动盘和故障恢复另用可恢复的测试硬件，不直接搬移真实办公数据。

记录：安装来源、产品版本、构建号、系统版本、入口、规则、收费与提示内容。分别检验当前官方可下载版本与经典版本；不为了验证旧教程安装来源不明的老包。

必须回答：

1. 当前入口在哪里？软件搬家、大文件搬家、聊天数据搬家是否共享引擎和恢复中心？
2. 大文件阈值和软件批量限制是否仍与历史帮助一致？
3. 被排除的软件有哪些？原因是否可理解？
4. 是否实际处理软件数据目录，还是主要处理安装目录？
5. 迁移后启动、更新、修复和卸载是否正常？
6. 历史记录保存多久？卸载电脑管家后恢复入口如何处理？
7. 当前迁移和还原是否收费，是否存在版本或容量限制？

### 12.2 第二阶段：测试矩阵

| 维度 | 最低覆盖建议 |
|---|---|
| 应用类型 | 普通桌面应用、游戏启动器管理应用、带服务应用、便携应用、商店应用、数据密集应用 |
| 存储拓扑 | 同硬盘跨分区、跨内部硬盘、SSD 到 HDD；不支持场景验证拒绝行为 |
| 路径 | 中文、空格、长路径、多用户目录、已含重解析点的目录 |
| 状态 | 正常退出、前台运行、后台服务写入、更新进行中 |
| 空间 | 充足、恰好不足、执行中被其他任务消耗、还原时源盘不足 |
| 故障 | 进程终止、重启、写入失败、目标掉线、权限变化 |
| 生命周期 | 首次启动、重启后启动、核心功能读写、应用更新、卸载、再安装、还原 |

文件数和大小校验只是起点；关键测试数据应校验内容完整性，并进行应用功能验证。哈希一致也不能证明配置、权限和服务依赖正确。

### 12.3 第三阶段：定性访谈与小规模可用性测试

建议招募约 8–12 名用户做探索性访谈，覆盖普通办公、多分区设备和高数据量应用用户；该样本只用于发现问题，不用于推断总体比例。

核心问题：

- 上次 C 盘不足时，你首先做了什么？
- 哪些软件或数据“宁愿不搬也不能坏”？
- 你理解的“软件搬家”是否包含聊天记录和项目数据？
- 什么证据能让你愿意点击开始？
- 搬完之后你如何确认成功？出现问题会去哪里恢复？

测试任务关注能否独立识别适合搬移对象、理解风险、找到恢复入口；不只记录点了多少步。

### 12.4 发布门槛【建议】

- 明确支持范围内的关键场景测试通过。
- 数据丢失类已知缺陷全部关闭；出现确认案例应暂停相关规则或版本扩量。
- 每个中断阶段都可恢复到已知状态，不能留下无解释的半迁移状态。
- 低风险用户分阶段灰度，具备应用/版本规则的远程禁用能力。
- A/B 测试可以比较解释和排序，不应通过放松安全校验提升转化。
- 兼容性未知率、使用验证覆盖率、异常率满足团队基于基线制定的门槛后，才扩大范围；本报告不虚构门槛数值。

## 13. 最终产品判断

### 值得保留

清晰的系统盘痛点、磁盘视角、软件与大文件分类、默认目的地和搬移历史/还原设计。这些构成有效的基础产品闭环。

### 应重点补强或验证

版本与入口一致性、实际释放量解释、目标盘选择、应用生命周期兼容、任务中断恢复、还原可发现性，以及软件主体与数据的区别。

### 不应盲目追求

全软件支持、全自动决策、无限制批量、笼统“零风险”、以迁移 GB 或按钮转化率替代用户问题解决。

> **PM 的首要任务不是让用户更敢点击“开始搬移”，而是让产品更有资格接受这次点击。最优产品不是帮用户搬最多的软件，而是用最小风险、最少干扰解决空间问题。**
