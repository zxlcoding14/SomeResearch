## TL;DR（结论先行）

| # | 结论 | 置信度 |
|---|---|---|
| 1 | **不是二选一，是端云双引擎**。扫描全能王 App 内置**本地 OCR**（端侧），同时提供**云端 OCR**（服务端）。官方 FAQ 原话：「CS 的 OCR 功能分为本地 OCR 和云端 OCR 两种」。 | 【官方】高 |
| 2 | **主路径在服务端，端侧是兜底**。三条独立证据同向：① 本地识别的 UI 形态是「**开关**」，默认需用户手动开启；② 免费用户 OCR 有**次数配额**（配额只能在服务端记账）；③ IPO 问询函把「**精准识别**」列为产生服务器在线交互成本的科目。 | 【官方+审计】高 |
| 3 | **端侧模型被刻意裁剪到极小**。有版本说明称「OCR 需联网，**离线模式下仅可识别英文与数字**」；云端语言包（41–50 种）放在服务端，由用户在「更多设置 → 文字识别 OCR → **云端文字识别语言**」里勾选。这是典型的「包体换精度」权衡。 | 【第三方·中】中 |
| 4 | **端侧 OCR 的商业理由是成本而非体验**。用 IPO 披露的服务器成本反推：若把免费用户的基础识别全部放云端，仅这一项年成本就达 **6,360 万元量级**（按 0.01 元/次保守锚点），是当年全年服务器成本（约 4,000 万）的 **1.6 倍**——商业上不可行。**端侧 OCR 每次调用边际成本为 0**，这是它存在的根本原因。 | 【推算·方法】中 |
| 5 | **开源可完整复刻的只是「识别」这一段，不是产品**。PaddleOCR / RapidOCR / ML Kit / Apple Vision 在**端侧**已可用（模型 3–20 MB、单页 200–800 ms）；在**服务端**有 PaddleOCR-VL、MinerU、docling、Surya 等（多为 Apache-2.0 / MIT，可闭源商用）。**但扫描全能王真正的壁垒不在 OCR 引擎，而在端侧超大字符集量化方案（>20,000 类）、图像增强链（去摩尔纹/去手写/曲面矫正）与多端同步存储体系。** | 【实测+官方】高 |
| 6 | **效果数字必须看口径**。同一家公司同一产品：常规印刷体「99.77%」与复杂场景「81.4%」相差 **18 个百分点**。前者是自选数据集/检测报告口径，后者是复杂场景平均值。**任何单一"识别率"数字都不足以支撑决策。** | 【审计】高 |

## 一、判定方法：我怎么得出「端云双引擎」的

这类问题不能靠猜，必须靠可核证据。下面是本次用到的六类证据，按可信度排序——**这套方法本身可复用到任何 App**。

| 证据类型 | 本次发现 | 可否推翻 | 可信度 |
|---|---|---|---|
| ① 官方 FAQ / 帮助中心原文 | 「CS 的 OCR 功能分为**本地 OCR** 和**云端 OCR** 两种。本地 OCR 功能为 app 内置，**识别词库量有限**。建议使用云端 OCR 获得更好的识别效果。」（v3.camscanner.com/mobile/faq?id=249） | 不可 | **【官方】高** |
| ② 官方产品设置项名称 | 「更多设置 → **文字识别 OCR** → 云端文字识别语言」；同页存在「**本地识别**」开关 | 不可 | **【官方】高** |
| ③ IPO 审计文件（服务器成本科目） | 「扫描全能王相关服务器成本主要系用户使用精确查找、**精准识别**、文件云端同步、**精准矫正**、数据导出等功能的**在线交互**产生」（问询函回复 2022-03-11） | 不可 | **【审计】高** |
| ④ 端侧开关的实操路径（多版本/多系统截图级教程） | 4 条独立教程覆盖 Android 11 / iOS 16.5.1 / iOS 14.8，路径一致：我的 → 更多设置 → 文字识别 OCR → **开启「本地识别」** | 难 | 【第三方·实操】中高 |
| ⑤ 港股招股书技术披露 | 「为解决**移动端部署难题**，公司研发了**基于边缘设备的深度学习量化加速压缩技术**，使大类别汉字识别模型能在资源受限的设备上高效运行」 | 不可 | **【官方·招股书】高** |
| ⑥ 版本说明 / 下载站技术注记 | 「OCR 文字识别需联网，**离线模式下仅可识别英文与数字**」 | 可 | 【第三方·低-中】低 |

**判定逻辑链**（三步闭环，缺一不可）：

```
官方 FAQ 说"有两种"           → 端侧确实存在（不是纯云）
        +
服务器成本科目含"精准识别"     → 主路径确实在云端（不是纯端侧）
        +
本地识别是"开关"+ 免费有配额   → 端侧定位是"降级/兜底"，云端是"主卖点"
```

## 二、架构拆解：端云双引擎干了什么

### 2.1 端侧（本地 OCR）

| 维度 | 事实 | 来源 |
|---|---|---|
| 存在性 | App 内置，非需下载的插件 | 官方 FAQ【官方】 |
| 默认状态 | **关闭**（UI 是「开启本地识别」开关，需用户主动打开） | 实操教程 ×4【中高】 |
| 词库/模型规模 | 「识别词库量**有限**」 | 官方 FAQ【官方】 |
| 覆盖语言 | 第三方称「离线模式**仅可识别英文与数字**」 | 下载站注记【低-中】 |
| 技术底座 | 自研「基于边缘设备的深度学习量化加速压缩技术」，支持**超大类别（>20,000 类）汉字**的低存储移动端识别 | 港股招股书【官方】 |
| 成本结构 | **每次调用边际成本 ≈ 0**（纯本地算力） | 架构推断【推算】 |

> **一个有意思的反差**：招股书强调端侧「超大类别 20,000+ 类汉字」的能力，但用户侧观察到的端侧覆盖却极窄（英数）。两种解释——① 端侧模型按机型/地区分档下发；② 端侧能力主要用于 **B 端端侧 SDK / AIoT 硬件**（TextIn 端侧 SDK 覆盖 Windows/Android/iOS/AIoT），而非 C 端 App 的默认路径。**公开资料无法区分，列入缺口。**

### 2.2 服务端（云端 OCR）

| 维度 | 事实 | 来源 |
|---|---|---|
| 承担的能力 | 「精准识别」= 付费/会员向的高精度识别；配套「精准矫正」「精确查找」 | IPO 问询函【审计】 |
| 语言覆盖 | 41–50 种，在「云端文字识别语言」中配置（官方提示：**不要勾选全部语言，会降低准确度**） | 官方 FAQ【官方】 |
| 高级形态 | 表格还原、版面还原、PDF→Word/Excel/PPT、书籍模式 | 官网功能页【官方】 |
| 成本科目 | 云存储（最大项）、**弹性计算云及其他**（含推理算力）、数据传输、CDN 专线 | IPO 问询函【审计】 |
| 配额机制 | 免费账户「可使用**有限次数**的文字识别」；网页版每日 3 页（第三方口径）；**OCR 额度跨端共享** | 官方 FAQ【官方】+ 第三方【低-中】 |

**「额度跨端共享」这个细节是强信号**：端侧 OCR 无法被服务端计数，只有云端识别才需要账号级配额表。它反向证明了**主计费路径在云端**。

### 2.3 为什么这样切：四条权衡

| 权衡点 | 全端侧 | 全云端 | 扫描全能王的选择 |
|---|---|---|---|
| 包体体积 | 41 种语言模型全塞进 App → 包体失控 | 包体小 | **端侧只留最小集，多语言走云端** |
| 单次成本 | 0 | 0.005–0.05 元/次 | **免费量走端侧，付费/高精度走云端** |
| 首次响应 | 快（无网络往返） | 慢（上传+排队+推理，1–3 s） | **端侧给"应急"，云端给"结果"** |
| 隐私叙事 | 强（数据不出端） | 弱 | **端侧作为"涉密可选方案"的合规挡箭牌** |

> 注意最后一行：端侧 OCR 在国内市场的真实角色，很大程度是**给政企/涉密场景一个"数据不出端"的话术出口**——而不是主力体验。这与官网「关闭云同步后文件不再上云」的措辞边界（≠所有处理都在本地）是同一套话术结构。

## 三、各端 OCR 能力矩阵（用户问的核心）

**结论：所有"客户端"都有 OCR 结果，但只有"带本地算力的客户端"才有端侧 OCR；Web 与小程序 100% 依赖服务端。**

| 端 | 端侧 OCR | 云端 OCR | 能力/效果特征 | 证据 | 置信度 |
|---|---|---|---|---|---|
| **Android App** | ✅ 有（默认关，手动开启） | ✅ 主路径 | 端侧仅基础语种；云端 41 种语言 + 表格/版面还原 | 官方 FAQ + 教程（Android 11 / v6.31.0） | **高** |
| **iOS App** | ✅ 有（同路径开启） | ✅ 主路径 | 同上；iOS 端是否叠加 Apple Vision 做基础检测**未证实** | 教程（iPhone 14 / iOS 16.5.1；iPhone X / iOS 14.8） | **高** |
| **HarmonyOS App** | 🟡 推测有（同移动端代码路径） | ✅ 主路径 | 鸿蒙原生版已上线（下载破千万、5.0 好评），已接系统原相机、去手写、反色滤镜 | 华为/媒体稿 | **中**（未拿到端侧开关截图证据） |
| **Windows 客户端** | ✅ 有（**离线包管理**，需手动下载中英文模型） | ✅ | 第三方称支持 GPU 加速与本地 OCR；离线能力明确存在 | 下载站说明页【低-中】 | **中** |
| **macOS 客户端** | 🟡 推测有 | ✅ | 官网提供 .dmg 下载 | 官网 | **低-中** |
| **Web 版**（camscanner.com/webapp） | ❌ 无（浏览器无内置模型） | ✅ 唯一路径 | 图像处理近似专业级，OCR 继承移动端能力；每日免费 3 页 | 官网 + 第三方 | **中高** |
| **微信小程序**（含「扫描全能王文档助手」） | ❌ 无 | ✅ 唯一路径 | 「免下载、纯前端运行」，OCR 必须走云端；免费版 PDF 带水印 | 小程序商店 + 攻略 | **中** |

### 效果横向：官方没给分端数据，只有产品级数据

**必须说清：合合信息从未公开过"端侧识别率 vs 云端识别率"的对比数据。** 现有全部数字都是**产品级（默认走云端）**口径：

| 场景 | 识别率 | 口径/来源 | 年份 |
|---|---|---|---|
| 常规印刷体文档（字符平均） | **99.77%** | 招股书援引检测报告【官方宣称】 | 2024–2026 |
| 手写体文档（字符平均） | **97.00%** | 同上【官方宣称】 | 2024–2026 |
| 手写体（另一口径） | 97.7% | 券商/自媒体整理【官方宣称·二手】 | 2026H1 |
| **复杂场景字符识别率（平均值）** | **81.4% / 81.9%** | 检测报告【官方宣称】，两个版本口径不一致 | 2026H1 / 2025 |
| 常规文档 / 多语言 / 困难集（早期口径） | 99% / 99% / 95% | IPO 招股书【官方宣称】 | 2021 |
| 手写集 / 复杂场景集（早期口径） | 92% / 91% | IPO 招股书【官方宣称】 | 2021 |
| 身份证 / 驾驶证 / 出租车票 / 增值税发票（条目识别率） | 99.6% / 99.2% / 98.5% / 97.7% | 招股书【官方宣称】 | 2021–2026 |

**三条口径陷阱（PM 必读）**：

1. **「字符平均识别率」≠「文档可用率」**。99.77% 的字符准确率，意味着一页 1,000 字的文档平均仍有 2.3 个错字——**"看起来很美，用起来要校对"**。而 81.4% 的复杂场景数字，一页就要改近 200 字，基本不可用。
2. **同一个指标名，两家公司/两个年份的口径可能完全不同**。合合的 99.77% 与竞品的 "99%" 不可直接对比——数据集难度、是否含后处理、是否人工挑选样本都未披露。
3. **端侧效果没有公开数据**，只能自测。**这正是下面第四节"自测方法"的价值所在。**

### 效果自测方法（可直接执行，7 项）

| # | 方法 | 判定 |
|---|---|---|
| 1 | **飞行模式测试**：断网后识别中英文长文档 | 能出结果 = 有端侧；无结果 = 纯云端 |
| 2 | **耗时差**：同一张图分别在「开/关本地识别」下计时 | 端侧通常 200–800 ms；云端 1–3 s（含上传+排队） |
| 3 | **抓包**（Charles / mitmproxy / 小黄鸟） | 看是否有图片流上行。**注意国内 App 多走自有协议/证书绑定，可能抓不到** |
| 4 | **安装包体积 + 资源扫描**：`apktool d` 后查 `assets/` 下 `.nb/.mnn/.onnx/.tflite`；iOS 查 `.mlmodelc` | 有模型文件 = 有端侧能力 |
| 5 | **配额耗尽测试**：把云端 OCR 次数用完，再用"本地识别" | 仍可用 = 端侧真实存在且不受配额限制 |
| 6 | **设置项存在性**：是否有「本地识别」开关 / 「离线包管理」 | 有 = 端侧存在（本次已验证） |
| 7 | **App Store 隐私标签 / 隐私政策**：OCR 场景是否声明「收集文件、图片」 | 声明了 = 至少存在上传路径 |

> 第 5 项最狠：**它同时验证了"端侧存在"和"端侧不受配额约束"两件事**——如果本地识别能无限用，那它就是扫描全能王最大的免费护城河，也是它绝不宣传的原因。

## 四、财务反推：端侧分流值多少钱

用 IPO 审计数据（扫描全能王服务器成本，单位：万元）：

| 项目 | 2021年1-9月 | 2020 | 2019 | 2018 |
|---|---|---|---|---|
| 收入 | 35,604.22 | 33,343.21 | 15,125.35 | 6,205.69 |
| **服务器成本合计** | **3,305.75** | **3,063.17** | **1,668.72** | **1,419.64** |
| ├ 云存储 | 1,594.16 | 1,653.40 | 1,194.46 | 1,019.14 |
| ├ **弹性计算云及其他** | **1,063.83** | 673.76 | 267.12 | 232.25 |
| ├ 数据传输 | 377.74 | 476.15 | 109.74 | 64.83 |
| └ CDN 专线 | 214.91 | 221.38 | 79.06 | 37.09 |
| 平均月活（万） | 10,597.20 | 9,767.55 | 7,948.57 | 4,986.22 |
| 存储量（万 GB） | 11,547.65 | 10,129.78 | 6,614.64 | 5,122.46 |
| 存储文件数（万） | 3,607,131.71 | 2,508,311.87 | 1,268,483.26 | 708,519.14 |

**关键读数**：
- 云存储占比 **48.2%**（2021 年 1-9 月），是服务器成本第一大项 → **扫描全能王的成本主体是"存"，不是"算"**。
- 弹性计算云占比 32.2%，且 2018→2021 增长 **4.6 倍**，与收入增速（5.7 倍）基本同步。
- 服务器成本/收入比从 2018 年 **22.9%** 降至 2021 年 **9.3%** → 规模效应 + IDC 自建替代云。
- 折算：**每 MAU 每月服务器成本 ≈ 0.035 元**（2021），其中算力部分 ≈ **0.011 元/MAU/月**。

**端侧分流的经济学（详见附 B）**：
- 若把免费用户基础 OCR 全部放云端，按 2021 年 MAU 1.06 亿 × 月 5 次 × 0.01 元/次 ≈ **530 万元/月 = 6,360 万元/年**——是当年全年服务器成本的 **1.6 倍**。
- **结论：免费额度 + 端侧兜底，不是产品设计偏好，是成本结构倒逼的必然选择。**

## 五、开源可替代方案（分层清单）

### 5.1 端侧（可嵌入 App，离线运行）

| 方案 | 许可 | 模型体积 | 中文表现 | 适合平台 | 实时指标 |
|---|---|---|---|---|---|
| **PaddleOCR（PP-OCRv5/v6 mobile）** | **Apache-2.0** | det ≈3 MB + rec ≈14 MB（FP32）；INT8 ≈1 MB + 4 MB | **强**（印刷体最佳；手写偏弱） | Android/iOS/桌面/嵌入式 | GitHub **90,932★**，2026-09-16 活跃 |
| **RapidOCR**（PP-OCR 模型的 ONNX 版） | **Apache-2.0** | 同 PaddleOCR（ONNX） | 强（≈PaddleOCR） | 同上，部署最轻 | **8,111★**，2026-10-11 活跃 |
| **Google ML Kit Text Recognition v2** | 免费 SDK（模型 Apache-2.0） | ≈2–5 MB | 中上；支持中文/日文/韩文/拉丁 | Android / iOS（**Android 依赖 GMS**） | 官方标称端侧；无手写 |
| **Apple Vision（VNRecognizeTextRequest）** | 系统框架，免费 | 0（系统内置） | 中上；**18 种语言含简繁中文** | iOS / macOS 专属 | fast ≈200–400 ms / accurate ≈800–1,200 ms（A14+ 准确率约 92%） |
| **Tesseract 5.x** | **Apache-2.0** | 中（+语言包 2–50 MB） | **弱**（中文明显落后：实测约 62%） | 全平台 | 单一对比中 50 字样本仅 48/50 正确 |
| ncnn-android-ppocrv5（现成 demo） | 依 ncnn | 同 PP-OCRv5 | 强 | Android | 201★，2026-05-27；ncnn 本体 23,937★ |

> **取舍要点**：中文场景**不要在 Tesseract 上浪费时间**。端侧首选 **PaddleOCR→ONNX（RapidOCR 路线）**；iOS 独占场景可用 **Apple Vision** 做零成本起步；Android 建议 **ONNX Runtime**（避开 GMS 依赖）。

### 5.3 移动端部署三条路线

| 路线 | 推理底座 | 模型格式 | 适用 | 评价 |
|---|---|---|---|---|
| **① ONNX Runtime**（推荐） | onnxruntime-android/iOS | `.onnx` | 绝大多数新项目 | 跨 iOS/Android 共用一套模型；SDK 可直接打成 AAR；minSdk 24–26 |
| ② ncnn | ncnn + opencv-mobile | `.param/.bin` | 要 GPU 加速 / 想跑现成 demo | Vulkan 加速；nihui 已有 PP-OCRv5 完整工程 |
| ③ Paddle-Lite | Paddle-Lite 2.10 | `.nb` | 存量 .nb 模型工程 | 工具链偏重、活跃度走低，新项目不推荐 |

**端侧实测锚点**（第三方公开数据，非本机实测）：
- PP-OCRv5 在 Android 9 真机全链路均值约 **420 ms**；官方 benchmark 口径。
- 嵌入式对比表中 PaddleOCR 轻量版 CPU 单张约 **80 ms**、RapidOCR 约 **60 ms**（不同测试集，仅作量级参考）。
- INT8 量化：识别模型 14 MB → 约 4 MB，速度提升显著，**识别精度损失约 1–3%，检测损失 3–8%**（建议：检测用 FP16/FP32、识别用 INT8）。

### 5.4 开源方案与扫描全能王的真实差距

| 能力 | 开源覆盖 | 差距判断 |
|---|---|---|
| 基础印刷体识别 | ✅ 已反超（PaddleOCR 生态） | **无差距** |
| 端侧部署 | ✅ 完整可行（ONNX/ncnn） | **无差距** |
| **端侧超大字符集（>20,000 类）低存储方案** | ❌ 无对应公开方案 | **真实壁垒**（合合专利/招股书明确披露） |
| **图像增强链**（去摩尔纹、去手写、曲面矫正、反光消除） | 🟡 部分（OpenCV + 研究级） | **明显差距**（合合拿下 CVPR 2026 NTIRE 反光消除赛道冠军） |
| 手写体 | 🟡 弱 | **差距**（合合官方 97.0%，开源普遍 82–95%） |
| 表格 / 版面还原 | ✅ PP-StructureV3 / MinerU 可覆盖大部分 | 小差距 |
| 多端同步 + 云存储 | 🟡 需自建（成本主体！） | **差距在工程与成本，不在算法** |

**一句话**：**开源能让你一周内做出「能用的 OCR」，但做不出「扫描全能王的 OCR 产品」。** 卡点在端侧大字符集、图像前处理、以及那 48.2% 的存储成本。

## 附 B：测算过程与敏感度（与实测分开）

**B1. 每 MAU 每月服务器成本**
```
2021年1-9月：3,305.75 万元 ÷ 9 个月 ÷ 10,597.20 万 MAU = 0.0347 元/MAU/月
2020 年：    3,063.17 万元 ÷ 12 个月 ÷ 9,767.55 万 MAU = 0.0261 元/MAU/月
2019 年：    1,668.72 万元 ÷ 12 个月 ÷ 7,948.57 万 MAU = 0.0175 元/MAU/月
```
→ 单位成本随规模下降，说明基础设施存在明显规模效应。

**B2. 算力部分单位成本**
```
2021年1-9月 弹性计算云及其他 1,063.83 万元 ÷ 9 ÷ 10,597.20 万 = 0.0112 元/MAU/月
```

**B3. 云存储单价反算**
```
2021年1-9月：1,594.16 万元 ÷ 11,547.65 万 GB = 0.138 元/GB（9个月）≈ 0.184 元/GB/年
```
→ 单价极低，印证问询函所述「标准存储改低频/深度冷冻 + JPEG→WebP 压缩约 50%」的降本动作。

**B4. 免费用户云端 OCR 成本的假想上限（关键推算）**
```
假设：MAU 10,597 万 × 每人每月 5 次 OCR = 52,985 万次/月 ≈ 5.3 亿次/月
按行业通用 OCR 边际成本 0.01 元/次：
  5.3 亿 × 0.01 = 530 万元/月 = 6,360 万元/年
对比：2021 年全年服务器成本估算 ≈ 3,305.75 ÷ 9 × 12 ≈ 4,408 万元
→ 单这一项即为全年服务器成本的 1.44 倍
```
**敏感度（单价 ±）**：

| 单次成本假设 | 年成本（月 5 次/人） | 相对当年服务器成本（≈4,408 万） |
|---|---|---|
| 0.005 元 | 3,180 万元 | 0.72×（勉强可承受 → 但需无私家算力） |
| **0.01 元** | **6,360 万元** | **1.44×（不可行）** |
| 0.02 元 | 1.27 亿元 | 2.9× |
| 0.05 元 | 3.18 亿元 | 7.2× |

**结论稳健性**：即使把假设放宽到「免费用户人均每月仅 1 次 OCR」，0.01 元/次口径下年成本仍达 1,272 万元，相当于当年服务器成本的三成——**结论不翻转**：**免费量必须靠端侧消化。**

**假设前提声明**：① 0.01 元/次来自通用 OCR 云服务的量级锚点，非合合实际成本（合合自建 IDC，实际单位成本应显著更低）；② 「人均月 5 次」为假设值，无公开数据支撑。**这两个假设是本节最脆弱的两点，但即使各下调 80%，结论方向不变。**
