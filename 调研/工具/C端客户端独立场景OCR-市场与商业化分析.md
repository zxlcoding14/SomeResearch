## 〇、结论先行（TL;DR）

**1. 能做，而且这一层是三份报告里唯一能拿到"一手用户原声"的一层——但它也是商业上最不成立的一层。**
因为它同时具备三个"可取证"条件（有 GUI 客户端可测、有开源仓库可查、有论坛长帖可读），也同时承受三重结构性压制：**OS 内置 + 即时通讯内置 + 开源免费 + 大模型客户端（四重包夹）**。这是「被 OS 内置 = 品类死亡判决」在本项目里的**第六次验证**（前五次：虚拟桌面、磁盘清理、重复文件查找、PDF 阅读器、截图）。

**2. 「客户端独立使用」这个限定词本身就指向了天花板：独立 = 无账号 = 无持续交付 = 只能买断 = 收不到第二次钱。**
与 PopDrop（纯本地投递工具）、虚拟桌面、磁盘清理同构。**国产独立客户端的定价锚点已经塌到 ¥30–59 一次买断**（白描 ¥30/¥40、天若OCR ¥59、迅捷 ¥88 终身），且全部可被 ¥0 覆盖。

**3. 2026 年这条线发生了一次「形态替换」，换的是"层"不是"功能"。**
新入局者（Cheese! OCR / ClariRec / HushSnap / ImgPeel / GhostText）**无一例外都是"薄壳 + 系统或本地免费引擎"**，定价 **$0–$9.99**，靠 Apple Vision / GLM-OCR / 微信 OCR 白嫖引擎；而传统"自带引擎的桌面客户端"（Umi-OCR 440MB、PandaOCR、ScreenOCR）**要么太大、要么停更**。
> 硬证据：**Umi-OCR 47,537★，但 `pushed_at` 停在 2025-11-20 —— 已 10 个月零提交**；ScreenOCR 作者不再维护；PandaOCR.Pro 转收费后免费版砍掉大模型接口。

**4. 最反常识的一条：精度已经不是差异化，而「本地模型 = 精度下降」是用户实测结论。**
论坛长帖原文：*"只要模型转为本地，识别能力就会大大下降。"* 这直接否定了「本地 + 隐私 + 高精度」三合一的叙事前提——三者不可同时成立，必须选二。

**5. 真实付费理由只有三个，且没有一个是"OCR"。**
① **结构化交付**（手写/竖排/表格/公式能不能直接用）；② **隐私**（合同/证件/病历不出本机）；③ **懒**（快捷键一步到剪贴板）。而**中文区的实际标准是微信截图 OCR**，用户原话：*"还是微信的截图识别文字在不那么清晰的时候，效果还是相对较好的。"*

**6. 包体撕裂成两个极端，两个极端都没赢。**
夸克扫描王 PC 版 **2.44MB** / 迅捷OCR 联想渠道 **3.65MB**（= 下载器壳 + 云端处理）↔ 扫描全能王 PC 版 **149MB** / Umi-OCR **约 440MB**（= 端侧引擎）。**相差 120 倍**。小包口碑差（交付墙 + 云端成本敞口），大包收不到钱（对标免费开源）。

**7. 可进场位置只剩三条，且都不在"识别"上。**
**P0 「OCR 之后的交付」**（截图表格→Excel、公式→LaTeX、报错码→检索、排版→Markdown）；**P0 「大模型客户端 + 5MB 极简壳」**（用户已自建：Cherry Studio + glm-4.6v-flash 免费，*"1 秒不到，精确度非常高"*）；**P1 竖排/古籍/漫画/日文**（论坛 1,502 + 1,045 次浏览全在问这个，而 *"Umi-OCR 识别竖排日文的能力为零，完全不可用"*）。

## 一、先立口径：这道题问的是什么，不是什么

用户问的是"**C 端用户、客户端、独立使用的场景下的 OCR**"。这句里有三个限定词，每一个都在缩小范围，必须显式切开，否则必错。

| 维度 | **属于本题** | **不属于本题（本系列前作已覆盖）** |
|---|---|---|
| 付费主体 | 个人用户自费（C 端） | 企业采购 / API 调用计费（B 端） |
| 交付形态 | 独立桌面客户端（Win/macOS GUI） | 云 API（纯 OCR 能力市场）、网页一次性工具、移动 App、SaaS 尾巴 |
| 使用模式 | **单机独立**（不依赖账号/联网即可完成主任务） | 账号绑定型订阅（扫描全能王 PC 版属灰色地带，见 §5） |
| 任务规模 | 单张 / 少量（≤几百） | 数十万至数亿页的批量工程（政企招标、档案数字化） |
| 价值主张 | 顺手、隐私、够用 | 确定性、字段完整率、兜底责任 |

**关键定义**：「独立使用」= **桌面客户端能脱离账号与云端独立完成主任务**。这条定义直接决定了商业化后果——**独立 = 无法计费到账号 = 无持续交付成本 = 只能一次性买断**。这是本报告全部结论的起点。

> ⚠️ **一个必须提前说明的口径事实**：**"C 端桌面 OCR 客户端"这一层，全球没有任何一份市场报告单独统计它**（见 §2.1）。这不是数据没找到，而是**这个细分小到不值得被单独建模**。这本身就是第一条结论。

### 2.3 需求侧：真实使用频次与付费意愿

**频次**（从论坛帖自述提取，为一手）：高频工作者**每天 10–30 次**（*"最多一天只识别少于30次"*）；普通用户"一年用两次"（*"大多数人偶然发现 Live Text，然后一年用两次"*）。

**这是一个致命的结构**：**高频用户少 + 低频用户不需要付费 + 免费替代充足 = 付费池极薄。**

**付费意愿的间接证据**：白描总用户 **1,000 万+**、华为应用市场近 **1,500 万次安装**、App Store 约 **4.9 分 / 4.2 万条评分** —— 而它的定价是 **¥30 / ¥40 一次性买断**。一个千万级用户量的工具，定价只有 30 元且不设续费。**这是独立开发者能拿到的最好结果，也是这条赛道的天花板画像。**

## 四、功能差异矩阵 + 场景覆盖

### 4.1 「独立客户端」场景下的功能维度

| 功能维度 | 意义 | 免费替代是否覆盖 | 是否可收费 |
|---|---|---|---|
| 快捷键截图取字 | 最高频入口（"懒"的价值） | ✅ 全覆盖（Win+Shift+T / 微信 / 实况文本） | ❌ |
| 截图后**自动复制到剪贴板**（不弹窗） | 减少一次点击，真实痛点 | ⚠️ 部分（PowerToys 可设；Live Text 需选中） | ❌（属基础体验） |
| 多区域连续捕获 | 长文档/多栏 | ⚠️ 少 | 🟡 弱 |
| 剪贴板图片直接识别 | 免存盘 | ✅ 多数已支持 | ❌ |
| PDF 加文字层（可搜索PDF） | 学术/合同刚需 | ✅ ocrmypdf / ABBYY（**用户实测 ocrmypdf "很方便"**） | ❌ |
| **表格 → Excel** | 财务/行政刚需 | ⚠️ 弱（**白描"表格识别是很多用户提到最惊喜的功能"**） | ✅ **强** |
| **公式 → LaTeX** | 科研刚需 | ⚠️ 弱（天若专业版需自配密钥；ClariRec 免费仅 20 次/月） | ✅ **强** |
| **竖排 / 日文 / 古籍** | 极窄刚需 | ❌ **几乎零覆盖**（见下） | ✅ **强** |
| 手写体 | 笔记/单据 | ⚠️ 弱且不稳 | 🟡 中 |
| 代码截图识别（保缩进） | 开发者刚需 | ❌ 覆盖差 | ✅ 中 |
| 离线 / 隐私（不出本机） | 合同/证件/病历 | ✅ 开源全覆盖 | ❌（免费已给） |

**读法**：**能收费的只剩三格——表格、公式、竖排/古籍；加上一格"代码"和半格"手写"。其余全部已被免费层覆盖。**

### 4.2 竖排 / 日文这一格：147,537★ 的开源项目都做不到

论坛 **T62706**（1,502 浏览 / 26 层）与 **T64879**（1,045 浏览 / 29 层）全部聚焦这一需求，关键原声：

- 需求原话：*"**纯本地**，不要调用 API 的软件；识别能力是第一优先级；支持横板和竖版日文；操作简单，像天若那样能框选区域自动识别"*
- 对 Umi-OCR 的实测否定：*"我刚刚试了 Umi-OCR，发现其**识别竖排日文的能力为零，完全不可用**。"*
- 唯一被认可的国产商业客户端：*"**白描** 竖排断句上有一点小瑕疵，但是问题不大，**识别率比 ABBYY 15 要强一点**"*
- 学术界仍在手工：1921 年毛笔手稿，*"别提 OCR 了，恐怕没接触过类似文字的普通人也难以识读"*、*"这个恐怕**纯手打反而是最快的**"*

**这是本报告里唯一"零竞争 + 高强度需求 + 用户愿意为本地与精度付费"的格子。** 但它窄到只能养一个独立开发者，养不了公司。

### 5.1 能力：识别精度已是负数资产

| 指标 | 数值 | 含义 |

## 八、收入状况、商业模式与整体市场判断

### 8.1 这一层收不到钱的四条结构性原因

1. **引擎是借来的。** 系统引擎（Apple Vision / Windows OCR）免费、开源引擎（PaddleOCR / Tesseract / GLM-OCR）免费、大模型算力用户自付。产品方**在成本上没有任何议价空间**。
2. **独立 = 无账号 = 无法计费。** "客户端独立使用"排除了账号体系，也就排除了订阅、云存储、续费管理——**唯一可收的钱是一次性买断，而买断等于永久封印第二次收入**。
3. **免费替代 ≥8 条，且其中 3 条是 OS 自带。** 这是本项目**第六次**验证「被 OS 内置 = 品类死亡判决」。
4. **精度已无差异化，且"本地换精度"被用户实测确认。** 唯一曾经能撑价的"本地 + 高精度"叙事在工程上不成立。

### 8.2 三个可进场位置（按优先级）

| 优先级 | 方向 | 为什么 | 定价建议 | 风险 |
|---|---|---|---|---|
| **P0** | **「OCR 之后的交付」**：截图表格→Excel、公式→LaTeX、代码→保缩进、报错码→检索、多栏→Markdown | 全行业只做到"输出文本"，**没有一家做到"输出可直接用"**；论坛需求已明确（表格是白描"最惊喜"功能） | **一次性买断 ¥39–99**（对应 TextSniper/ZenOCR 的 $7.99–12.99 档） | 大模型客户端可能吞掉这一步 |
| **P0** | **「大模型客户端 + 5MB 极简壳」**：把 Cherry Studio + 视觉模型那条链路压成一个应用 | **用户已自建且验证有效**（*"1 秒不到，精确度非常高"*）；痛点原文是*"期待出现一个用大模型的极简OCR软件"*，*"大小：10-50MB 左右"* | **免费 + BYOK**（用户自付 token）→ 或用 credits 计费 | BYOK 决定"无持续成本"，也就决定收不到订阅费 |
| **P1** | **竖排 / 古籍 / 日文 / 漫画**：本地引擎 + 断句后处理 | 47,537★ 的 Umi-OCR 在这一格 *"能力为零"*；需求真实（1,502 + 1,045 浏览） | **一次性买断**（该人群愿付溢价） | 池子极小，只够养一个独立开发者 |

### 8.3 ❌ 明令回避

- **又一个"能截图识字的客户端"**（8 条免费通道已饱和，ShareX / Umi-OCR 全覆盖且免费开源活跃）
- **把"识别更准"当卖点**（开源已反超商业云；用户以微信为基准线，差异感知为零）
- **纯本地客户端挂年费/订阅**（无持续交付成本，用户一眼看穿；本条线所有挂订阅的要么依赖云，要么是 SaaS 尾巴）
- **付费墙设在"导出/复制"环节**（迅捷OCR 模式：转化最优、口碑最差，直接催生"免费版不可用"的畸形设计）
- **下载器壳 + 云端处理**（2.44–3.65MB 那一路：必有次数限制、必有终身无限次的负毛利敞口、客户端差异化不可能来自端侧）
- **翻译 / TTS / 屏幕录制等附加功能**（用户明确不要：*"不要翻译功能，翻译全用 AI 客户端工具了"*；这些功能还会把包体推回 100MB+）

### 8.4 坦率的负结论

> **做"用户端独立客户端 OCR"的期望 ROI 结构性 < 1。**
> 理由：**GhostText 全赛道唯一公开真实数字——3 个月 $196、200+ 用户。** 这是一个人在没有融资、没有受众的情况下做出的"真实且健康"的结果，而它同时也是这个品类的**天花板画像**：用户愿意付费，但付得极少；产品不是玩具，但也长不成生意。
> 唯一的例外路径是：**不要把它当产品，把它当分发通路** —— 用免费 OCR 壳换装机量与品牌，在"交付层"或"B 端责任层"变现（扫描全能王 PC 版走的就是这条路，但它有 1.99 亿 MAU 的母体做支撑，单体创业者没有）。
