## 〇、结论先行（TL;DR）

> ## **这是一款「外壳极简、内核极重」的产品。UI 层 1 个人 2 周能抄完，但它 90% 的护城河不在 UI 里 —— 在 110 万条食物库、AI 宠物的内容资产、和 11 年沉淀的评分上。复刻的正确姿势不是「照着做一遍」，而是「照着它的体验骨架，换一套轻资产内核」。**

**1｜功能结构是「三层同心圆」，且只有最内层值得抄。**
- **内环（灵魂，1 个）**：AI 宠物搭子 —— 它是**唯一支撑 28.15% 三日留存**的功能，也是**唯一复刻成本高到不该由个人承担**的部分。
- **中环（骨架，5 个）**：体重记录 / 饮食记录 / 趋势分析 / 减肥食谱 / 轻断食 —— 这是产品的「功能主体」，也是**复刻的合理标的**。
- **外环（可砍，6 个）**：社区 / 体围 / 形体照 / 习惯打卡 / 运动记录 / 极速版 —— **对留存贡献边际，却是工程与合规负担**。

**2｜【否定性结论】不要复刻它的「全貌」，只复刻它的「iOS 系统级打卡体验 + 记录内核」。**
理由：① 110 万条食物库从公开数据源（1,700 条）补齐需要 **647 倍**的采集量；② AI 宠物需要**美术 + 动效 + 状态机 + 文案**四套内容资产，工时 **3–5 人月**、且对个人版营收贡献极低（前序报告已量化）；③ 社区功能会把**内容审核责任**揽上身，是个人开发者最不该碰的一块。**抄「打开就记、10 秒完成」这一件事，就抄到了它 60% 的用户价值。**

**3｜iOS 端真正的差异化不在 App 里，在「App 之外」——这是本次拆解最重要的发现。**
它把打卡入口搬到了**桌面小组件 / 锁屏小组件 / 实时活动 / Apple Watch** 四处（官网与更新日志双重证实）。后果是双面的：**活跃被系统性外溢（第三方 DAU 低估它）**，但**广告变现被同时切掉**（系统层不产生曝光）。对复刻者的含义是：**这套系统集成是 iOS 端最值得抄的一段（它直接决定留存），但它与「广告变现」天然互斥 —— 抄它，就等于选择订阅制、放弃广告制。**

**4｜付费墙的形状已经明确了：功能墙 + 体验墙的混合体，且免费层「够用但不完整」。**
实测 8 个 IAP SKU（¥12/月 – ¥168 永久），第三方实测与逆向记录共同指向三条**会员专属线**：**AI 拍照识别、AI 自动打卡、完整食谱内容（非会员只看介绍）**。**体重记录、趋势图、基础饮食记录是免费的** —— 这是它「7 万人打出 4.89 分」的前提，也是复刻时**不能动的一条红线**：免费层一旦缩水，评分优势立刻消失。

**5｜对复刻者，本合同最该记住的是一个数字：`MVP ≈ 6–8 人月`（含 AI 编码助手提速后，个人可压缩到 4–8 周）。**
前序报告已给出三档总价（MVP ¥15–28 万 / 体验对齐 ¥63–137 万 / 全量对齐 ¥90–160 万）。本文在这一基础上做了一件前序报告没做的事：**把 MVP 拆成了一张 AI 可以直接执行的页面级 / 字段级任务清单**（§六）。**结论是：MVP 里 80% 的页面都是 CRUD + 图表，AI 编码助手能在数周内完成；真正卡人的只有「食物库冷启动」和「AI 宠物的内容资产」两项——而这两项，MVP 建议直接砍掉或降级。**

## 二、产品形态与信息架构

### 2.1 一句话定义（不贴品类词）

> **它是一个「用一只会成长的宠物，换你每天站上秤台那 10 秒」的工具 —— 记录是手段，坚持才是产品。**

（刻意不用「体重管理 App」这类品类词：品类词会掩盖它真正的差异 —— **它卖的不是记录功能，是「明天还想打开」的动机**。）

### 2.2 界面哲学的官方自述（③ 官方宣称，原文）

- 「我们不想做一个大而全的功能杂货铺，只想把『体重管理』这一件事做好。」
- 「打开就能记录，不用在复杂的菜单里翻找。」
- 「极简不是简陋，而是让你专注于真正重要的事，把精力花在坚持上，而不是花在操作 APP 上。」

> **PM 判读**：这三句是**设计约束**，不是口号。它直接规定了复刻时的**交互红线** —— **任何需要二次跳转才能完成打卡的设计，都违背了它的产品哲学**。这条红线在 §六 的页面规格里被逐页落实。

### T1 内核层

#### 3.1.1 体重记录（产品的「中心功能」）

| 项 | 内容 |
|---|---|
| **功能定义** | 以「超大数字面板」为核心入口，秒级完成一次体重录入 |
| **已证实细节**（③ 官方 + ② 实测） | ① 超大数字面板轻松记录；② **支持每日多条记录**；③ 支持**斤 / 公斤 / 磅**三单位切换；④ **支持两位小数**；⑤ 支持**自定义体重标签**（如「晨起」「睡前」「运动后」）；⑥ 支持**自定义首页皮肤** |
| **交互流程**（② 二手实测，安卓端教程） | ① 首页点击圆形快捷区 → ② 呼出数字键盘（默认上次值）→ ③ 输入体重 → ④ （可选）选标签 → ⑤ 完成，回首页刷新概览与柱状图 |
| **补记流程** | 首页左右滑动切换周视图 → 点击目标日期的柱状条 → 弹出补记面板 → 录入 |
| **数据字段**（建议模型） | `id` / `user_id` / `weight_value`（Decimal(5,2)）/ `unit`（斤\|kg\|lb，**存储统一为 kg，展示时换算**）/ `tag`（自定义标签，可空）/ `measured_at`（时间戳，精确到分钟）/ `created_at` |
| **业务规则** | ① 每日多条 → 趋势图默认取「当日首条或均值」（需明确口径，**官方未披露，列为缺口**）；② 单位切换 **只影响展示，不改存储**；③ 数值范围校验（建议 20–300 kg，超出告警）；④ 同一时间戳重复录入 → 覆盖确认 |
| **难度** | 低 |
| **复刻取舍** | ✅ **必抄**。这是产品的定义性功能。**注意保留「默认上次值 + 一键确认」这个降摩擦细节** —— 它是「秒记」体验的来源 |

| **细节**（③ 官方 + ② 二手） | 与形体照配套；用于「塑形」人群区分于「减重」人群 |
| **数据字段** | `id` / `user_id` / `part`（枚举：腰\|臀\|大腿\|胸\|臂\|自定义）/ `value_cm` / `measured_at` |
| **难度** | 低 |

#### 3.1.3 形体对比自拍

| 项 | 内容 |
|---|---|
| **功能定义** | 上传 / 拍摄形体照，按时间对比身材变化 |
| **细节**（③ 官方 + ② 二手） | 「支持上传形体自拍照，制作对比照」；**本地存储 + 云端备份** |

| **难度** | 低（功能）／中（隐私合规） |
| **复刻取舍** | ⚠️ **可砍**。合规成本 > 功能价值，个人开发者**强烈建议不做** |

#### 3.1.4 趋势分析 / 健康分析（产品的「价值兑现层」）

| 项 | 内容 |
|---|---|
| **功能定义** | 把流水记录转成「看得见的进步」 |
| **已证实细节**（③ 官方 + ② 实测） | **六种可视化**：① 体重列表；② **柱形图**；③ **趋势线（曲线图）**；④ **百分比圆环**；⑤ **月度掉秤率**；⑥ **体重饮食日历**（把体重与当天饮食并列） |
| | **自动 BMI 计算**（身高 + 体重）；**目标进度追踪**；**月度对比** |
| | 「自动匹配你的当前体重并智能检测营养搭配比例」（饮食侧联动） |
| | 「对不同的食物是如何影响到体重变化进行**个性化分析**」 |
| **交互** | 记录页日历选日期 → 进入当日详情；首页滑周视图；图表可切换周期 |
| **数据字段** | BMI = `weight_kg / (height_m)^2`（身高存 `user.height_cm`）；掉秤率 = `(期末 − 期初) / 期初` |
| **难度** | 中（图表聚合 + 时间轴处理） |
| **复刻取舍** | ✅ **必抄（但可精简）**。MVP 只需**趋势线 + 柱形图 + BMI + 目标进度**四种；`体重饮食日历` 与 `个性化食物影响分析` 属 T2/T3，MVP 后置 |

### T2 扩展层

#### 3.2.1 饮食记录 + AI 拍照识别（**会员专属线之一**）

| 项 | 内容 |
|---|---|
| **功能定义** | 「拍张照片，AI 自动识别食物并估算热量」 |
| **已证实细节**（③ 官网原文） | ① 拍照 → **AI 自动识别食物 + 估算热量**；② **三餐 + 加餐 + 饮水**一目了然；③ **运动消耗同步记录**；④ 「不需要称重、不需要查表」；⑤ 长期形成「饮食档案」：**哪些天吃多了 / 蛋白质够不够 / 外卖比例有多高** |
| **营养检测**（② 二手） | 登记进食时**自动提示碳水 / 蛋白质 / 脂肪摄入比例是否科学均衡** |
| **会员边界**（⑤ 二手：第三方实测 + 逆向帖） | **「AI 拍照识图」被列为会员专属**（原文：「普通用户需付费开通永久会员方可解锁 AI 拍照识图、AI 自动打卡、个性化减重指导等高级功能」）→ **免费层只能手动搜索添加食物** |
| **交互流程** | ① 点饮食卡片 → ② 选餐次（早/中/晚/加餐）→ ③ 三个入口：**拍照识别** / 搜索食物库 / 手动输入 → ④ 选分量（份 / 克 / 拳 / 碗）→ ⑤ 自动汇总当日热量与三大营养素 → ⑥ 与目标对比显示进度 |
| **数据字段** | `meal_record`：`id` / `user_id` / `date` / `meal_type`（枚举 6 值：早/中/晚/上午加餐/下午加餐/晚上加餐）/ `total_kcal` / `created_at` |
| | `meal_item`：`id` / `meal_record_id` / `food_id` / `food_name` / `quantity` / `unit` / `kcal` / `carb_g` / `protein_g` / `fat_g` |
| | `water_record`：`id` / `user_id` / `date` / `amount_ml` |
| **业务规则** | ① 拍照识别返回**候选列表 + 置信度**，需用户确认（不能全自动，错误率是口碑杀手）；② 未匹配食物 → 落库为「自定义食物」并可分享到社区（**UGC 食物库的增长机制**）；③ 当日热量 = 所有 meal_item 求和 |
| **难度** | **中高**（依赖视觉模型 + 食物库匹配 + 分量估算） |
| **复刻取舍** | ⚠️ **MVP 降级为「搜索 + 手动」，AI 拍照放到 V1**。理由：识别准确率不足会直接伤评分；且拍照识别是**云成本项**（边际成本红线） |

#### 3.2.2 食物库（**最大的资产，也是最大的复刻陷阱**）

| 项 | 内容 |
|---|---|
| **已证实规模**（③ 官方宣称） | **官方 50 万种 + 社区 UGC 60 万种 = 110 万条** |
| **公开可采数据**（④ 前序报告实测） | 中国食物成分表仅 **1,506–1,700 条**（字段 31–118 项）→ **差距 647 倍** |

| **难度** | **高**（前序报告估 4–8 人月） |

#### 3.3.1 AI 宠物搭子（**产品的灵魂，也是复刻的最大诱惑与最大陷阱**）

| 项 | 内容 |
|---|---|
| **官方原文**（③ 官网，全文保留） | 「从你第一次打开 APP 的那一刻起，一颗专属的**宠物蛋开始孵化** —— 它会在你的陪伴下**破壳、成长**，成为你独一无二的减肥伙伴……**掉秤了，它会手舞足蹈地为你庆祝；遇到平台期，它会送上暖心的鼓励；你好几天没记录，它会担心地望着你。**它会**记住你每一次站上秤台的勇气**……每天打开 APP，都有新的惊喜等着你 —— 或许是它**学会了新表情**，或许是它为你准备了**一份小礼物**。」 |
| **机制拆解**（本次分析新增） | 它是**四套内容资产**的合成：① **美术资源**（多状态角色 + 表情）；② **动效系统**（庆祝/鼓励/担心）；③ **情绪状态机**（掉秤/平台期/断更/里程碑 → 状态切换）；④ **文案库**（覆盖各场景的台词） |
| **触发规则**（推导） | `掉秤` → 庆祝动画 + 台词；`平台期（连续 N 天无下降）` → 鼓励；`断更（>N 天未记录）` → 担忧表情；`里程碑（累计打卡 N 天 / 掉秤 X 斤）` → 礼物 |

| **难度** | **高**（前序报告估 3–5 人月，**工时最不可压缩**） |
| **复刻取舍** | ⚠️ **这是全篇最需要克制的一项判断**。它是 28.15% 留存的核心驱动，**砍掉它产品就退化成又一个记录工具**；但它需要**美术 + 文案 + 动效**三样非技术资产，且对个人版营收贡献极低。**建议：MVP 用「轻量版宠物」（静态形象 + 3–5 个状态 + 模板化文案），把「多表情 / 礼物系统」推到 V2。** |

> **★ 一个可直接执行的替代方案**（本文新增，见 §6.5）：
> 把「美术 + 动效」**降级为「文字 + Emoji + 一张主形象图」**，用 **LLM 动态生成台词**替代静态文案库。这样保留「它记得我、它在回应我」的核心情绪价值，而把成本从「3–5 人月的内容生产」压缩到「1 个状态机 + 1 个 Prompt」。

## 四、iOS 端系统集成的详细设计规格

> 本节是**复刻文档中最有增量价值的一节** —— 前序报告只指出了「有这些入口」，本节给出**每个入口的规格**。

### 4.1 桌面小组件（WidgetKit）

| 尺寸 | 建议展示 | 交互 | 实现要点 |
|---|---|---|---|
| Small | 今日体重 + 距目标进度环 | 点击 → 直达体重录入 | `AppIntent` 配置 + `TimelineProvider` |
| Medium | 体重变化曲线（近 7 天）+ 今日饮食热量 | 点击分区 → 对应页面 | 曲线用 `Path` 手绘或 Swift Charts |
| Large | 目标达成率 + 三项打卡（体重/饮食/运动） | 分区点击 | 「左上角配置显示达成率」（官网原文）→ 支持 `AppIntentConfiguration` |

**技术约束**：iOS 15+ 支持小组件；**一键打卡需要 `AppIntent`（iOS 17+）**；旧系统降级为「点击跳转」。

### 4.2 实时活动（Live Activity）

- **适用场景**：轻断食计时器（最佳载体）、饱腹感计时
- **形态**：锁屏常驻卡片 + 灵动岛（iPhone 14 Pro+）
- **关键细节**（官网原文）：「**饱腹感实时活动的完成细节，支持打卡后主动消失**」→ **打卡完成即结束活动**，不做残留
- **技术**：`ActivityKit` + `ActivityAttributes`；**注意 iOS 16.1+**

### 4.3 Apple Watch

- **能力**：抬腕查看体重 / 体脂 / 步数；快捷打卡
- **技术**：`WatchConnectivity` 或 **Watch App 独立 Target**；数据经 HealthKit 或 CloudKit 同步

### 4.4 HealthKit 双向同步

| 方向 | 动作 | 注意 |
|---|---|---|
| 写入 | App 记录体重 → 写 `HKQuantityType(.bodyMass)` | 需用户授权写权限 |
| 读取 | 读取体重/体脂/步数 → 合并进 App | 需读权限 |
| **审核风险** | 健康数据用途必须在**隐私清单**声明；**不得用于广告** | 苹果对此极严，误用会被拒 |

### 4.5 AI 语音打卡

- **形态**：语音输入体重（「今天 65.2」）→ ASR 转文本 → 解析数值 → 确认

### 6.4 AI 宠物状态机（可直接实现的规格）

**状态定义**

| 状态 | 触发条件 | 表现 | 台词方向 |
|---|---|---|---|
| `egg` | 新用户 | 蛋，轻微晃动 | 欢迎语 |
| `celebrating` | 本次体重 < 上次记录 且 降幅 ≥ 0.3kg | 跳跃/烟花（轻量版：🎉 Emoji + 放大动效） | 庆祝 |
| `happy` | 本次体重 ≤ 上次，降幅 < 0.3kg | 微笑 | 肯定 |
| `encouraging` | **连续 ≥ 3 次记录无下降（平台期）** | 加油手势 | 鼓励 |
| `worried` | **距上次记录 > 3 天** | 担忧表情 | 关心 + 提醒 |
| `milestone` | 累计打卡达 7/30/100/365 天，或累计掉秤达 1/5/10 kg | 礼物/庆祝 | 里程碑 |
| `idle` | 无特殊事件 | 待机 | 日常问候 |

**优先级**：`milestone > celebrating > worried > encouraging > happy > idle`

**成长规则**（建议）
```
exp += 10  (每次录入体重)
exp += 20  (完成一日饮食记录)
exp += 50  (连续打卡满 7 天)
stage: egg(<100) → hatched(100-499) → growing(500-1999) → adult(≥2000)
```

**「它记得」（关键情绪点）**：台词生成时**必须注入用户历史上下文**（连续打卡天数、累计掉秤、上周同期对比），这是官方评论中被用户明确称赞的细节。

### 6.5 AI 能力规格

#### 6.5.1 宠物台词生成（轻量版方案）

- **输入**：`{触发场景, 本次体重, 上次体重, 连续打卡天数, 累计掉秤, 用户昵称, 宠物名, 宠物性格}`
- **输出**：一句 15–40 字的台词（**口语化、温暖、不用"您"、不用感叹号轰炸**）
- **Prompt 骨架**：
```
你是一只陪伴用户减肥的宠物，名叫{pet_name}，性格{friendly/energetic/gentle}。
当前场景：{trigger}
用户数据：本次体重{now}kg，上次{prev}kg，连续打卡{n}天，累计掉秤{d}kg。
要求：用一句不超过 40 字的话回应用户，温暖、具体、不空洞。
必须引用至少一个具体数字（体现"我记得你"）。不要用"加油！"这类空话。
```
- **降级策略**：模型不可用时，回落到**模板池**（每场景 ≥ 5 条预置文案，随机不重复）
- **成本控制**：台词生成**缓存 24 小时**；同一场景同一天不重复调用

#### 6.5.2 AI 营养师（V1）

- **输入**：`{用户身高体重, 目标, 当日三餐记录, 提出问题}`
- **输出**：饮食建议（**必须基于用户真实数据，禁止编造**）
- **边界**：**必须声明「不构成医疗建议」**；不得对疾病、用药给出建议
- **成本**：设**每日调用上限**（如免费 3 次/日，会员 20 次/日）—— C 端方法论「边际成本红线」要求

#### 6.5.3 AI 拍照识别（V1）

- **流程**：图片 → 多模态模型 → 返回 `[{food_name, estimated_quantity, confidence}]` → **匹配食物库** → 用户确认/修正 → 落库
- **约束**：`confidence < 0.6` 的条目**不自动添加**，仅作为候选；用户修正结果**回流用于优化**

## 附 B · 测算过程与敏感度（与实测严格分开）

### B.1 复刻工时的复算（承接前序报告 §4.3）

前序报告给出的三档工时：**MVP 6–8 人月 / 体验对齐 22–39 人月 / 全量对齐 28–45 人月**。

本文在**引入 AI 编码助手**后做一次压缩比估算：

- **假设**：AI 编码助手在「CRUD 页面 + 图表接入 + 数据模型」类任务上提效 **50%–70%**；在「美术 / 动效 / 内容生产 / 合规」类任务上提效 **0%–15%**。
- **依据**：MVP 工作量构成 —— CRUD+图表约占 **70%**，内容/合规约占 **30%**。
- **推算**：
  ```
  压缩后工时 = 6~8 人月 × (0.7 × (1−0.6) + 0.3 × (1−0.1))
             = 6~8 × (0.28 + 0.27)
             = 6~8 × 0.55
             ≈ 3.3 ~ 4.4 人月
  ```
- **结果**：**MVP 降至约 3.3–4.4 人月**；若单人全职 + AI 辅助 → **约 4–6 周**。
- **置信度**：**低–中**（AI 提效比例为主观假设，无实测样本）。
- **敏感度**：提效比例取 30%–70% → 结果在 **2.4–6.4 人月** 区间，**量级（个位数人月）不翻转**。

> **⚠️ 诚实声明**：上表是**方法演示**，不是承诺。**AI 提效在"从零搭建合规账号体系 + 食物库清洗"这类任务上几乎无效**，这两项仍按人力工时计。

### B.2 边际成本对照（AI 类红线自检）

| 方案 | 边际成本/次 | 对照定价 |
|---|---|---|
| 云端 LLM 台词生成 | ≈ ¥0.002–0.01/次（按低价模型） | 会员 ¥88/年 → **安全** |
| 云端多模态拍照识别 | ≈ ¥0.05–0.3/次 | 需设**每日上限**，否则高频用户可击穿 |
| **端侧小模型（V2）** | **≈ 0** | **最优** |

- **敏感度**：若拍照识别被高频滥用（如 20 次/日 × 30 天 = 600 次/月），单用户月成本可达 **¥30–180** → **直接亏损**。**结论：拍照识别必须设用量墙，这不是产品选择，是生存线。**
