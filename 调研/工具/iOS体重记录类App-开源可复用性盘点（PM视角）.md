## 〇、结论先行（TL;DR）

1. **「能不能直接复用」要拆成两问，答案相反：**
   - **① 能不能拿现成开源 App 改吧改吧上架？** → **不能。赛道没有被开源吃掉，这是好事。**
   - **② 能不能直接复用零件，把编码工期从「月」压到「周」？** → **能，而且现金成本几乎为 0。**
2. **赛道雷达判定：L1（有库无成品）——开源侧没有能威胁你的产品。**  
   实测：iOS 体重类开源仓库 **206 个**、热量记录类 **404 个**，合计 **610 个**；**两类的 Star 榜首分别是 79★（且已归档）和 38★（停更 3 年半）**。对照方法论 §2.1 的 **L3 门槛（Star > 10k + 30 天内有提交 + 功能高度重叠）——差 3 个数量级。**
3. **⚠️ 但有一个必须知道的例外：`wger-project/wger`（7,125★ / AGPL-3.0 / 今日仍活跃提交）**——它是本次实测中**唯一功能高度重叠（体重 + 营养 + 训练）且活跃的开源产品**。**但它同时被两道门排除**：① **AGPL-3.0 属方法论「D 档·禁用级」**，网络服务也触发开源义务，**做闭源商业产品等于把整条产品线送出去**；② 它是 **Django(Python) 后端 + Flutter 前端**，不是 iOS 原生。**结论：搜到它、认出它、然后正确放弃它——这是本报告与「搜到就抄」的分界线。**
4. **真正的可复用资产不是 GitHub，是苹果第一方框架。** Swift Charts（图表）、SwiftData（持久化）、HealthKit（健康数据）、WidgetKit + Live Activity（打卡入口）、StoreKit 2（订阅）、CloudKit（同步）——**零许可风险、零维护跟随成本、零包体代价**。桌面工具赛道**没有**这个待遇（那里得自己拼 Tauri + 各语言库）；**iOS-only 的结构性优势就在这里**。
5. **开源零件层最值得直接用的 5 个（全部 A 档许可）：**
   | 能力域          | 推荐                           | 实测                                | 省下什么                             |
   | ------------ | ---------------------------- | --------------------------------- | -------------------------------- |
   | 订阅与支付        | **RevenueCat/purchases-ios** | **3,077★ / MIT / 2026-10-15 仍提交** | 服务端验签 + webhook + 权益表，省 2–3 周    |
   | 本地数据库        | **groue/GRDB.swift**         | **8,688★ / MIT / 2026-09-29**     | 手写 Core Data 栈，省 4–6 人日          |
   | 健康数据 + AI 问答 | **StanfordBDHG/HealthGPT**   | **1,964★ / MIT / 2026-07-14**     | 「自然语言查健康数据」参考实现，直接对位体重小本的 AI 营养师 |
   | 后端与同步        | **supabase/supabase-swift**  | **1,303★ / MIT / 2026-10-15**     | 账号 + 同步 + RLS                    |
   | 分析埋点         | TelemetryDeck / PostHog      | 229★ / **许可 NOASSERTION，须核实**     | 埋点 SDK                           |
6. **两个实测陷阱（本报告新发现，价值最高的一条在第一个）：**
   | 陷阱                            | 实测事实                                                                                                                                                                                                            | 教训                                                                                                               |
   | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
   | **A · 高 Star ≠ 可复用**          | **`bizz84/SwiftyStoreKit` 6,670★ / MIT——但 `pushed_at` = 2024-06-28，停更 27 个月，196 个 open issue，且是 StoreKit 1 时代产物**                                                                                               | **Star 是墓志铭，不是保质期。** 这是本项目第二个实证（第一个是方法论里停更 10.6 个月的 Umi-OCR）。它 Star 是 RevenueCat 的 2.2 倍，但对 2026 年的新项目来说**是负资产** |
   | **B · ODbL 是"数据许可"，不是"代码许可"** | `rbaumier/kcalz`（MIT / 3★）自述「**vibe-coded with Claude Code, offline search over 988k Open Food Facts products**」——把 Open Food Facts **98.8 万条**数据搬进端侧；但 **Open Food Facts 数据库是 ODbL 协议**，share-alike 作用于**数据库** | **代码许可与数据许可必须分开过。** ODbL 的传染逻辑与 GPL 不同但同样必须过法务——**而现有方法论 §4 许可矩阵只覆盖代码**                                          |
7. **对前序报告的一条重要增量（往回修正）**：母链里我说体重小本的「110 万条食物库」是**不可复制的护城河**。**这条要拆开**：
   - **国际食物库已经免费了**（Open Food Facts，ODbL，98.8 万条，有活跃 SDK / 离线方案）→ **不是护城河**
   - **中国食物库没有对应的开源资产**（公开食物成分表仅约 1,506–1,700 条，前面报告已测）→ **这才是护城河，而且它的护城河属性来自「本地化数据采集」，不来自「技术难度」**
8. **中国区一条硬约束（最实战）**：Apple 在 iOS 26 起开放 **Foundation Models 框架**（端侧约 3B 模型、`@Generable` 结构化输出、**对开发者免费**），iOS 27 新增 **Core AI** 框架与私有云计算免费额度（**限 App Store 小企业计划 + 首次下载 < 200 万次**）。**但公开资料显示，该端侧模型不支持中国大陆账号。** → 意味着「用苹果送的免费端侧 LLM 做 AI 营养师」这条路在中国区**大概率走不通**，只能走云端 API（DeepSeek 等）或自打包模型（Core AI / MLX）。**置信度：中（来源为二手技术文章 + 苹果官方口径"部分地区/语言可用"，未取得苹果开发者文档的一手确认）」**
9. **量化：编码段压缩约 3 倍，整体工期压缩约 1.2–1.6 倍。**  
   开源压缩的**只是编码段**，而编码段只占单端 MVP 总工时的 **45%–60%**。剩下 40%–55%（设计 / 上架 / 合规 / 数据采集 / 测试）**开源帮不上忙**。这条常被高估——**"复用开源能把工期砍半"是个流传很广的错判**。

## 五、量化：复用 vs 自建

### 5.1 四栏对照（对 6 个核心能力域各填一遍）

| 能力域           | ① 复用方案                                       | ② 复用成本                        | ③ 自建成本                         | ④ 差额与风险                                               |

| **持久化**       | SwiftData / GRDB                             | 1–3 人日                        | 5–8 人日                         | **省 4–5 人日**；风险：**架构分叉点**，选错要重做                       |

| **后端 / 同步**   | CloudKit 第一方 / Supabase Swift                | 5–8 人日                        | 15–25 人日                       | **省 10–17 人日**；风险：CloudKit 只覆盖 Apple 生态               |

### 5.2 算式 1 · 编码段工期压缩比

```
编码段自建工时 = 12+8+5+6+10+15 至 18+12+8+10+15+25 = 56 – 88 人日
编码段复用工时 = 3+1+1+3+4+5 至 5+2+3+5+6+8  = 17 – 29 人日

编码段压缩比 = 56–88 / 17–29 = 1.9× – 5.2×（中值约 3.1×）
```

**→ 编码段可压缩约 3 倍。** 置信度：**中**（工时为假设值，依据是 ⑤ 号报告已达成的「订阅 2–3 周」「自建 4–6 周」等锚点；构件集成工时按同类 iOS SDK 集成经验估）。

### 5.3 ★ 算式 2 · 整体工期压缩比（**这条才是真相**）

```
单端 MVP 总工时（自建）        = 6 – 8 人月 = 126 – 168 人日（沿用 ③ 号报告口径）
其中「编码段」占比              = 45% – 60%
  → 编码段                      ≈ 57 – 101 人日
  → 非编码段（设计/上架/合规/     ≈ 69 – 111 人日 ← 开源帮不上忙
     数据采集/测试）

复用后总工时 = (126–168) − (57–101) + (17–29)
             = 42 – 140 人日（中值约 90 人日 ≈ 4.3 人月）

整体工期压缩比 = 126–168 / 42–140 = 0.9× – 4.0×（中值约 1.4×）
```

**→ 整体工期压缩约 1.2–1.6 倍（取中值附近收敛）。**  
**⚠️ 这是本报告最容易被误读的一栏，故意写成区间：**

| 情形                         | 压缩比               | 说明          |
| -------------------------- | ----------------- | ----------- |
| 若「编码占比高、复用度高」（纯工具型、无本地化数据） | **1.6× – 2.2×**   | 复用的价值充分释放   |
| **典型情形（含中国食物库采集 + 上架合规）**  | **1.2× – 1.6×**   | **推荐按这个规划** |
| 若「非编码段占大头」（数据采集、合规、设计）     | **≈ 1.0× – 1.2×** | **开源几乎无感**  |

**敏感度**：编码占比 ±10 个百分点 → 整体压缩比在 **1.05× – 2.2×** 之间；**「压缩比 > 2 倍」只有在编码占比 ≥ 65% 时才成立**。方法论里那句「工期可以按周而不是月来算」**在本赛道要打折**——因为本赛道的瓶颈在数据与合规，不在编码。

### 5.4 算式 3 · 复用后的隐性成本（三项，不许漏）

| 隐性成本          | 本赛道具体情况                                                           | 量化                                  |
| ------------- | ----------------------------------------------------------------- | ----------------------------------- |
| **维护跟随成本**    | RevenueCat / GRDB / supabase 都在高频迭代（今日均有提交）                       | 每次大版本适配 **0.5–2 人日**；**每年约 3–8 人日** |
| **包体 / 性能代价** | 全部为 Swift Package，无跨语言运行时；**Swift Charts / SwiftData 为第一方，零额外包体** | 开源部分预计 **+3 – +12 MB**（需实测）         |
| **许可与供应链合规**  | **AGPL 已命中 1 次、GPL 3 次、NOASSERTION 4 次、ODbL 数据 1 次**              | **一次性核查 2–3 人日 + 建依赖清单**            |

### 5.5 一句话结论（可复算）

> **开源能把「写代码」这一段砍掉约三分之二，把「做完一个能上架的 App」这件事砍掉约三分之一到一半。它不改变「要不要做、卖给谁」——那两个问题本报告不回答。**
