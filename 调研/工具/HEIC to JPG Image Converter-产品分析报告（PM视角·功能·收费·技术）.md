## 0. 结论先行（TL;DR）

1. **你问的这个 App，技术上 15 行代码就能复刻。** iOS 上 HEIC→JPG 是 `CGImageSource` → `CGImageDestination` 一次调用，系统自带硬解。**护城河为零**，所以这个词下挤了 **249 个 App**（ASOTools 实测）。
2. **钱不可能收在「转换」上，只能收在「外围」。** 因为转换本身系统免费给（文件 App「转换图像」/ 快捷指令 / AirDrop 自动转 / 设置里改相机格式）。品类里所有能收费的点，全部落在**批量吞吐、去水印、去广告、队列优先、EXIF 控制、格式矩阵**这六层外围。
3. **付费策略几乎是行业统一答案：周订阅当锚 + 年订阅承接 + 买断兜底。** 主体 App 是 **周 $4.99 / 年 $17.99**；品类里出现频率最高的结构是「周 $2.99–4.99 + 3 天试用，年费标 75–93% off」。这不是巧合 —— 是**低频刚需**逼出来的唯一可行结构（见 §4.5）。
4. **技术真相与营销叙事相反：HEIC → JPG 会让文件变大，不是变小。** 2 MB HEIC 通常变成 3–4 MB JPG（q85–90）。**「省空间」是伪卖点，这个品类本质是「兼容性工具」** —— 这说明它的需求面比看上去窄得多。
5. **收入天花板已被测出：品类 iOS 头部 `The Image Converter`（Float Tech）经营 12 年、4.6★ / 4.7 万条评分，月收入约 $6K（¥4.26 万/月）。** 而本次主体 App 排名 **#867,093**，年收入量级约 **¥1,619–¥1.94 万**。**这是一个 ASO 彩票，不是一个生意。**
6. **主体 App 有一处值得记录的定价手法**：文案用「跳过排队 / 插队」给 Premium 定价，但转换是本地且单张 <0.5 s —— **排队在物理上不存在**。把不存在的稀缺性货币化，属 dark pattern。【推断·文案，需实机验证】

## 3. 收费点：钱到底收在哪一层

### 3.1 五种可收费的「面」

把 §2.2 的九项功能映射回收入结构，只剩五张可用的牌：

| 收费面 | 机制 | 代表实现 | 强度 |
|---|---|---|---|
| **A. 吞吐（批量）** | 免费单张，批量锁 | 主体 / Alptekin / Luis Rosas | ⭐⭐⭐ 最主流 |
| **B. 次数** | 每日 N 张，超了付费 | Luis Rosas（3/天）、Miyuki（10/天）、Verity Tools（有限次） | ⭐⭐ |
| **C. 无痕（去水印/去广告）** | 免费出水印或带广告 | Alptekin（水印）、Bokeria（广告+通行证） | ⭐⭐ |
| **D. 元数据（EXIF）** | 去 GPS / 保留时间戳 | Luis Rosas / Miyuki / Alptekin | ⭐ |
| **E. 功能矩阵（PDF/OCR/超分）** | 扩品拉高单价 | Miyuki（OCR+PDF） | ⭐⭐ |

### 3.2 关键结论：**不能收「转换」，只能收「外围」**

**证据链**：

1. iOS 侧至少 **5 条免费通道** 已经吃掉转换本身：文件 App「转换图像」（支持批量）、设置→传输到 Mac/PC→自动、相机→兼容性最佳、Shortcuts 官方 convert 动作、AirDrop→Mac 原生读 HEIC。
2. ASOTools 实测：核心词 `heic to jpg` **搜索量指数仅 35/100，难度 44/100，相关 App 249 个**；长尾词搜索量全部 ≤5。**低需求 × 高供给 × 零门槛 = 只能靠外围建墙。**
3. 品类里没有一家把「转换」本身设成付费墙而活得好 —— **设硬墙的那几家（PZ Global）排名都在百万级**。

> **一句话**：**这个品类的商业模式，本质是「把系统免费给你的东西，用一个更顺手的壳包起来，然后为壳里的顺手收费」。**

### 3.3 唯一的例外：真的「不能转换」时

系统三条路都失效的场景只剩：**云盘上传、网页表单上传、桌面传输**（这些通道 iOS 不会触发自动转换）。**需求存在，但被压缩到极窄**，而且频次低 —— 这是后面 §4.5 付费策略必成「周订阅」的根因。

## 4. 付费策略：周订阅当锚 · 年订阅承接 · 买断兜底

### 4.1 主体 App 的定价结构

| 档位 | 价格 | 折人民币【假设 7.1】 | 折年 | 折月 |
|---|---|---|---|---|
| 免费 | $0 | — | — | — |
| **周订阅** | **$4.99/周** | ¥35.43/周 | **$259.48（¥1,842.31）** | $21.62（¥153.50） |
| **年订阅** | **$17.99/年** | ¥127.73/年 | $17.99（¥127.73） | $1.50（¥10.65） |

**年订阅相对周订阅：省 93.1%**（$17.99 vs 折不买周的 $259.48）。

> **这就是「锚」的力学**：周价被刻意定到「年费的 14.4 倍」，让 $17.99/年 看起来是**作弊级的便宜**。RevenueCat 2026 数据佐证：**周订阅已占 App 订阅收入的 55.5%**（2023 年为 43.3%），而年订阅的时长占比从 41.4% 跌到 33.6%。**周订阅是收银台，年订阅是留存器。**

### 4.2 免费额度设计：主体把 hook 放在「单张免费且无广告」

| App | 免费给什么 | 付费墙卡在哪 | 设计意图 |
|---|---|---|---|
| **主体（Wouter）** | **单张 · 无限次 · 零广告** | 批量（>1 张） | 极致零阻力获客，把「用得到一次」的人全放进来，只对「有整批需求」的人收钱 |
| Verity Tools | 有限次免费 | 次数用完 | 直接按耗损收费 |
| Alptekin Gok | 有限次 + **水印** | 批量 + 格式 + 去 EXIF + 去水印 | 四墙齐上 |
| Luis Rosas | **3 张/天** | 每天超过 3 张 | 频次计费 |
| Miyuki Kikuchi | 10 张/天 + PDF/OCR 各 3 次 | 无限量 + 去广告 | 双墙（量 + 功能） |
| PZ Global | **订阅才可用** | 硬付费墙 | 无免费层 |

**主体的选择是「软墙（freemium）里最聪明的一种」**：单张免费解决了 90% 的一次性需求（不冒犯用户、不产生差评），批量收费恰好命中「旅行回来一整本相册」这种**高意愿时刻**。**把付费点从「能力」搬到「规模」上 —— 这是本品类唯一优雅的解法。**

### 4.4 Android 侧的两条完全不同的路

| 路线 | 代表 | 机制 |
|---|---|---|
| **纯买断 / 付费下载** | TAPUNIVERSE **$1.99**、Moca **$1.99** | 无广告无内购，一次付清 —— **Google Play 用户对订阅的抗拒明显更强** |
| **广告 + 通行证** | Bokeria（免费：≤3 张/次 + 激励视频解锁 2 小时无限；通行证：去广告 + 解限） | 广告是主收入，通行证是降压阀 |
| **纯广告** | SmartVQ84、FocusProduction | 免费带广告 —— 评分里已有「新版加了广告」的差评 |

> ⚠️ **Android 侧最值得注意的一条差评**（SmartVQ84，AppBrain 抓取）：
> *"the developer already created an app that worked just fine then removed that app from the Play store and replaced it with this app and the only difference is this one now has ads"*
> **这是本赛道最真实的生存策略写照：产品迭代不动，只在变现开关上做文章。**

### 4.5 为什么这个品类必然走向「周订阅 + 短试用」

**因果链（本报告的核心结构洞察）：**

```
需求是低频的（一年可能只用 2–3 次）
   ↓ 依据：AppStoryo 实测表述「一年只转换少数几个文件两次」
   ↓ 依据：转换后的 JPG 比 HEIC 大 1.5–2 倍 → 「没必要提前批量转」→ 抑制囤积式使用
订阅不成立（用户凭什么按年付一个低频需求？）
   ↓
只剩两条路：① 买断 ② 周订阅
   ↓ 买断 = 单价低（$1.99）、无复购 → 必须靠量，长尾没有量
   ↓
周订阅 + 3 天试用 = 从「一次性急需」中榨取最大单点价值
```

**RevenueCat 2026 数据给这条链补上血**：

| 指标 | 数值 | 对本品的含义 |
|---|---|---|
| 硬付费墙 D35 转化 | **10.7%** | 比软墙（2.1%）高约 5 倍 |
| 软墙（freemium）D35 转化 | **2.1%** | 主体 App 走的就是这条 |
| D60 每安装收入 · 硬墙 | $3.09（¥21.94） | — |
| D60 每安装收入 · 软墙 | **$0.38（¥2.70）** | ← 主体 App 的收入基准 |
| 试用 17–32 天 → 付费 | 42.5% | — |
| **试用 < 4 天 → 付费** | **25.5%**（且 3 天试用有 **55% 的取消发生在第 0 天**） | 3 天试用是「筛掉犹豫者」，不是「转化者」 |
| 周订阅占订阅收入 | **55.5%** | 品类定价结构的宏观印证 |
| 账单失败导致取消 · Play / App Store | **31% / 14%** | App Store 侧的实际到手率明显更高 |

> **★ 一条可复用的判据（建议并进 `C端方向方法论`）**：
> **「订阅的正当性 = 持续交付成本的可见性」。** 转换类工具边际成本≈0、无服务器、无内容更新 → 用户看不见「为什么要按年付」。**这正是 ZenConverter（上一份报告）和本报告指向同一个墙的另一面**：
> - ZenConverter：**完美做到了零边际成本 → 反而丧失了订阅的全部正当性**；
> - 本品类：**知道订阅说不通 → 于是退化成周订阅的单点收割**。
> **两端同因，只是表现相反。**

## 5. 技术方案：一个 API 调用，四种实现路径

### 5.1 一张图看懂（分层）

```
┌─ 输入层 ────────────────────────────────────────────────┐
│  Photos 相册 (PHAsset) │ Files/SAF │ Share Extension │ 服务器上传(Web) │
└─────────────────────────────────────────────────────────┘
                     ↓
┌─ 解码层 (HEVC 解出 RGBA) ───────────────────────────────┐
│  iOS:   ImageIO / Core Image  → 硬件 HEVC 解码 (A10+)    │
│  Android 9+:  ImageDecoder (API 28+) → 系统 HEIF 解码    │
│  Android <9:  libheif (NDK/JNI .so)   ← 唯一需要引库的路径 │
│  Web:   libheif → WASM (heic-to / heic2any)              │
└─────────────────────────────────────────────────────────┘
                     ↓
┌─ 处理层 ────────────────────────────────────────────────┐
│  色彩管理 (Display P3 → sRGB) │ 方向 │ EXIF 取舍 │ 缩放/压缩 │
└─────────────────────────────────────────────────────────┘
                     ↓
┌─ 编码层 (RGBA → JPEG 比特流) ───────────────────────────┐
│  iOS: CGImageDestination(UTType.jpeg) │ Android: Bitmap.compress │
│  Web: canvas.toBlob('image/jpeg', q)                     │
└─────────────────────────────────────────────────────────┘
                     ↓
┌─ 输出层 ────────────────────────────────────────────────┐
│  相册 / Files / MediaStore / 下载 │ 批打包 ZIP │ Share Sheet │
└─────────────────────────────────────────────────────────┘
```

### 5.2 iOS 原生方案（主体 App 走的就是这条）

| 环节 | 技术 | 备注 |
|---|---|---|
| 读取 | `PHPickerViewController`（iOS 14+） | **零相册权限**，用户选定即授权 —— 省掉隐私弹窗，是 iOS 14 后的关键红利 |
| 备用读取 | `UIDocumentPickerViewController`（读 Files）/ Share Extension | 覆盖「从微信/浏览器分享进来」的入口 |
| 解码 | `CGImageSourceCreateWithURL` / `CreateWithData` | **A10 及以上硬件解码**，老设备软件解码较慢 |
| 编码 | `CGImageDestinationCreateWithURL(dst, UTType.jpeg, 1, nil)` | 一次调用 |
| 质量 | `kCGImageDestinationLossyCompressionQuality: 0.8–0.95` | — |
| **色彩** | `kCGImageDestinationOptimizeColorForSharing: true` | ⭐ **不做这步，P3 照片输出会偏色** |
| 方向 | `kCGImagePropertyOrientation` | HEIC 方向存在 EXIF 里，不搬就竖图躺倒 |
| 元数据 | `CGImageSourceCopyPropertiesAtIndex` → dict → 写回目标 | 删 `kCGImagePropertyGPSDictionary` 即「去位置」 |
| 写回相册 | `PHPhotoLibrary.performChanges` + `.addOnly` | 或直接存 Files |

**性能量级【推算·方法】**：12 MP 单张在 A16 上 ≈ **0.15–0.5 s**（硬解 + JPEG 编码）。

> ⭐⭐ **关键技术结论：iOS 上 HEIC→JPG 完全不需要后台任务授权。**
> 对比上一份报告里的**视频转码**：iOS 后台约 30 s 冻结、`BackgroundTasks` 时机由系统决定、Infuse 路线要靠 `AVAudioSession` 抢占音频会话挂后台。
> **图片转换没有这个问题** —— 单张 <1 s，前台跑完即可。
> **这是它比视频转换「容易做」的原因，也是它护城河为零的原因。** 门槛低 → 供给爆炸 → 249 个同名 App。

### 5.3 Android 原生方案

| 场景 | 方案 | 说明 |
|---|---|---|
| **API 28+（Android 9+）** | `ImageDecoder.createSource(cr, uri)` → `decodeBitmap` | 系统 HEIF 解码，**零依赖，性能最佳**；配 `ALLOCATOR_SOFTWARE` |
| API 26–27 | `BitmapFactory.decodeStream` | 有限的软件解码支持 |
| **API ≤25** | **libheif**（NDK 编译 `.so` + JNI） | ⚠️ **唯一需要引第三方库的路径** → 触发 LGPL 许可义务（见附 D） |
| 编码 | `Bitmap.compress(Bitmap.CompressFormat.JPEG, 90, out)` | — |
| **色彩** | `Bitmap.getColorSpace()` + `ColorSpace.connect(P3, sRGB)` | ⭐ **Android 侧最常翻车的地方**，不做就褪色 |
| 元数据 | `androidx.exifinterface.media.ExifInterface` | 读写 EXIF；删 GPS 即隐私增强 |
| 落盘 | API 29+：`MediaStore.Images.Media.insert` + `RELATIVE_PATH` + `IS_PENDING` 两段提交 | 否则相册不刷新 |
| 批量 | 推荐**串行**处理 | 大图并发易 OOM |

### 5.4 Web / WASM 方案（大量在线转换器走这条）

```
HEIC 字节 → libheif(WASM, ~1.2–3 MB) → Web Worker 内解码 → RGBA
         → canvas / OffscreenCanvas → toBlob('image/jpeg', q) → [JSZip 打包] → 下载
```

- 首载 **~800 KB–3 MB**，之后走缓存；**解码在 Worker 内，避免卡主线程**。
- **致命局限**：libheif 只解**主图**，深度图 / HDR gain map / Live Photo 的 MOV **天然拿不到**。
- 隐私模型差异：服务器端转换（如 heic.online）文件会上传，拿「1 小时后删除」做承诺；WASM 端侧转换**架构上不可能泄露**。**「本地处理」是这个品类唯一站得住的差异化点**（且它免费）。

### 5.5 桌面方案（顺带，作为竞争参照）

| 平台 | 方案 |
|---|---|
| Windows | 系统**不自带** HEVC 解码 → 需装 HEVC Video Extensions（$0.99 或 OEM 免费版）；或应用自带 libheif |
| macOS | `sips -s format jpeg in.heic --out out.jpg`（**一行命令**）/ Preview 导出 |
| 通用 | ImageMagick、XnConvert、iMazing Converter（免费，v2.0.14 / 2026-07-14） |

## 6. 怎么实现的转换：逐步拆解

### 6.1 iOS 管线（9 步，含代码骨架）

```swift
// 1) 建源（HEIC 自动硬解）
guard let src = CGImageSourceCreateWithURL(heicURL as CFURL, nil) else { return }

// 2) 读原属性（EXIF / TIFF / GPS / 方向）
let props = CGImageSourceCopyPropertiesAtIndex(src, 0, nil) as? [CFString: Any] ?? [:]

// 3) 建目标
guard let dst = CGImageDestinationCreateWithURL(
    jpgURL as CFURL, UTType.jpeg.identifier as CFString, 1, nil) else { return }

// 4) 组装写入选项
var out: [CFString: Any] = [
    kCGImageDestinationLossyCompressionQuality: 0.90,   // 质量
    kCGImageDestinationOptimizeColorForSharing: true,   // ⭐ P3 → sRGB 安全转换
]
if let orient = props[kCGImagePropertyOrientation] {
    out[kCGImagePropertyOrientation] = orient            // 方向
}
if stripGPS {                                            // EXIF 取舍
    out[kCGImagePropertyGPSDictionary] = nil             // 不搬 = 去位置
} else if let gps = props[kCGImagePropertyGPSDictionary] {
    out[kCGImagePropertyGPSDictionary] = gps
}

// 5) 源 → 目标（用 FromSource 版本，避免在 Swift 侧持有整张 CGImage）
CGImageDestinationAddImageFromSource(dst, src, 0, out as CFDictionary)

// 6) 收尾
CGImageDestinationFinalize(dst)
```

**第 5 步是工程要点**：用 `CGImageDestinationAddImageFromSource`（而非先 `CGImageSourceCreateImageAtIndex` 拿 `CGImage` 再 `AddImage`），**批量时内存峰值显著更低** —— 因为不必在 Swift 侧同时持有多个已解码的位图。

### 6.2 Android 管线（6 步）

```
1. SAF 选图：ACTION_OPEN_DOCUMENT + EXTRA_MIME_TYPES = ["image/heic","image/heif"]
   （或 MediaStore 查 MIME_TYPE IN ('image/heic','image/heif')）
2. 解码：API28+ ImageDecoder.createSource → decodeBitmap{ allocator=SOFTWARE }
        低版本 → libheif JNI
3. 色彩：getColorSpace() 若为 Display P3 → ColorSpace.connect(p3, sRGB)
4. 编码：bitmap.compress(JPEG, 90, FileOutputStream)
5. 元数据：ExifInterface 读原 EXIF → 写回（可选删 GPS）
6. 落盘：MediaStore.insert + RELATIVE_PATH + IS_PENDING 两段提交
```

### 6.3 五个必踩的坑（工程口径）

| # | 坑 | 现象 | 解法 |
|---|---|---|---|
| 1 | **色彩未管理** | 输出**发灰/褪色**（用 sRGB 解释 P3 数据）或**过饱和** | iOS `OptimizeColorForSharing` / Android `ColorSpace.connect` / Web managed canvas |
| 2 | **体积反直觉** | HEIC 2 MB → JPG 3–4 MB | **不是 bug**，HEVC 比 JPEG 高效。这是「兼容性工具」不是「压缩工具」 |
| 3 | **方向丢失** | 竖图躺倒 | 搬 `kCGImagePropertyOrientation` |
| 4 | **批量 OOM** | 25 张 12 MP 并发崩 | 单张 RGBA ≈ **12e6 × 4 = 48 MB**；限并发 2–4 或串行 |
| 5 | **代际损失** | 反复「转→改→存」越来越糊 | q90 的 SSIM ≈ **0.959**（jpgtoolkit 实测口径）；引导「从原图转一次」 |

### 6.4 转换的**真实边界**：保留什么 / 丢什么

| ✅ 保留（需显式搬运） | ❌ 永久丢失（JPG 装不下） |
|---|---|
| 主图像素（解码→重编码） | **HDR gain map**（10/12-bit → 8-bit SDR，宽渐变出现色带） |
| EXIF：相机 / 镜头 / 快门 / 光圈 / ISO / GPS / 拍摄时间 | **深度图**（人像模式可再编辑的景深） |
| 色彩配置文件（P3 或 sRGB，含 ICC） | **Live Photo 的 3 秒 MOV** |
| 方向标志 | **连拍序列**（只留一帧） |
| | 编辑历史 / 辅助图（auxiliary images） |

> ⚠️ **这不是「品质问题」，是「格式表达力问题」。** 而它带来一个致命的商业后果：
> **用户一旦知道「转了就回不去」，就会倾向「只在必须时转一次」** → **需求被技术事实自我抑制** → **频次更低** → 回到 §4.5 的周订阅因果链。
> **技术上「无损保留元数据」是个卖点，但正因为 JPG 装不下深度图和 HDR，这个卖点无法被兑现。** 品类里所有宣称「无损」的都在说谎（或者说的是「主图视觉无损」）。

## 8. 反直觉结论（可进方法论）

### 8.1 「HEIC 转 JPG 会让文件变大」

品类里大量文案宣称「省空间 / 压缩」，**技术上恰好相反**：2 MB HEIC → 3–4 MB JPG（q85–90）。HEVC 比 JPEG 的编码效率高约 2 倍。
→ **推论：这个品类本质是「兼容性工具」，不是「压缩/存储工具」。** 定位错位的 App，会吸引到错误用户（想省空间的用户，用完发现更占地方 → 差评）。

### 8.2 「需求被技术事实自我抑制」

用户一旦知道「转了就丢 HDR / 深度图 / Live Photo 动作」，就会**只在必须时转一次** → 使用频次被压低 → 订阅更不成立 → 只能靠周订阅收割一次性需求。
→ **推论：「无损」在这个品类是不可兑现的承诺**，因为 JPG 装不下 HEIF 容器里的辅助图。**卖点越强调「无损」，越暴露它做不到无损。**

### 8.3 「把不存在的稀缺性货币化」（dark pattern 记录）

主体 App 的 Premium 卖点写的是 **"SKIP THE WAITING LINE… Premium users cut straight to the front"**（免排队/插队）。
但**转换是本地端侧、单张 <0.5 s 的同步操作 —— 排队在物理上不存在**。
→ **推论：这是一张「虚空稀缺性」牌**，用排队暗示服务器瓶颈（同时暗示「别人也在用」的社会认同），为去重定价。
→ ⚠️ **【推断·文案】**：需实机验证是否存在真实的云端队列。若不存在，属典型 dark pattern，是本报告唯一需要动手核实的功能层疑点。

### 8.4 「ASO 套利型产品」的识别特征

| 特征 | 主体 App 表现 |
|---|---|
| 名字 = 精确长尾搜索词 | `HEIC to JPG: Image Converter` 直接等于查询串 |
| 上线即定终局，不做产品迭代 | 2025-07 上架，至今 **v1.0** |
| 定价不匹配量级 | 排名百万级却挂 **$4.99/周** |
| 文案重修辞轻功能 | 「so smooth, it feels illegal」「personal JPG butler」 |
| 同名竞争者 | ≥3 家抢同一串词 |

→ **用户量不是目标，搜索位才是目标。** 这类 App 的经济学是「**用最小成本占一个词，赌自然流量**」，不是「做产品」。

### 8.5 「平台选择就是定价决策」的第二个证据

上一份报告已建立「同能力在不同平台年 ARPU 差 25–140 倍」。本报告补第二组证据：
- **iOS 侧长尾普遍走订阅**（$2.99–5.99/周），因为 App Store 账单失败率仅 14%，订阅能续上；
- **Android 侧显著更多走买断 / 广告**（$1.99 一次性、通行证、激励视频），因为 Play 账单失败率达 31% —— **订阅在 Android 上「收不满」。**
→ **推论：不是 Android 用户穷，是 Android 的账单管道更漏。** 这是「平台选择即定价决策」的微观机制。

## 9. 若要做，可进场位置

**先把话说前面：我不建议单做这个品类**（理由见 §7.3）。若已有桌面/自动化产品，可考虑的是**「作为副产品的一层」**，而非独立产品。

| 位置 | 形态 | 为什么可能成立 | 为什么大概率不成立 |
|---|---|---|---|
| **P1. 系统短板位** | 专做「云盘/网页表单/桌面传输」这三条**不触发 iOS 自动转换**的通路 | 唯一未被系统覆盖的窄真空位 | 频次太低，撑不起订阅 → 只能买断 → 需要量 |
| **P2. 元数据位** | 「带 EXIF 的 HEIC → WebP/AVIF」——保留**色彩配置 + 时间戳**，转成**更小**的容器 | 三处避让：不碰 JPG（体积劣势）、不碰「无损」谎（WebP/AVIF 确实更小）、碰「跨平台包体」 | 用户不认 WebP/AVIF 是「安全格式」，教育成本高 |
| **P3. 顺手位（最现实）** | 挂在你已有的桌面产品里做一个 `右键 → 转 JPG` | 零获客成本，纯留存/顺手度提升 | 不产生独立收入，是「不亏」而非「赚」 |

## 附 D · 开源依赖与许可清单

| 组件 | 许可 | 触发场景 | 义务 / 风险 |
|---|---|---|---|
| **libheif**（struktur AG） | **LGPL-3.0**（含部分组件商业授权） | **Android API ≤25 的解码路径**、所有 Web/WASM 方案 | ⚠️ **动态链接（.so / .wasm）通常可满足 LGPL**；**静态链接进闭源 App 会触发「必须提供可替换的目标文件」义务** → 上架前必须走法务确认 |
| **heic-to / heic2any** | MIT（heic2any 为 MIT） | Web 侧 libheif 的 JS/WASM 封装 | 宽松，保留版权声明即可 |
| **JSZip** | MIT / GPL 双许可 | Web 侧批量打包 ZIP | 选 MIT 分支，保留声明 |
| **libheif 内嵌 HEVC 解码 (libde265)** | **LGPL-3.0** | 同上 | 同 libheif |
| **HEVC / H.265 专利池（Access Advance / Via LA）** | 商业专利许可 | ⚠️ **任何「解码 HEVC」的产品（含纯客户端）都可能落入** | ⚠️ **这是本报告最重要的法务风险**：Apple/Android 系统内置解码已由平台方承担许可；**一旦自带 libheif 绕过系统解码器，专利义务上移到开发者自身** → 与上一份报告的 AGPL 双向封锁同属「许可即商业模型」类风险 |
| iOS ImageIO / Core Image | 系统框架 | 主体的实现路径 | 无许可风险（平台承担） |
| Android ImageDecoder (API 28+) | 系统 API | Android 高版本路径 | 无许可风险 |

> **★ 附 D 的否决项（动手前必须先查）**：
> **① 若走 Android 低版本兼容 → 自带 libheif → 同时触发 LGPL-3.0 + HEVC 专利双重义务；**
> **② 若只走 iOS ImageIO / Android API 28+ → 许可干净，但市占覆盖率损失 Android 9 以下机型。**
> **这两条是互斥的，也解释了为什么这个品类里「Android 低版本兼容」做得好的 App 很少 —— 不是不能做，是不敢做。**
