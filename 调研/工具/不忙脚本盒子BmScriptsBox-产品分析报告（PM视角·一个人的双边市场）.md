# 不忙脚本盒子 BmScriptsBox — 产品分析报告（PM 视角 · 一个人的双边市场）

> **分析对象**：`bm-qihengzhi/BmScriptsBox`（GitHub）+ 官网 `bm-box.cn` + 脚本社区（97 个详情页 / 96 个在架）
> **版本快照**：v1.5.1（2026-10-21 发布）；changelog 起点 v0.1.0（2026-05-07）；GitHub 仓库创建 2026-07-14
> **采集日**：2026-10-22
> **分析目的**：判断「这类产品能不能做 / 该怎么做」——**学它 + 判它**，不是投它
> **计数口径**：① 脚本数 = 分类页去重条目（96，与 sitemap 97 差 1 条，疑为已下架）；② 安装量 = 社区页「N 次安装」字段，服务端渲染，逐分类翻页全量抓取；③ 下载量 = GitHub release asset 累加；④ 装机量 = 推算（见附 B1），非实测
> **可信度**：GitHub / 站点数据为【实测·API】；竞品价格为【实测·定价页】；装机量与收入为【推算】；无经审计财务
> **本报告要回答的 3 个问题**：① 它到底是什么（是工具还是平台）？② 为什么 5.5 个月做到 96 个脚本还是收不到钱？③ 同一份代码换个形态能不能成立？

## 〇、结论先行（TL;DR）

**1. 这是本系列三次分析里工程质量最高的一档，也是唯一「商业结构说得通」的一档——但它把形态选错了：把一个可以单边成立的「运行时」，做成了一个必须双边才成立的「应用商店」。**

它做对了一件前两个标的都没做的事：**付费墙的位置是对的**。它有真实的持续交付成本（脚本托管、环境兼容、社区审核、更新分发），所以订阅在结构上正当——这正是 L4 判定里唯一合法的那一档。WatuDisk 的墙后面是空的，HDS 的墙后面是 21 年的兼容矩阵，而它的墙后面本来可以是「脚本被持续维护」。**问题不在墙的位置，在于墙前面没有人。**

**2. 硬数据：96 个脚本、1,030 次安装、中位 8 次、最大 78 次；34 star、199 次 GitHub 下载、装机推算 300–520（P50 ≈ 400）。**

对照：Quicker 8,000+ 动作 / 500 万+ 安装 / 专业版 ¥57.6/年；uTools 5,338+ 插件 / 500 万+ 用户 / 50 亿+ 唤醒 / 会员 ¥98–99/年。**供给差 83 倍，需求差 1 万倍以上。** 而双边市场的价值是两边相乘，所以差距不是加法级的。

**3. 最关键的一条分布事实：它没有爆款。**

97 个脚本里最大 78 次安装，中位约 8 次，均值 10.7 次。这不是「长尾」——**长尾的前提是有头**。这是一个平坦而稀薄的分布：没有任何一个脚本被任何一群人当成「离了它不行」的工具。Quicker 单个动作平均 625 次安装，是这个产品单个脚本均值的 **58 倍**。**供给不缺（96 个在 5.5 个月里不算少），缺的是「有人非要不可」。**

**4. 唯一被验证的需求，落在灰区。**

装机量第 **1、第 4、第 5** 名全部是「自动签到 / 薅积分」脚本（WorkBuddy 签到 78 次、Qoder 签到 33 次、Trae 签到 33 次，合计 144 次，占全部 1,030 次的 **14.0%**）。其中 Trae 签到脚本的公开描述写着：**「自动提取本机客户端凭证」**、**「9074 限流自动换设备号」**。作为分发方，平台对这类脚本负连带责任；而这类需求既不能公开商业化，目标平台一次风控升级就会让它归零。**社区真正想要的东西，恰好是平台不能卖的东西。**

**5. 打分 71/135（52.6%），命中一票否决 2 条；但同一份代码换形态后是 95/135（70.4%），刚好压线进入可做。**

这个反差是全文最重要的一句话：**问题不在代码里，在「把它包装成什么卖」里。** 代码做的是「脚本 → 可安装的一键工具」这件极难的事；而产品卖的是「一个脚本商店」这件必须双边冷启动的事。前者一个人能做，后者一个人做不了。

## 一、定位与口径（L0 + L1）

### 1.1 它其实是两个产品被绑在一起

这是读懂这个产品的前提——**报表上的所有矛盾，都来自这两层被混在一起看**。

| 层 | 是什么 | 谁在受益 | 边际成本 | 能否单边成立 |
|---|---|---|---|---|
| **A · 运行时底座** | 一份 TOML 声明 → 自动装 Python/Node/Pwsh/AHK 环境 → 自动生成参数面板 → 自动挂右键/热键/定时 → 统一错误码与数据契约 | 脚本作者（不用写 GUI、不用打包） | ≈0 | ✅ **能**（一个客户就能成交） |
| **B · 脚本社区** | 97 个脚本的发现、安装、更新、评分 | 普通用户（不用找脚本） | 随脚本数线性增长（每个脚本的兼容问题都是工单） | ❌ **不能**（必须双边冷启动） |

**A 是资产，B 是负债。** 而目前所有对外表达（官网 hero、README 首段、`给电脑装上超能力`）讲的全是 B，A 只出现在开发者文档里。

### 1.2 一句话定义（不用品类词）

> **它让「别人写的一段命令行程序」变成「我妈也能双击用的按钮」——顺带开了一个卖这些按钮的柜台。**

官网自己的比喻是「面向 Windows 桌面自动化的桌面版油猴」。这个比喻准确，但也暴露了问题：油猴的价值 99% 在「脚本社区已经有几百万个脚本」，而不在「油猴这个壳」。

### 1.3 品类归属与货架

陌生用户会把它放到哪个货架，直接决定它的竞品集合：

| 用户可能的货架 | 会拿谁对比 | 对它的结果 |
|---|---|---|
| 「启动器 / 效率工具箱」 | uTools、Quicker、Listary、Raycast | **全面劣势**（生态差 2 个数量级） |
| 「脚本管理器」 | 油猴、AutoHotkey、PowerShell 终端 | 优势明显，但**这个货架没人逛** |
| 「绿色软件 / 单文件工具」 | 52pojie 上的各种小工具 | 认知错位（它是平台，不是工具） |

**它站错了货架。** 一个产品最贵的错误不是功能做得不好，是被放进了一个「自己必然输」的对比集里。

### 1.4 Non-scope（它明确不做什么）

- ❌ 不做跨平台（仅 Win10/11 64 位）
- ❌ 不做 AI 对话/Agent（只做「把本地 AI 模型下载好给脚本用」）
- ❌ 不做云端（不强制注册、不上传数据、运行全离线）
- ❌ 不做工作流可视化编排（只有脚本互相调用的 API，没有画布）—— **这条最可惜，见 §8.1**
- ❌ 不做商业授权外的闭源分发（MIT + Commons Clause，商用需授权）

### 1.5 时间线（真实开发强度）

| 时间 | 事件 | 意义 |
|---|---|---|
| 2026-04-20 | 自建 UI 库 `xsideui` 首发 0.9.3 | 先造零件，再造产品 |

| 2026-05-29 | v0.2.0 脚本市场 / 快捷键 / 定时任务 | 3 周做出平台骨架 |
| 2026-07-14 | GitHub 仓库创建（开源） | 决定开源，改用 Commons Clause |
| 2026-07-15 | v1.0.2 首个 release | 发行版起点 |
| 2026-09-14 | v1.4.1 脚本联动 / 节点声明 / 图形化窗口 | 从「工具集」走向「工作流」的关键一步 |

## 二、功能全景（四层分层）

| 层 | 内容 | 商业含义 |
|---|---|---|
| **T1 内核**（去掉它不成立） | ① **TOML 声明式接入**（零侵入、无 SDK、无需 import）；② **环境自动部署**（Python/Node/Pwsh/AHK 便携运行时 + venv + 依赖）；③ **统一触发面**（右键菜单 Shell 扩展 / 全局热键 / 双击 Ctrl 超级复制 / 定时任务 / 卡片） | 这才是定价的地基。**它解决的不是「脚本从哪来」，而是「脚本怎么才能被非程序员用」** |
| **T2 增强**（提效可替代） | 脚本商店检索与一键安装、更新检测、资源清理（无用二进制/模型回收）、托盘常驻、多语言、深浅主题 | 决定口碑，不该单独收费 |
| **T3 差异化**（只有它有） | ① **命令行脚本一键生成 GUI**（TOML → 渲染参数面板，不写 UI 代码）；② **依赖即声明**（`runtime.binaries` 自动下载 FFmpeg/Pandoc/7zip 并注入 PATH；HuggingFace/ModelScope 模型按需拉取 + **跨脚本复用**）；③ **脚本联动 API**（`/api/link` + `[bmscriptsbox.node]`，脚本可互调并拿回结果）；④ **uv/pnpm + 硬链接共享缓存**（多脚本不重复占盘）；⑤ **Commons Clause 而非纯 MIT** | ① 和 ② 是真差异化，且**免费替代没有**——PyInstaller/Nuitka 能打包，但不能「声明即得界面 + 依赖 + 定时 + 热键」。这是它最值钱的一段 |
| **T4 长尾** | Windows 11 右键菜单样式切换、微信推送（ClawBot 扫码绑定）、国际化翻译、启动动画 | 装饰。**「微信推送定时任务结果」这种功能，是典型的「看起来很懂用户、实际没人需要」** |

**判断**：T1 + T3-①②⑤ 是资产，其余是成本。而 T4 里的微信推送、菜单样式切换，占了 v1.4.6 更新日志的一大半——**一个人最稀缺的资源被投在了最不该投的地方**。

## 三、用户与场景（L2）

### 3.1 三类用户，三种命运

| 角色 | 是谁 | 规模 | 他要什么 | 他会不会付钱 |
|---|---|---|---|---|
| **普通用户** | 不会装 Python、但有一堆重复劳动的办公/设计/运营人员 | 理论最大 | 「我要批量改 200 个文件名」——**要结果，不要脚本** | 会，但**不会为「脚本管理器」付**，只会为「那个具体功能」付 |
| **脚本作者** | 会写 .py/.ps1、但不会做 GUI 和分发的开发者 | 小 | 「我写完了，怎么给别人用」 | **最可能付**，但只有一个场景：**内部/团队分发**（见 §8.3） |
| **作者本人** | 綦恒智（单人，业余时间，见 donate 页自述） | 1 | 做出一个平台 | — |

**致命错位**：产品为「普通用户」而建（首页全是「零基础」「无需命令行」），但普通用户**没有脚本**——他们在找的是成品工具，不是脚本运行器。真正需要它的是「有脚本、缺分发」的那一小群人，而这一群人的数量，撑不起一个社区。

### 3.2 JTBD 与频次

| 场景 | 触发 | 频次 | 判定 |
|---|---|---|---|
| 选中文件右键 → 批量改名/压缩/转格式 | 有文件要处理时 | 周级 | 中频，但**替代品是「资源管理器 + 一个绿色小工具」** |
| 双击 Ctrl → 选中文字 → 翻译/改写/查词 | 阅读时 | 日级 | **高频**，但这一格被 uTools/Quicker/Raycast 全面占据 |
| 定时跑签到/同步/备份 | 每天固定时刻 | 日级 | 高频，**但灰区** |
| 装上 → 试两个脚本 → 再也没打开 | 一次 | 一次性 | **这是大多数人的真实结局（中位 8 次安装 = 大多数人只装了 1–2 个就停了）** |

**最后一行才是关键数据。** 1,030 次安装 / 96 个脚本 = 10.7；而中位数只有约 8，说明分布不是「少数脚本被重度使用」，而是「每个脚本都被轻微用过几次」。**这不是使用曲线，这是试用曲线。**

### 3.3 替代方案谱系（六类必须列全）

| 替代 | 具体 | 成本 | 它挡得住吗 |
|---|---|---|---|
| 手动做 | Excel 宏、手工批处理 | 时间 | 部分挡得住（它更快） |
| **系统内置** | Win11 右键菜单、任务计划程序、PowerShell | 0 | 挡不住——系统内置已覆盖「定时 + 右键」两件事 |
| **免费开源** | **Rubick**（Electron 插件工具箱）、**Wox / Flow Launcher**（启动器 + 插件）、**PyInstaller / Nuitka**（脚本打包）、**AutoHotkey**（热键 + GUI） | 0 | **这是最危险的一格**：打包有 PyInstaller，界面有 AHK/tkinter，热键有 AHK，定时有任务计划程序——**四件事各有免费解，只是不在一处** |
| 竞品 | uTools、Quicker、Listary、Raycast | 免费起 | 全面劣势（生态） |
| 找人做 | 淘宝代做脚本 | ¥50–500 | 它便宜，但用户根本不知道它存在 |
| **忍着不做** | 继续手工 | 0 | **最强对手**——绝大多数人选择这一格，所以脚本数再多也没有用 |

**结论**：它面对的不是某一个竞品，而是「**四件免费的事不在一处**」这个摩擦力。这是一条真实但极窄的价值主张——**窄到只能支撑一次「打包出售」，撑不起一个「必须每天来逛的商店」**。

### 3.4 一手声音（社区脚本本身就是需求证据）

不编造评论，只用可核实的脚本名与描述反推需求：

| 脚本 | 安装 | 它暴露的真实需求 |
|---|---|---|
| WorkBuddy 签到 | 78 | 「帮我自动领积分」 |
| Qoder 签到 / Trae 签到 | 33 / 33 | 同上，且**明确写「提取凭证」「换设备号」** |
| 文档格式转换 | 21 | 「Word/PDF/表格互转」——**这一格被 WPS/Adobe/在线站全覆盖** |
| Excel 工具箱 | 28 | 「离线批量处理表格」——正是它最该赢的一格 |
| 图片压缩/加水印/加圆角/分割 | 5–15 | 「批量图片处理」——**付费意愿最高的一格，但全被免费在线站吃了** |
| .gitignore 生成 | 2 | 开发者玩具，一次性 |

**读法**：安装量最高的四类里，两类是灰区（签到）、两类是「被免费替代完全覆盖」（格式转换、图片处理）。**没有一个落在「只有它能做」的格子里。**

## 四、价值主张与需求硬度（L3）

### 4.1 卖点逐条对撞免费替代

| 它的卖点 | 对撞后还剩多少 | 判定 |
|---|---|---|
| 「不用装 Python，自动部署环境」 | **剩很多**。PyInstaller 要作者打包，用户侧仍需处理杀软误报；它做到了「用户零配置」 | ✅ **真卖点，且是 10 倍可感知** |
| 「命令行脚本一键生成 GUI」 | **剩很多**。tkinter 能写但难看，PySide 要学；TOML 声明得界面是真省事 | ✅ **真卖点，且是它独有的** |
| 「七种语言统一管理」 | 剩一半。「统一」有价值，但用户一生只用一种 | 🟡 对「作者」有价值，对「用户」无感 |
| 「右键/热键/超级复制/定时 四种触发」 | **剩很少**。AHK + 任务计划程序能全做，Quicker 做得更好 | 🔴 包装 |
| 「内置脚本社区」 | **剩很少**。96 个 vs 5,338 个（uTools）/ 8,000 个（Quicker） | 🔴 劣势项，不是卖点 |
| 「完全免费开源可审计」 | **负值**。对一个要常驻、要 Shell 扩展、要下载并执行远程代码的工具，「免费」反而是「没人对它负责」的信号 | 🔴 **这是它最大的自我伤害，见 §5.2** |
| 「一切皆脚本」 | **0**。这是价值观，不是卖点。用户要的是「这个文件能批量改名」 | 🔴 需教育 = 不存在 |

**能打的只有两条：环境零配置 + 声明即得界面。** 这两条恰好都在 A 层（运行时），不在 B 层（商店）——与 §1.1 的判断完全一致。

### 4.2 需求的真实硬度：手段刚需 ≠ 目的刚需

- **手段层（跑脚本）**：对一个不会编程的人，这从来不是他的问题——**他根本没有脚本**。
- **目的层（把这事自动化）**：这是真需求，但它的正确形态是「一个成品小工具」，而不是「一个能跑脚本的盒子」。

> **这就是它需求硬度的天花板**：它解决的是**供给侧**的痛（作者不会做界面/不会分发），却把产品做给了**需求侧**（普通用户）。而需求侧的人不需要「脚本能力」，只需要「结果」。

打分卡里「痛点硬度」只能给 2 分（×3 = 6），原因就在这——**不是痛点不够痛，是痛的人不在它的目标用户里**。

### 4.3 天花板（三口径）

| 口径 | 算法 | 结果 |
|---|---|---|
| **TAM**（理论） | 中国 Windows 效率工具活跃用户 ≈ 3,000 万–5,000 万（按 uTools/Quicker 各 500 万装机、市占 10–15% 反推） | 3,000 万–5,000 万 |
| **SAM**（可服务） | 其中「有脚本、且愿意用第三方运行器」的比例 ≈ 1%–3%（开发者 + 重度折腾党） | 30 万–150 万 |
| **SOM**（它能拿到） | 5.5 个月实际 300–520 装机；按当前增速年化 ≈ 870 | **年增 ~870，累计 5 年 < 5,000** |

**SOM 与 SAM 差 2–3 个数量级。** 这不是执行差距，是「一个人 + 冷启动双边市场」的结构上限。

### 5.2 最贵的一个错误：把「免费」写成了合同

他在**四个地方**做了永久性承诺：

| 位置 | 原话 |
|---|---|

### 5.3 如果要收费，墙应该砌在哪里（建议）

| 墙 | 内容 | 为什么成立 | 定价锚 |
|---|---|---|---|
| **功能墙**（首选） | 团队/私有脚本库（内部仓库 + 白标 + 权限）、多设备配置同步、脚本加密分发 | 有真实持续成本（存储 + 同步 + 权限），且**只有 B 端和重度作者会需要** | ¥199–999/年（个人 Pro）；¥2,000–20,000/年（团队） |
| **用量墙** | 不限量脚本数 / 不限量定时任务数 | 当前已声明不限量，改动即背刺 | ❌ 不可用 |

**结论**：唯一能砌的是「团队协作 + 私有分发」这堵墙。而它恰好**不需要 C 端社区**——再次指向 §8.3 的机会点。

### 5.5 「永久免费」在这个品类的结构性代价

- 无云成本 → 订阅本可不需要，但**脚本兼容维护是真实的人工成本**（见附 B4），所以它既不能纯买断（维护无底），也不敢订阅（承诺在先）。
- 结果：**它落在了一个「既不能买断、也不能订阅」的模型真空里**，只能靠打赏——而打赏在本赛道已有两个零收入样本（PopDrop 333 star / 2,070 下载 → ¥0；本项目 34 star / ~400 装机 → 推算 ¥0–400）。

### 6.3 双边市场的乘法（这一节是判决的核心）

**平台价值 ∝ 装机量 × 脚本数。** 两边分别比：

| | BmScriptsBox | Quicker | 倍数 |
|---|---|---|---|
| 脚本数（供给） | 96 | 8,000+ | **83×** |
| 装机量（需求） | 300–520 | 5,000,000+ | **≈ 12,500×** |
| 乘积 | 3.1 万–5.0 万 | 4.0×10⁹ | **≈ 10 万倍** |

> **这就是为什么「再迭代 6 个月」不会改变结论**：它需要同时把两边各推 2 个数量级，而一个人在业余时间只能推一边。**「高频迭代 + 社区分发」这个个人最优解，前提是「社区已经存在」——它要造的正是这个前提。**

### 6.4 护城河：只有一条，而且很薄

| 候选 | 强度 | 判定依据 |
|---|---|---|
| 脚本适配存量（96 个 TOML + 依赖声明） | 🟡 弱中 | 是真实的存量资产，但**一份 TOML 的迁移成本 ≈ 10 分钟**，作者随时可以同发 uTools |
| 接入规范（TOML schema + 47 页文档） | 🟡 弱中 | 规范本身无网络效应，除非成为**跨工具的标准**——那是标准之战，个人打不了 |
| 网络效应 | 🟢 几乎为 0 | 96 个脚本里 **只有 14 个（14.4%）在详情页暴露了第三方仓库**，其余 83 个无第三方归属信息 → **社区供给主要是作者自营**，不存在「作者带作者」的链式增长 |
| 技术（环境部署 / 声明式 GUI） | 🟡 中 | 真本事，但可被复制（uTools 的插件机制已在做类似事） |

**关键发现（本轮最硬的一条）**：97 个脚本中，**14 个**指向外部作者的 GitHub 仓库（其中多个与知名开源项目作者 ID 吻合：`taojy123`、`ihmily`、`ZhengPeng7`、`SakuraMathcraft`、`pashkov256` 等），**其余 83 个无第三方仓库归属**。

这意味着两件事：
1. **「社区」目前是作者的产能，不是用户的产能。** 96 个脚本能在 5.5 个月做出来，靠的是**给现成开源工具套一层 TOML 外壳**，不是从零写——这解释了产能，也解释了为什么护城河薄：**外壳可复制，被包装的工具是别人的**。
2. **双边中的「供给边」其实是单边。** 一个人做 96 个脚本是可能的（他做到了）；一个人做「96 个脚本 + 10 万装机」不可能。

### 6.6 开源覆盖度五级判定

| 等级 | 定义 | 本例 |
|---|---|---|
| L0 未覆盖 | 无开源实现 | — |
| L1 有库无产品 | 有组件无成品 | — |

## 七、持续性与风险（L6）

### 7.1 bus factor = 1，且他同时维护 4 个系统

| 自建件 | 说明 | 风险 |
|---|---|---|
| 主程序 | ~90 个 .py，PySide2 + Flask + peewee + pygit2 | 一人 |
| **UI 组件库 `xsideui`** | 自建 30+ 组件 / 主题系统 / SVG 引擎，PyPI 独立发布 9 个版本 | 一人，且**主程序依赖它**——两个项目互为单点 |
| **C# 右键菜单扩展** | SharpShell + RegAsm + 注册脚本（.NET 技术栈） | 一人，且**跨语言维护** |
| 社区后端 + 官网 | 脚本托管、更新分发、Webhook、管理控制台（`/bm-console`） | 一人 |

**一个人的业余项目，同时维护 Python 桌面端 + Python 组件库 + C# Shell 扩展 + Web 后端 + 96 个脚本。** 这不是「勤奋」，是**风险集中**：任一环节断更，整条链路停摆。而 donate 页自己写着「由一个人在业余时间维护」——**意味着这是副业，且作者另有本职工作**（合规上还涉及职务作品与竞业问题，见附 C）。

### 7.2 合规风险：分发方连带责任（最被低估的一条）

| 风险 | 证据 | 后果 |
|---|---|---|
| **灰产脚本** | 3 个签到脚本占 14.0% 安装量；Trae 签到描述含「**自动提取本机客户端凭证**」「**9074 限流自动换设备号**」 | 作为分发方，平台对脚本行为负连带责任；目标平台一次维权即可要求下架，社区信誉一次性受损 |
| **UGC 可执行代码** | 脚本可为 Python/BAT/EXE/PowerShell，来源为任意 GitHub 仓库 + 直连下载 | **无审核、无沙箱、无签名**。sha256 校验只保证「与作者发布的一致」，**不保证安全** |
| **「不强制注册」的代价** | README 明写「仅发布脚本到社区时需注册」 | 无实名 → 出事找不到作者 → 责任全部回落到平台 |
| **杀软误报** | 作者自述「买不起代码签名证书」 | 对一个要常驻 + 装 Shell 扩展 + 下载执行远程代码的工具，这是**致命的分发摩擦**（每一次误报都是一次卸载） |

> **这三条叠加起来，构成了「个人不能做 UGC 代码分发」的结构性理由**：不是技术问题，是「审核能力 + 追责能力 + 签名成本」三样都不具备。这是打分卡里「合规/平台风险」只给 1 分的原因。

### 7.3 技术债：PySide2 已 EOL

| 项 | 现状 | 风险 |
|---|---|---|
| `PySide2==5.15.2.1` | Qt for Python 5.15 系列**官方 wheel 止于 CPython 3.10**，项目声明 `requires-python >=3.8`（无上界） | 在 3.11/3.12/3.13 环境**装不上**；一旦要升级 Python 就必须整体迁 PySide6 |
| `xsideui` 双兼容 | 该库自称支持 PySide2/PySide6 | **迁移成本被自建库抵消了一半**——这是他做过的最有价值的技术决策之一，因为迁移按钮在自己手里 |
| `pygit2` | 依赖 libgit2，Windows 上编译/分发麻烦 | 中 |
| 单文件 39 MB 安装包 | 内置运行时 | 与「解压即用」的承诺一致，但更新成本高 |

**判定**：技术债存在但**有解，且解法的钥匙在自己手里**（自建 UI 库双兼容）。这在个人项目里很少见。

### 7.4 生命周期位置

**萌芽期（Beta，官网自标「Beta 公测中」）**，且**尚未跨过 PMF 线**——依据是「无爆款、中位安装 8 次、装机 < 1,000」。它现在的问题不是「能不能长大」，是「**还值不值得继续长大**」。

## 八、可迁移结论与机会点（L7）

### 8.1 值得直接抄的 6 条（这是本报告最有价值的部分）

| **1** | **TOML 声明式接入，零侵入、无 SDK** | 把「接入成本」压到一份配置文件，从而把供给面从「会写 GUI 的开发者」扩大到「会写脚本的所有人」。**任何 UGC 工具平台的第一条** | 插件平台、模板市场、脚本市场 |

| **6** | **自建 UI 组件库（双框架兼容）** | 一举解决国产开源工具最常见的死因（界面丑），并把未来迁移的钥匙握在自己手里 | 长期维护的 Python 桌面项目 |

### 8.2 不要学的 5 条

| # | 坑 | 为什么致命 |
|---|---|---|
| 1 | **把「永远免费」写成品牌承诺（4 处）** | 法律门开着、品牌门焊死。应写「当前免费」/「公测期免费」 |
| 2 | **形态跳跃：从单点直接跳到平台** | 方法论明写形态阶梯：单点工具 → 工作流套件 → 平台/生态（个人几乎必败）。**先做一个爆款脚本，再做盒子** |
| 3 | **卖点写成价值观（「一切皆脚本」「给电脑装上超能力」）** | 用户要的是「这个文件能批量改名」。需要教育才被理解的卖点 ≈ 不存在 |
| 4 | **一个人同时维护 4 个系统** | bus factor = 1，且跨 Python/C#/Web 三栈 |
| 5 | **把资源投在 T4 长尾（微信推送、菜单样式切换）** | v1.4.6 一半篇幅在这上面，而「最该做的事」一件没做（见 8.3） |

### 8.3 机会点：把 A 层剥出来，做「脚本分发底座」（B 端单边）

**这是全篇唯一我认为结构上成立的切入点。**

| 项 | 内容 |
|---|---|
| **做什么** | 不做社区、不做商店。只做「**把一堆命令行脚本，变成同事能双击的按钮**」的私有化底座：TOML 声明 → 参数面板 → 环境隔离 → 定时 → 权限 → 内网离线分发 |
| **卖给谁** | ① 企业 IT / 数据团队的内部工具分发（10–50 人规模）；② 有脚本但没有分发渠道的独立开发者（白标打包） |
| **为什么成立** | **单边即可成交**——一个部门 20 人就能签单，不需要社区、不需要双边冷启动；**无云成本**（完全离线）；**支持面窄**（一个 TOML schema + 一套部署文档，可自助）；**边际成本 ≈ 0**（多一个客户不增加人工） |
| **定价** | ¥2,000–20,000/年/团队（按席位 ¥100–300/席位/年）；或白标授权 ¥5,000–30,000/年 |
| **复用度** | **代码 100% 复用**，只改分发形态（去社区、加白标、加权限、出部署文档） |
| **为什么他现在做不了** | 他把自己定位成「免费开源项目作者」，没有主体（自然人无法开票）、没有 ToS、没有商业授权话术——**但 LICENSE 里的商业授权条款，恰好就是为这条路留的** |
| **风险** | 从「产品」变成「项目制服务」：单价高但不可规模化；B 端要发票、要合同、要一点实施支持（不重，但不再是纯自助） |

**为什么不是别的机会**：
- ❌ 做 C 端脚本商店 → 已在场证明不行（96 脚本 / 1,030 安装 / 无爆款）。
- ❌ 做「脚本打包器」卖给开发者 → PyInstaller/Nuitka 免费，付费意愿极低。
- ❌ 做 AI 工作流编排 → Raycast/uTools 已在，且需算力成本。

### 8.4 最小验证（2 周，成本 ≈ 0）

| 步 | 动作 | 判定门槛（**先写死**） |
|---|---|---|
| 1 | 把现有盒子做一次「企业版」话术改造：去掉社区入口，加「私有脚本库」说明页 | 1 天 |
| 2 | 找 **3 家**有内部脚本的分发对象（自己公司 IT / 朋友公司数据团队 / 一个做 RPA 的外包） | 能指名到人 |
| 3 | **人肉代做**：免费帮其中 1 家把 5 个脚本装进盒子，记录真实耗时 | ≥ 5 个脚本在 2 小时内完成接入 = 产品成立；> 2 小时/个 = 形态不对 |
| 4 | 直接问价：「这套东西 ¥5,000/年，你们买吗」 | **≥ 1 家明确说买**（口头不算，要报价单回复）→ 立项；3 家全说「再看看」→ 杀 |

### 8.5 如果坚持做 C 端，唯一可走的路

**放弃「商店」，只做「一个爆款脚本 + 运行器」。** 具体：
1. 从 96 个脚本里挑**唯一一个**「高频 + 有付费意愿 + 免费替代弱」的（按现有数据，最接近的是「截图美化 / 批量图片处理」，但这两格已被免费在线站吃掉；真正没被吃的是「**A3 试卷分割 A4**」这种极端垂直的教育场景）。
2. 把这个脚本做成**独立产品**（不需要盒子也能跑），用它去获客。
3. 用户量起来之后，再把盒子作为「进阶版」卖给其中 1%–3% 的人。

**这条路的问题**：它等于把已经做好的平台拆掉重做——**沉没成本会强烈阻止他这么做**。所以现实中他不会走，这也意味着这个项目大概会停在「一个做得很好的免费开源工具」这个位置上。

### 9.1 四道闸门（顺序否决）

| 闸门 | 判定 | 依据 |
|---|---|---|
| **① 收得到钱** | ✅ **过** | 有付费先例（Quicker ¥57.6/年、uTools ¥98–99/年）；Commons Clause 已留商业授权口子；微信/支付宝个人码已在用（打赏）。**但注意：法律上过，品牌上被自己封死** |
| **② 扛得住成本** | ❌ **不过** | 双边市场客服 = 每个脚本的环境/兼容问题都是他的工单；UGC 代码分发的审核与追责能力为 0；人工边际成本 ¥7,200/月量级（附 B4），对照收入 ¥0 |
| **③ 送得到人** | ❌ **不过** | 已试 6 个渠道（GitHub / Gitee / 蓝奏云 / 夸克 / 52pojie / 软仓转载），5.5 个月 300–520 装机。**渠道都试过了，天花板就在这里** |
| **④ 算得过账** | ❌ **不过** | 若走订阅 ¥68/年、2%–5% 转化，需 2.9 万–7.4 万装机才能年入 ¥10 万；按当前年化 870 装机 → **需 33–84 年**（附 B3）。机会成本 ¥4.8 万–19.0 万（附 B5） |

> **②③④ 三道同时不过，是结构性问题，不是努力问题。** 而这一切的根因在第一道闸门之后的那句话：**「收得到钱」过了，但「收得到人」过不了——而没有人，钱从谁那里来？**

## 附 B · 测算过程与敏感度（与实测分开）

### B1 装机量推算（两法互证）

| 段 | 内容 |
|---|---|
| **假设** | 人均安装脚本数 = 2–3 个 |
| **依据** | uTools 免费版限 10 插件，重度用户装 8–15；轻度用户 2–3。该产品无插件数限制，但脚本需逐个探索，实际接近轻度用户区间。中位安装 8 次 / 96 个脚本的分布也支持「大多数脚本只被装几次」 |
| **推算 A（自下而上）** | 装机 = 1,030 ÷ 3 ~ 1,030 ÷ 2 = **343 – 515** |
| **推算 B（交叉校验）** | GitHub 下载 199；若 GitHub 占总下载的 40%–65%（其余走蓝奏云/夸克/光鸭/软仓/西西等镜像），总下载 = **306 – 498** |
| **结果** | **装机 P50 ≈ 400，区间 300–520** |
| **置信度** | **中**（两次独立估算落在同一量级，且量级一致为「百级」） |
| **推翻条件** | 若得知真实 installer 数 > 2,000，则「分发天花极低」的结论需要修正；若 < 150，则连「Beta 有用户」都不成立 |

**敏感度（人均安装数）**：

| 人均 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|
| 推算装机 | 515 | 343 | 258 | 206 |

→ 区间 **206–515**，量级不变。**结论不翻转。**

### B2 收入上限（打赏）

| 段 | 内容 |
|---|---|
| **假设** | 打赏转化率 0.5%–2%；人均 ¥20–50 |
| **依据** | 国产开源工具捐赠转化普遍 < 1%；同赛道已有一个零收入样本（PopDrop：333 star / 2,070 下载 → ¥0） |
| **推算** | 400 装机 × 0.5%–2% = **2–8 人** × ¥20–50 = **¥40–¥400**（累计 5.5 个月） |
| **年化** | **¥90–¥870** |
| **交叉校验（同模式效率法）** | 若按 uTools 的单用户年收入 **≈ ¥2.1**（推算 250–1,100 万营收 ÷ 500 万用户）套算：400 × 2.1 = **¥840/年** —— 与上面同一量级 |
| **结果** | **打赏收入 ≈ ¥0–¥900/年。不是「低」，是「零」。** |
| **置信度** | **中高**（两法互证 + 同赛道零收入先例） |

### B3 若走订阅：需要多少用户（这是判决的核心算式）

| 段 | 内容 |
|---|---|
| **目标** | 年净收入 ¥10 万（个人开发者生存线下限） |
| **定价** | ¥68/年（锚点：Quicker ¥57.6、uTools ¥98–99 的中间值） |
| **付费转化** | 2%–5%（工具类免费转付费的行业区间） |
| **推算** | 付费用户 = 100,000 ÷ 68 = **1,471 人**；装机 = 1,471 ÷ 5% ~ ÷ 2% = **2.9 万 – 7.4 万** |
| **当前增速** | 400 装机 / 5.5 月 → 年化 **≈ 870 装机/年** |
| **所需年数** | 29,000 ÷ 870 ≈ **33 年**（乐观）；73,500 ÷ 870 ≈ **84 年**（悲观） |
| **结果** | **在现有分发能力下，需要 33–84 年。** |

**三重敏感度**：

| 变量 | 悲观 | 基准 | 乐观 | 所需年数（乐观/基准/悲观） |
|---|---|---|---|---|
| 定价 | ¥54（−20%） | ¥68 | ¥82（+20%） | 41 / 33 / 28 |
| 付费转化 | 2% | 3.5% | 5% | 84 / 48 / 33 |
| 装机增速 | 435/年（−50%） | 870/年 | 1,740/年（+50%） | 168 / 84 / 42 |

→ **全部情形都在 28 年以上。结论不翻转。**

**但必须说清一个反转条件**：若发生**一次分发事件**（大 V 推荐 / 应用商店首页 / 某个脚本爆红）带来 10 万装机，则 33 年 → 0.3 年，**结论立刻翻转**。所以准确的表述是：

> **这个产品的命运由「一次分发事件」决定，而不由「任何一轮功能迭代」决定。** 而分发事件不来自产品改进——这就是为什么「再迭代 6 个月」是错的努力方向。

### B4 人工边际成本（闸门 ② 不过的定量依据）
