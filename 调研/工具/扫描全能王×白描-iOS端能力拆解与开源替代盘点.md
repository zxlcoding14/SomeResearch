## 0. TL;DR（结论先行）

| 问题 | 直接答案 |
|---|---|
| 两款 App 的能力关系 | **不是同一类产品**。扫描全能王是「扫描 → OCR → PDF 编辑/转换 → 云文档管理」的全链路办公套件；白描是「OCR 识别 → 扫描件/PDF 生成」的轻量效率工具，无 PDF 编辑、无云盘、无协作。 |
| 用什么框架 | **两者 iOS 端都是原生开发，不是 Flutter / React Native 这类跨平台框架**。白描是 iOS 工程师独立开发（Xcode 工具链）；扫描全能王是合合信息自研 SDK 体系。 |
| 核心技术差异 | 扫描全能王 **自研 OCR 引擎（TextIn）**，印刷体 99.7% / 手写 97%（官方宣称），含自研去畸变、去阴影、表格结构还原；白描 **不自研引擎**，创始人亲述「自己从头做识别引擎几乎不可能」→ 长期采用第三方云端 OCR（百度系）。 |
| 是否有开源替代 | **有，但只能拼装，不存在「一键替代品」**。开源侧最接近的两块：完整扫描 App 用 `Open Scanner (MIT)` + Apple VisionKit；OCR 用 `PaddleOCR / RapidOCR (Apache-2.0)`。 |
| 替代的真实缺口 | 扫得动 ≠ 认得准。**非刚性去畸变（弯曲书页/褶皱）、去阴影、表格/公式版面还原**这三块是商业 App 的核心壁垒，开源方案停留在论文级 demo，工程化落地成本高。 |
| 复刻建议 | 做「扫描 + 文字提取 + 可搜索 PDF」→ 开源完全够用，成本可控；做「表格转 Excel / 公式识别 / 高精度手写」→ 要么买 SDK（TextIn/ABBYY），要么自训模型，开源不留退路。 |

### 2.6 结论：一句话定位

- **扫描全能王 = 手机上的「扫描仪 + OCR + PDF 编辑器 + 云文档库 + 传真机」**，功能宽度没有任何开源项目能一对一覆盖。

## 3. 技术框架：它们各自是什么做的

### 3.1 白描 —— 原生 iOS + 第三方云 OCR

| 事项 | 判断 | 证据与标签 |
|---|---|---|
| 客户端框架 | **原生 iOS（Objective-C / Swift），非跨平台框架** | 开发者陶新乐（Tolecen）为 iOS 工程师出身；访谈中自述日常工作「离不开 Xcode」，产品线全为独立 App；查无任何 RN/Flutter 使用痕迹。【二手·高：开发者一手访谈】 |
| 开发组织形式 | 个人 + 小团队（2017-06 辞职转独立开发） | 少数派 / 利器 / AppSo 多个一手访谈一致。【二手·高】 |
| OCR 引擎来源 | **不自研，采购第三方云端 OCR 服务** | 创始人原话：「自己从头完全做自己的识别引擎几乎是不可能的事，于是研究了市面上可以提供这个服务的厂商的产品并进行对比」——AppSo 专访原文。【二手·高】 |
| 具体供应商 | 指向百度 OCR | 百度百科词条：「采用百度 OCR API」；另有一位 iOS 开发者对白描抓包的公开记录：白描「选中文字行 → 逐行转文字」的行为与百度 OCR 返回的坐标数据吻合，其原文即感慨坐标来自百度。【二手·中高】 |
| 是否使用 Apple Vision | **否** | App Store 官方文案：「高精度 OCR 识别引擎，**远胜过 iOS 自带的文字识别**」——明确把自己与系统识别区分开。【审计】 |
| 图像预处理 | 自研（白描真正的技术活） | 创始人列举：图像压缩保清晰、波纹过滤、长图自动裁剪、去杂乱背景、自动分段、自由选区。【二手·高】 |
| 隐私说明 | 官方隐私政策写明：使用 OCR 识别时「会先上传文件至服务器识别后返回结果」 | 白描 PDF 隐私政策原文。【审计】 |
| 「离线识别」说法 | **存疑，官方未背书** | 「支持离线识别」仅见于第三方下载站与自媒体（今日头条系、下载站），官网与隐私政策均未声明端侧识别，且隐私政策反向说明会上传。判定为低可信。【二手·低】 |

### 3.2 扫描全能王 —— 原生 iOS + 自研 OCR 全栈

| 事项 | 判断 | 证据与标签 |
|---|---|---|
| 客户端框架 | **原生 iOS**，与 Android / 鸿蒙各自原生实现；非跨平台框架 | 合合信息为 iOS 端侧 SDK 与硬件方案供应商，且 2023-12 与华为签约做鸿蒙原生开发——跨平台框架路线与「鸿蒙原生应用」定位互斥。【官方宣称 + 推算·依据】 |
| OCR 引擎 | **自研，产品名 TextIn** | 合合信息官网：「专注于智能文字识别技术 15 年，自研文字识别引擎……**为扫描全能王、名片全能王提供底层识别能力**」，印刷体 99.7%、支持 50+ 语言、10+ 复杂场景。【官方宣称】 |
| 部署形态 | 公有云 API + 私有化部署 + **端侧 SDK（iOS/Android/HarmonyOS/Windows）** + AIoT | TextIn 产品页明列四种部署方式，端侧 SDK「无需网络即可使用」。【官方宣称】 |
| 关键算法（第三方解读） | 非刚性去畸变：预测 3D Mesh 而非四个角点，像素重映射「熨平」曲面；去阴影：GAN（生成器补像素 + 判别器判真伪）；表格结构：GCN 图卷积，把文本块当节点预测邻接关系 | 来源为 OCR 垂直媒体解读文章，非官方技术白皮书。【二手·中】 |
| 手写技术路线（官方口径） | 三级架构：智能图像处理层 → 基于注意力机制的检测分割层 → 改进 CRNN + Transformer 序列识别层 | 合合信息官方技术博客。【官方宣称】 |
| 可信度提示 | 「99.7% 印刷体 / 97% 手写」为**官方自评口径**，无第三方基准（如 OmniDocBench）交叉验证 | — |

### 3.3 框架层结论

1. **两款 App 都不用跨平台框架。** 扫描与 OCR 是重相机管线 + 重图像处理场景，对 Metal/Core ML/相机帧回调的掌控要求高，业界普遍选原生——这也解释了为什么其包体（401 MB / 48.8 MB）远大于同类跨平台应用。
2. **真正的技术分水岭不在框架，而在引擎。** 白描的「框架」问题在 PM 视角下几乎不重要：它的护城河是**交互打磨 + 第三方引擎选型**，可复制性高；扫描全能王的护城河是**自研引擎 + 论文级图像恢复算法**，可复制性低。
3. **白描的技术风险是结构性的**：核心识别能力依赖外部供应商（且为云服务），成本与毛利受制于人，且隐私说明与「本地处理」的营销话术存在张力。

### 3.4 证伪记录（重要）

检索过程中命中两篇标题为「白描技术破局与生态构建」「白描 OCR 文案识别技术解析」的文章（百度智能云/开发者社区域名），内容声称白描：

- 采用 **Flutter** 构建 UI 层、**Electron** 开发 Windows 端、Chrome 扩展；
- 在 GitHub 开源核心图像处理模块（1.2k Star）、举办 OCR 算法挑战赛；
- 与蚂蚁链合作做**区块链存证**（已处理 12 万份法律文件）；
- 设有「白描之星」用户激励计划、开发者平台、模型市场。

**判定：不可信，属 AI 生成的拟真内容，本次不采信。** 依据：① 与开发者一手访谈严重冲突（个人/小团队开发者，产品线仅 OCR 与效率类小工具，无企业级生态动作）；② 白描无 GitHub 官方组织与开源仓库；③ 无任何一手信源（官网、App Store、开发者访谈、播客）提及上述任何一项；④ 文中技术细节（Flutter + Electron + 区块链存证的组合）与产品实际形态矛盾。

> 这类内容在「XX 技术架构解析」类关键词下密集出现，做技术选型调研时是主要污染源。**凡非官网/非一手访谈/非仓库的技术描述，一律降级处理。**

## 4. 开源替代：分层清单

替代不是「找一个开源 App」，而是**五层各自替换**。

### 第一层｜Apple 系统能力（免费，但闭源）

| 组件 | 能力 | 说明 |
|---|---|---|
| VisionKit `VNDocumentCameraViewController` | iOS 13+ 系统级文档相机：边缘检测、自动拍照、透视校正、多页扫描、自动增强（除倾斜/展平/对比度） | 免费、零依赖、无自定义空间（不能改 UI、不能限页数） |
| Vision `VNRecognizeTextRequest` | 端侧文字识别，支持中英日等多语言混合 | 与文档相机无缝组合；`recognitionLevel` 可选 fast/accurate |
| VisionKit `DataScannerViewController` | iOS 16+ 实时文本/条码识别 | 用于实时取景识别，非整页扫描采集 |

> 边界提示：**Google ML Kit 的 Document Scanner API 仅支持 Android**（Google 官方文档明示，最低 API 21、需 1.7 GB 内存、依赖 Google Play 服务）。iOS 侧只能用 ML Kit 的 Text Recognition v2，没有文档扫描器。跨端团队常在这里踩坑。

## 7. 给 PM 的落地判断

**如果要复刻「白描」这一层（识别工具）：**
- 技术路径：VisionKit 采集 + Apple Vision 保底 / PaddleOCR 或 RapidOCR 提精度 + 自建校对交互。
- 难度与壁垒都在「非技术」侧：批量体验、选区交互、校对同屏、买断定价的信任感。白描 ¥30–¥40 买断、无广告，是靠个人开发者口碑撑起来的定价锚，商业团队很难用同样价格覆盖成本。
- 提醒：**白描的识别能力可被复制，但它的成本结构不可被复制**——个人开发者用云 API 按量付费，没有团队固定成本。

**如果要复刻「扫描全能王」这一层（办公套件）：**
- 直接放弃自研引擎。真要做，只有两条：买 TextIn/ABBYY 类 SDK，或基于 PaddleOCR 自训 + 自建服务端。
- 相机体验可 100% 用系统 VisionKit 起步，把资源全部投到「扫描质量」与「结构化输出」这两个用户真正付费的点上。
- 开源能覆盖的，恰好是**不构成付费理由的部分**（采集、增强、基础 OCR、PDF 工具箱）；开源覆盖不了的，恰好是**付费墙后面的部分**（曲面矫正、复杂表格、版面还原、云协作）。

**一句话总结：开源替代可以让一款扫描 App「跑起来」，但不会让它「卖得动」。**

## 附 B｜推算过程

本次涉及判定性推算两处，与实测数据分开列出：

**B1. 「白描是否自研 OCR」的判定链**
- 前提 1：创始人一手访谈明确说「自己从头做识别引擎几乎不可能」→ 排除自研。
- 前提 2：百度百科词条标注「采用百度 OCR API」。
- 前提 3：第三方 iOS 开发者对白描抓包的公开记录显示，其「逐行选字」功能的行为与百度 OCR 返回坐标吻合。
- 前提 4：App Store 文案自称「远胜过 iOS 自带的文字识别」→ 排除 Apple Vision。
- 结论：白描 iOS 端的识别能力主要来自第三方云端 OCR（指向百度）。
- 置信度：**高**。三条独立证据同向。唯一残余风险是版本迭代后已更换供应商。
- 敏感度：即使供应商更换为自研或他家，**「不依赖系统 Vision、采用外部服务商」这一结构性结论不变**，第 7 节的成本结构判断不受影响。

**B2. 「两者均不用跨平台框架」的判定链**
- 前提 1：白描开发者自述 iOS 工程师出身、工作依赖 Xcode；产品线为多个独立 iOS App。→ 原生。
- 前提 2：扫描全能王所属公司为端侧 SDK 供应商，且与华为签约「鸿蒙**原生**应用开发」——若其 iOS 端使用跨平台框架，产品形态与「原生」定位会自相矛盾。
- 前提 3：两者 iOS 包体分别为 401 MB / 48.8 MB，远超典型跨平台框架应用基线，符合「原生 + 内置模型/资源」特征。
- 结论：两者 iOS 端均为原生实现。
- 置信度：**中高**（属推断，非官方披露）。标注为【推算·依据】。
- 敏感度：该结论即使翻转，也不影响第 4–6 节的开源替代判断。
