## 〇、结论先行（TL;DR）

1. **池子见底的判断成立，且剩余 3 个立项候选可以收敛成两条主线**：① 通用效率线 = 一台「录屏/屏幕捕获引擎」+ 多种导出模板（A1 为核，A3 交互 Demo、E4 多格式切片、B9 排版全部是它的导出形态）；② 垂直行业线 = 「高客单价 × 小人群」的卷宗/资料整理（J1 律师、J7 工程）。后续资源应按这两条主线分配，不再按 68 个散点分配。
2. **J1 律师卷宗仍是第一优先，但分数已修正：96 → 约 90（见下钻文档）**。修正原因：2026-10-26 复采发现「Windows 桌面 + 本地存储 + 免费」这个位置已被圆周律πLex 占住，腾讯智审对律师免费做证据目录，WPS 365 以 ¥599/人/年把 AI 编目打包进办公套件。**结论不变：仍与 A1 并列做，但产品假设收窄成楔子——零配置 / 案由要件模板库 / 团队模板一致性**，不做全功能卷宗工具。下钻见 `律师卷宗方向-能力拆解与Windows工具可行性.md`。
3. **A2 桌面屏幕记忆建议从 P1 降级为「观察/有限测试」**（对原文结论的修正）。理由：① 头号竞品 screenpipe 本身开源且已商业化，是「开源竞品」而非「开源底座」；② 微软 Recall 已在 Copilot+ 机型系统内置，系统内置威胁已部分兑现；③ 常驻捕获 + 本地向量索引是重工程，与单人时间预算不匹配。
4. **否定性结论：68 个场景里没有任何一个「面向大众 C 端」的方向能活**——所有可尝试方向都收敛到「垂直专业人群」逻辑上。这与方法论「¥299/¥999 客单价 × 小规模高意向人群」的最优区间判断完全一致，也反证池子冻结 54% 的判法是可信的。
5. **J7 工程投标资料整理当前最大的缺口不是需求，是分发**：痛点真实（投标废标 = 直接经济损失）、玩家少，但「我能否 2 周零预算触达 20 个造价员/资料员」未验证——三问快筛第 3 问（一票否决项）目前答不出来。先跑分发测试，再谈产品。
6. **A1 的市场选择建议：海外先行或国内小微自助**。海外付费已被 Scribe $25/月（≈¥178/月【换算·假设7.1】）、Tango、Guidde 等验证，MoR 通道（Paddle 类）个人可用；国内空白既是机会也是信号——国内团队级工具的收款（发票、对公）对个人不友好，国内试应锁定「小微自助型 B」，绕开席位销售。

## 一、口径与整体读法（L0）

- 粒度：方向池级研判（非单品报告）；快照：2026-10-26。
- 输入可信度：场景池的竞品判决为二手整理（⑤→③ 级），本文的增量在「收敛逻辑 + 打分 + 闸门判定」，不在重新取证。**若进入证伪阶段，A1/J1 的竞品价格需按附 C 清单重核。**
- 池子统计复述：🟢 3（4%）· 🟡 9（13%）· ⚪ 7（10%）· 🔴 37（54%）· ❔ 12（18%）。**52 个场景已被判死或冻结，本文只在剩余 16 个（🟢🟡⚪❔）里做二次筛选。**

## 二、为什么是「两条主线」——池子的结构性读法

把 16 个非冻结场景按「能力内核 × 人群出口」重排，会出现明显的复用关系：

| 主线 | 能力内核 | 复用出口（模板） | 人群 | 商业形态 |
|---|---|---|---|---|
| **通用效率线** | 录屏/捕获 → AI 结构化（A1） | A3 交互式 Demo · E4 长视频→多格式 · B9 文档排版导出 | 培训师 / 客服团队 / 产品经理 / 自媒体 | 订阅（有云端处理成本）|
| **垂直行业线** | 文件/卷宗理解 → 结构化整理 | J1 律师卷宗 · J7 工程投标资料 · （B5 附件归档为监听模板） | 律师 / 造价员·资料员 | 高客单年费 |

这张表的含义：**🟡 的 9 个场景大多数不是独立方向，而是主线的导出模板或数据源**——池子自己已经这么标了（A3「并入 A1 v2」、E4「=A1 v2」、F5「屏幕记忆引擎的远程数据源模板」）。这意味着实际要做的产品数量是 2 个，不是 16 个。**一台引擎 + 多个出口同时解决了「单点工具市场太小」和「套件开发太重」的矛盾。**

## 三、逐方向评估（打分卡 + 闸门）

### 3.1 A1 录屏→SOP/操作文档（池子 P0，维持）——约 81 分，中间带偏上

| 维度 | 分 | 依据 |
|---|---|---|

| 痛点硬度 ×3 | 4 | 手工写 SOP = 录屏 + 截图 + 排版，单篇数小时【推算·经验】 |

| 替代糟糕度 ×2 | 4 | 手工流程痛苦；国内无成熟本土化工具 |
| 付费方 ×2 | 4 | 海外 $25/月级已验证（Scribe）；国内待证 |
| 持续交付成本 ×2 | 4 | 云端视频处理 + 模型调用 → 订阅成立 |
| 独占优势 ×2 | 2 | 无 |
| 窗口期 ×1 | 3 | 钉钉/飞书有内置可能，但优先级不高 |
| 合规 ×1 | 5 | 录屏内容涉及企业内部信息，需隐私说明，风险低 |

**判定**：维持 P0，两周 falsify 计划正确。**关键分歧点在市场选择**：国内空白更可能是「国内付费意愿/收款结构不支持」而不是「没人想到」。最小验证建议**直接收钱**：做 3 个真实 SOP 的对比 Demo，挂 MoR 收款页（海外）+ 人工收款（国内），只认付费信号。同时按一票否决第 5 条自问：去掉 AI，录屏+时间轴截图+模板导出还剩多少价值？——答案是仍有 70% 价值（AI 只是加速结构化），这是它比多数 AI 包装型工具健康的地方。

### 3.2 J1 律师卷宗/证据梳理（池子 P1.5，建议升格）——约 96 分，过线

| 维度 | 分 | 依据 |
|---|---|---|
| 频次 ×3 | 4 | 诉讼律师案头工作，按案件日频 |
| 痛点硬度 ×3 | 4 | 卷宗整理按计费小时折算是直接的钱；开庭前刚需 |
| 分发 ×3 | 3 | 律师社群（青年律师群/律所内推网络）可触达，待实测 |
| 替代糟糕度 ×2 | 4 | 牛马AI 泛化覆盖无垂直深耕；人工整理外包按页收费且慢 |
| 付费方 ×2 | 4 | 律师付费先例充分（幂律 ¥980 起、通义法睿按页【官方宣称·转引】）|
| 持续交付成本 ×2 | 3 | 云端模型调用，有真实成本 → 年费成立 |
| 独占优势 ×2 | 2 | 无独占数据，靠垂直打磨 |
| 窗口期 ×1 | 3 | 大厂法务线聚焦合同审查（J2），卷宗是脏活，2 年内大概率不碰 |
| 合规 ×1 | 3 | 定位「辅助整理」不输出法律意见，避开 J2 的合规深水区；但需律师数据保密承诺 |
| 收款 ×3 | 4 | 个人律师/小所可走对公或个体户开票 |
| 隐性成本 ×3 | 3 | 需要懂卷宗结构（非纯粹技术活），学习成本前置 |
| 客体匹配 ×2 | 4 | 单点工具 + 小人群，匹配 |

**判定（2026-10-26 修正）**：**保持与 A1 并列的并行验证项，但打分从 96 下调至约 90（替代糟糕度 4→3、付费方明确度 4→3、窗口期 3→2）**。修正依据：圆周律πLex（桌面免费、本地存储、自备 Key，已覆盖时间线/证据目录/缺口）、腾讯智审（对律师免费做证据目录）、WPS 365 ¥599/人/年（含 AI 编目 + 时间轴 + 法律关系图 + 私有化部署）三条新证据。方向不死的理由是剩余楔子不在任何一家能力域内：**零配置、案由要件矩阵、团队模板一致性**。完整拆解见 `律师卷宗方向-能力拆解与Windows工具可行性.md`。最小验证：按细分人群型原型 → 深访 20 名诉讼律师（**只问过去行为**：上次开庭前花几小时整理卷宗、是否用过 πLex/智审、是否自费买过工具），其中 ≥3 人表达明确付费意向才进入构建。

### 3.3 A2 桌面屏幕记忆（池子 P1，建议降级）——约 88 分，中间带，且带两个红信号

分数不低，但**质量比分数重要**：
1. **开源竞品不是底座**：screenpipe 本身开源、且以 $25 起商业化——它既是活跃竞品（抢用户）又证明该品类云端毛利难做。复用它做底座则 License 与商业模式直接冲突。
2. **系统内置已部分兑现**：微软 Recall 在 Copilot+ 机型免费内置。按 C 端方法论「定价天花板 ≈ 竞品价格 × (1−免费替代覆盖率)」，Windows 侧天花板被持续压低。
3. **重工程不匹配单人**：常驻捕获 + OCR + 本地向量索引 + 隐私脱敏，是一个 6 人月起的工程【推算·经验】，且上线后隐私类客服/合规问题密度高。

**判定**：降级为 ⚪ 观察。若仍想保留测试，唯一值得做的切片是 B5（邮件附件自动归档）这类**监听模板**——用屏幕记忆 10% 的能力解决一个可买断的单点需求，验证「捕获引擎」技术路线本身，不正面进入记忆赛道。

### 3.4 J7 工程/投标文件整理（池子 ❔ 首推，条件同意）——约 86 分，中间带，卡在闸门 3

需求侧信号好：投标废标 = 直接经济损失（痛点硬度 5 分级），玩家少。但**分发侧当前为 0**：造价员/资料员/投标专员聚集在建筑行业垂直社群，本 workspace 现有渠道触达不到。按个人开发者方法论闸门 3，**答不出「前 100 个用户从哪来」之前不投任何实验资源**。
**行动**：先花 1 周做分发侦察（找到 3 个具体的造价/资料员社群并能混进去），达成后再启动 J7 的三问快筛全流程。这也是把 J7 放在 ❔ 扫描首位时应有的前置动作——池子说「值得作为 J 域下一个验证点」，我同意，但**验证顺序应该是先验证「够不够得着人」，再验证「需求多痛」**。
